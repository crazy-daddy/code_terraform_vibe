### 1j. Field Mining Drill Telemetry (`lib/mining_drill.py`)

A drill needs no control. It extracts on its own; the only script surface is `drill_rate()` and a read-only `PickupOutputSlot` stockpile (docs/components/mining_drill.md). One controller (`MiningDrillController`) serves all three variants (`mining_drill`, `mining_drill_industrial`, `mining_drill_heavy` thin scripts).

- **Who publishes**: orchestrator_automation.py, every `DRILL_TELEMETRY_TICK_INTERVAL = 600` ticks, for every drill (`publish_all_drills()`: power-grid members of a drill type plus existing `drill.status` entries; one `MiningDrillController` per drill kept across passes so warnings fire once per change). A drill's own script publishes once and ends — the drill mines without a script, and a running script costs every script budget (dev_workflow.md §1d-1).
- **Poll**: `POLL_INTERVAL_S = 60.0` (Mk I: 2,000 units at 25 t/h = ~80 h to fill; Heavy: 5,000 at 200 t/h = ~25 h). Capacity always read live.
- **State**: `drilling` (rate > 0), `full` (rate 0, count ≥ capacity), `stalled` (rate 0 with room left: unpowered, no deposit, or deposit too hard; API can't tell these apart). Warn once per transition into `full`/`stalled`; info on recovery.
- **Near full**: fill ≥ `NEAR_FULL_FRACTION = 0.8` while drilling → one warning with time-to-full, re-armed once fill drops back under it.
- **Time-to-full**: `(capacity − count) / drill_rate()`, assumes 1 stockpile unit = 1 t (unverified).
- Thin script passes `drill_type` (published as `type`).
- **Telemetry** `drill.status` (§4). Drills sit on mineral sites, not the outpost network, so `ArchiveCleaner.clean_machine_status()` can't prune them; the age rule of `archive.publish_status()` (archive_ipc.md §4) does.
- **Pickup advert**: the `drill.status` entry's `items` is what the reverse hauler (§2i) reads as the drill's free stock; its position comes from its `MiningSite` (§2i "Drill location").

### 1m. Weather Station Signal Decoding (`lib/weather_signals.py`)

Recovers storm aftermath coordinates (Raw Uranium from dust storms, Storm Glass from thunderstorms; docs/guide/weather_system.md) and publishes them for drone collection (collection: §2j-1 in `vehicles_drones.md`).

- **Reception** (simworker `Fre()`): a powered station hears every `broadcast` copy plus its own biome's dust channel, planet-wide (no distance check). Thunder: 4 packets, all broadcast, so one station suffices. Dust: `DUST_PACKET_TOTAL = 8` packets, packet 1 broadcast, the other 7 spread over all 5 biome channels, so a dust message completes only with one powered station in **every** biome. Missing biomes are warned on change.
- **One running script**: `signal_receiver` is a read-only property, so the leader (lowest id among powered stations) reads every station's receiver; every other station's script ends at once. Stations re-discovered (and leadership re-checked) every `STATION_REFRESH_SWEEPS = 10` sweeps. Weather Stations are in no shed tier (§1a).
- **Sweep**: every `SWEEP_GAME_HOURS = 1.0` world-clock hour (`clock.real_seconds_per_hour()`, fallback `DEFAULT_REAL_SECONDS_PER_HOUR = 25.0`). Messages stay audible until storm end + `SIGNAL_GRACE_GH = 4.0`.
- **Validation**: valid copy = `sum(ord(c) for c in data) == checksum` and `data` = `event_id|number|total|dx|dy` matching the copy's fields. Noise copies reuse the valid checksum with a changed dx/dy. Coordinate = sum of dx/dy over packets 1..total (absolute world x/y).
- **Timing**: aftermath appears at storm end = `expires_at_gh − SIGNAL_GRACE_GH` (`ready_gh`) and lasts `AFTERMATH_WINDOW_GH` = uranium 48 h, storm_glass 96 h. The coordinate is usually known before `ready_gh`. Units: uranium 14–28, glass 2–4 (`AFTERMATH_UNITS`); one `collect()` takes at most 5.
- **Archive** (§4): `weather.signals` (incomplete messages, kept across restarts; dropped when their window closes) and `weather.aftermaths` (decoded sites, pruned after `expires_gh`). The leader's Signal Board shows the newest decoded site via `resolve()`.

### 1n. Fuel Assembler (`lib/fuel_assembler.py`) and Lead Casks (`lib/lead_cask.py`)

One script per Fuel Assembler (thin `nuclear/fuel_assembler.py`). Recipes (simworker): `craft_fuel_rod` = 4 Raw Uranium + 2 Lead Plates, 6 game h, 1,800 W; `craft_nuclear_battery` = 4 Raw Uranium + 3 Lead Plates, 4 game h, 1,200 W. Stockpile 40 units mixed, output buffer 5.

- **Demand, Fuel Rods first**: target = local consumer reserve (`lead_cask.consumer_rod_reserve()`: `ROD_RESERVE = 1` + `RODS_PER_REACTOR = 2` × Reactors + `RODS_PER_MK4 = 1` × Mk IV `temp_heater`/`pressure_generator`/`oxygen_generator` (`tier() >= 4`), constants in `lib/lead_cask.py`) + rods owed to Supply Dock orders, all at this outpost. Supply Docks take only cask rods above that reserve less the rods staged in the consumers (`lead_cask.rods_for_orders()`), so an Earth order never drains a Reactor's buffer. Have = rods in this outpost's casks + those consumers' `input.count()` + output buffer + a craft in progress. **Nuclear Batteries** next: `fabricator.manual_orders` entry (counted down on delivery) + max(0, dock orders + blueprint need − network stock) − pending.
- **Pick**: first short recipe whose one craft the stockpile plus local stock covers (uranium in this outpost's casks, plates via `storage.takeable_stock()`). Without a Fuel Rod cask only batteries are picked. A running craft or one with progress is never switched (`set_recipe()` answers `busy`). Both recipes share inputs, so a switch keeps the stockpile.
- **Staging**: inputs for min(shortfall, `STAGED_CRAFTS = 2`) crafts. The input port takes one source at a time: uranium via `lead_cask.take_from_casks()`, plates via `storage.take_item()`.
- **Power gate**: inputs are staged only while the grid's reserve (lower of battery fraction and `power.reserve_fraction()`) ≥ `START_RESERVE_FRACTION = 0.6`, so crafts run as bursts on a full bank; a staged craft runs to completion. Hard-shed in Power Guard tier 1 (§1a); `power.shedded` also stops new staging.
- **Lead Plates**: every Fuel Assembler outpost keeps a 200-plate stockpile (`site_supply.SITE_STOCK_TARGETS`, §2i-1). At home only, a standing upgrade order (requester `"fuel_assembler"`, §2a-1 item 4) also asks for the plates of the next `PLATE_ORDER_CRAFTS = 2` short crafts, cleared when nothing is short; off home it would pull plates home (upgrade-order roots are consumed at home). One shared requester: a second assembler overwrites the entry (harmless, see sizing).
- **Output**: Fuel Rods first straight into a local Supply Dock whose order owes them (`production.dock_owed_at()`), capped by `lead_cask.rods_free_to_ship()` (cask rods + rods in hand beyond the local consumers' reserve, the floor `rods_for_orders()` leaves the docks), the rest into this outpost's `fuel_rod` cask; Reactors and Mk IV generators pull from it. Nuclear Batteries: local dock order first (`dock_delivery_targets()`), then `storage.drain_port_storage_first(include=)`, `consume_manual_order()` on the stored units.
- **Idle** (nothing short): clears the recipe (needs an empty output buffer) and parks (`script_parking` kind `fuel_assembler`, wake after 3000 ticks). Poll `ACTIVE_POLL_S = 5.0`, `IDLE_POLL_S = 20.0`.
- **Sizing**: after the Weather Program unlock, dust storms come every 48 game h (simworker `rw()`), 14–28 Raw Uranium each: about 10.5 U/day if every one is decoded and collected, about 2.6 rods/day. One assembler makes 4 rods/day (6 h craft); a Reactor at heat 1.0 burns 1/3 rod/day, a Mk IV 0.1 rod/day. Uranium, not assembler time, is the limit (about 7 Reactors at full heat), so one assembler is enough.

**Lead Casks** (`lib/lead_cask.py`, tier 4, shared by the assembler, `drone_weather`, `supply_dock`, `terraforming` and `production`). A cask holds one hot item and unlatches when empty. A Depot unloading hot cargo takes the **first** cask at its outpost that is empty or holds that item with room (simworker drone `unload`), so scripts cannot pick the cask; roles are enforced by planning and repair:
- `lead_cask.roles` (§4): `{cask_id: "fuel_rod" | "raw_uranium"}`. `ensure_rod_cask()` (called by the assembler every step) gives one cask per outpost the `"fuel_rod"` role: a cask holding rods, else an empty one, else the least-full uranium cask. Needs at least 2 casks at the outpost. Entries of casks that no longer exist are pruned on write.
- `room_for()` (drone uranium collection, `drone_weather.cask_room()`) leaves out casks reserved for the other item.
- `repair()` moves Raw Uranium out of a `"fuel_rod"` cask with `transfer_to()` into other casks; `take_from_casks()` drains such a misfiled cask first. With every other cask full, the assembler stages that uranium into its own stockpile (`unlatch_rod_cask()`, up to `UNLATCH_STAGE_UNITS = 24` Raw Uranium staged; sets the rod recipe when none is set), so finished rods can still leave the output buffer. The cask unlatches when empty and the next rod latches it.
- `unload_target()`: cask for an eject of hot cargo (role allows it, room left), used by `supply_dock.drain_dock_cargo()`.

### 2a-0. Supply Dock cargo draining (`lib/supply_dock.py` `SupplyDockController`)

`set_order()` rejects with `"cargo_present"` while any cargo loaded in dock's 5 slots —
`clear_order()` deliberately does **not** drain cargo, only releases order assignment.
`drain_dock_cargo()` ejects every non-empty slot to Inventory (off home: a local Warehouse via `best_unload_target(outpost=)`, none with room → left in the dock); `step()` calls it (retries next
cycle) whenever `curr_order` is `None` but `dock.total() > 0`, before trying `set_order()`.

### 2a-0-1. Construction material demand cascade (`lib/production_cascade.py`)

`_cascade_blueprint_demand()` = single source of truth for "how much of any item — finished or
intermediate — active construction ultimately needs":

- Seeded from `required_item`/`required_count` across every pending/paused Construction Blueprint
  job (summed, deduped by job id).
- Seed netted against units already aboard ground vehicles (`_vehicle_cargo_counts()`, via
  `fleet.vehicles()` + live `cargo.stacks()`): a constructor Pioneer loads a whole chained-job batch
  while every job stays pending until built, so without this the Fabricator re-crafts the batch.
  Cargo a hauler pickup already reports aboard (`logistics_requests.aboard_units()`, counted as
  network stock) is not netted again.
- Breadth-first propagated down through Fabricator/Smelter recipe `inputs` (`recipe_inputs_for()`).
- **Only each tier's shortfall propagates down** — demand beyond item's current
  `inventory.count()`, so on-hand stock counted once. Example: 10 `power_line_segment` needed,
  3 in Inventory → 7 to build → 7 `titanium_ingot` needed, 5 in Inventory → only 2 propagate →
  4 `titanium_ore` needed (2:1 smelt ratio), not 20.
- Known limitation: item reachable via multiple paths nets shortfall against same Inventory
  snapshot independently per occurrence, slightly overstating demand under diamond-shaped recipe
  dependency — not worth full MRP-style solve for game's shallow (2-3 tier) chains.

Two consumers read cascade differently:
1. `get_fabricator_targets()` (§2a-1) uses **raw, uncapped demand** for items Fabricator can
   build.
2. `get_construction_material_reservations()` nets against current stock
   (`min(inventory.count(item_id), demand)`) — protect-from-shipping amount.
   `supply_dock.py`'s `step()`/`pick_best_order()` subtract this before deciding how much to
   `take()` or how "ready" order looks.

Deliberately conservative: job's full cascaded demand stays reserved while pending/paused, even
after cargo loaded (cargo not tracked here).

### 2a-0-2. Multi-Fabricator Support (`lib/production_core.py`, `lib/production_sites.py`, `lib/fabricator.py`)

`production.discover_fabricator_ids()`/`_default_fabricator()` find Fabricators at runtime (no hardcoded ids), network-wide (every `outpost_network.outposts()` entry; pass `outpost=` for one outpost). `discover_smelter_ids()` and `discover_supply_dock_ids()` same. `claim_recipe()`/`release_recipe()` (`lib/fabricator.py`,
`STALE_TICKS=600`, archive key `"fabricator.recipe_claims"`, shape `{outpost_id: {recipe_id: {"fabricator": id, "tick": n}}}` via `production.site_recipe_claims()`/`claim_site_id()`, so only machines at the same outpost block each other; flat per-recipe entries are dropped on the next write) stop multiple Fabricators converging on same recipe: `choose_recipe()`'s candidate loop claims each sourceable candidate in shortfall order, next on claim fail.

- **Pile-on fallback + even split**: if NO candidate exclusively claimable (only one recipe demanded), `choose_recipe()` joins biggest-shortfall one anyway, no idle.
  `get_fabricator_worker_ids(recipe_id, site_id)` (sorted live roster of Fabricators on that recipe at that fab site) splits `crafts_remaining` floor-plus-remainder: first `crafts % workers` ids get one extra, shares sum exactly (a worker may get 0 and idle). The join gate counts the same site only (`get_fabricator_worker_count(recipe_id, site_id)`).
- **Pipeline netting**: every "still needed" (`get_fabricator_active_recipe()`, `choose_recipe()`) = site target (§2a-0-6) − `SourceCache.held_stock(item, outpost)` (`local_stock()` + that outpost's Drone Depot stockpiles, `depot_stock()`; loaders such as Smelters and Supply Docks use `local_stock()`, since `take_item()` doesn't reach Depots) − `production.get_fabricator_pipeline(cache, site_id)` = output-buffer stacks + one craft's output per running craft of every Fabricator at that site (`_pipeline_by_site()`, memoized on `SourceCache`; no `site_id` = whole network).
- **Outpost-aware machines** (off-home Smelter/Fabricator): ports rest on `storage.local_port_target(outpost)` (`"inventory"` at home, else first local Warehouse; none → one warn, no connect). `take_item(outpost=)` pulls from local Warehouses only, output drains and `recover_input()`/`eject_excess_inputs()` go to a local Warehouse (`best_unload_target(outpost=)`), Smelter ore stock = `SourceCache.local_stock(item, outpost)` (home: `stock()`; elsewhere that outpost's Warehouses, one `.stacks()` sweep each per pass). Dock raw-ore reserve applies to home Smelters only. Smelter demand = `get_smelter_demands()` (netted vs `network_stock()`), and at every site (home included) per item `max` with `production.site_smelter_demands(outpost)` (`SmelterController.demands()`): local Fabricators' active-recipe need (`fab_site_gross_need()`) − local stock − in flight, so a site short of glass that sits at another outpost still smelts its own. Fabricator demand is per fab site (§2a-0-6). `production.machine_outpost_id(machine)` = `machine.outpost.id`.
- **Output drain**: Fabricator `drain_output()` first pushes each output stack straight into a local Supply Dock whose order still owes it (`production.dock_delivery_targets(item, count, outpost)`: `dock_owed_at()` = required − shipped − what this outpost's docks on that order hold; with Construction Blueprint demand for the item only stock + count beyond the gross blueprint demand may ship), via `storage.push_to_targets(port, item, count, [(id, cap)])` (connect refused / busy / nothing taken → next target; returns `[(id, moved)]`). The rest goes `storage.drain_port_storage_first()`: local Warehouse first, then `local_port_target()` (Inventory at home); Inventory-only items still land in Inventory (`best_unload_target()` → `_inventory_first()`). `consume_manual_order()` counts only the stored units. Smelter `drain_output()` pushes first into local Fabricators short of the ingot (`production.fabricator_wants_for()`, the `fabricator.wants` archive key, less what this Smelter already pushed against the same entry tick), then a local dock order (`dock_delivery_targets()`), then storage. Smelter (`drain_output()`, `recover_input()`), Fuel Assembler batteries, Seed Supply and Feed Maker drain storage-first too; `drain_port_inventory_first()` (Inventory first, a Warehouse only on `INVENTORY_FULL_STATUSES = ("partial", "target_full", "slots_full")`) serves the Seed Maker. Every port send goes through `send_stack(port, item_id, count, target) -> (moved, status, message)` (connect if needed, then send).
- **Material slots**: a multi-material input stockpile holds only so many distinct materials, per type (simworker `defaultItemStackSlots`): Fabricator 8, Feed Maker 8, Crop Automator 8, Waste Processor 10, Plant Terraformer 6, Habitat 5, Bio Lab 4, Bio Caster 4, Fuel Assembler 3, Seed Maker 3, Drone Depot 3/4/6 (only the Depot reports it, `slot_capacity()`). `take()` of a new material past the cap answers `slots_full` with unit room left, so a loader that leaves stray materials behind jams. `storage.hit_slot_cap(report)` spots it in a `take_item(report=)` result, `storage.eject_unneeded(port, keep, target)` ejects every stack not in `keep`. Users: Feed Maker (`eject_strays()`), Crop Automator (`eject_unused_seeds()`); Fabricator, Bio Lab and Seed Maker eject every unneeded input each step anyway. Test fakes enforce the same caps (`tests/game_stubs.py` `MATERIAL_SLOTS`).
- **Load chunking**: `load_inputs()` capped to `FABRICATOR_LOAD_CHUNK_SIZE = 10` units per call. `lib/smelter.py` ore top-up has matching `SMELTER_LOAD_CHUNK_SIZE = 10`; Supply Dock loading has `SUPPLY_DOCK_LOAD_CHUNK_SIZE = 10`.
- **Poll cadence** (Smelter and Fabricator `run()`): `step()` returns whether the machine is active (running, buffers non-empty, or it loaded/drained/ejected/set a recipe this step); `run()` sleeps `ACTIVE_POLL_SECONDS = 1.0` then, `IDLE_POLL_SECONDS = 2.0` otherwise. A script's step allowance depends on how many scripts run, not on how busy they are (docs/BENCHMARK.md, Load dependence), so a faster poll costs only this script's own steps. A Smelter that sets a new recipe tops up ore in the same step. Fabricator `load_inputs()` logs one `Loaded …` line per call, Smelter `drain_output()` one `Sent …` line per call.
- **Smelter refill hysteresis**: a running Smelter with `in_buf >= max(units_per_run, prefill_cap // 2)` skips the take (outcome `buffer_ok`), so top-ups come in larger batches instead of a feeder wait for 1–2 units every poll.
- **`production.craft_prefill_units(recipe, item_id, prefill_seconds=INPUT_PREFILL_SECONDS)`**
  (`INPUT_PREFILL_SECONDS = 30`, no archive state) = real fairness mechanism. Asks "how much staged to keep crafting next ~30 real seconds", not "how much left to load": `ceil(prefill_seconds / craft_seconds(recipe))` crafts' worth, floor one craft's requirement. `craft_seconds()` converts `recipe.duration_game_hours` via
  `SECONDS_PER_GAME_HOUR = lib/power.py's DAY_CYCLE_DURATION_SECONDS / 24.0` (reused, not redefined), divided by the machine's speed (`speed=`, `machine_speed(machine)` from `MACHINE_TIER_SPEED = (1, 2, 4)` for Mk I/II/III). Smelter/Fabricator `duration_game_hours` is the Mk I time on every tier (only the Feed Maker's includes its tier), so callers pass the speed: both controllers their own machine's, `production_sites.local_make_seconds()` the site's fastest machine of that kind (`_site_speed()`). `lib/smelter.py` ore top-up + `lib/fabricator.py`'s `load_inputs()` both cap take with this, plus chunk-size ceilings above (simple per-call cap, not primary fairness). Supply Dock stays on `SUPPLY_DOCK_LOAD_CHUNK_SIZE` only (no recipe/duration for prefill window).
- **Smelter demand = whole order tree** (`production.get_smelter_demands(cache)`, used by `lib/smelter.py` instead of `get_material_demands()`). `get_material_demands()` only sees ingot demand through each Fabricator's *currently selected* recipe (per-worker split, each share netted vs full stock separately), and `_cascade_fabricator_output_demand()` stops at Smelter outputs, so it misses the order tree. Gross-then-net-once: each `get_fabricator_targets()` entry with deficit `D` adds `D × ratio` per recipe input that is Smelter output; target set directly on Smelter output counts as-is; dock orders for Smelter outputs not in targets added; then net once vs total stock **and** every Fabricator's staged `get_stockpile()`.
- **Raw ore owed to dock never smelted**: `production.dock_remaining_requirements(outpost_id)`
  (`required − shipped − dock.count()` per item, active orders held by a dock at that outpost, `_dock_order_sites()`; an order held at two outposts counts at both; no `outpost_id` = every order) subtracted from local stock in `SmelterController.available_ore()` with the Smelter's own `site_id()` (home is no special case) — needed since real ingot demand can eat every unit.
- **Fab-site ingot buffer** (`production.fab_site_ingot_targets(outpost, cache)`): every outpost with a Fabricator keeps each Smelter output some Fabricator recipe takes as input, at `(target, need)` from `production.ingot_stock_levels()` (archive `production.ingot_stock_targets`, target default `storage.default_stock_target()` (unseeded before Warehouse research; seeded after, with `INGOT_STOCK_NEED = 100` per item, then editable; values in §2d `ore_stock_target()`)). Smelter side: when `select_needed_ore()` finds no sourceable real demand, `step()` runs it again on `site_ingot_refill()` (target − local − in flight, own outpost only) and refines for the buffer (outcome detail `refill: True`, log reason "the fab-site ingot buffer"); real demand found on a later step wins the selection again. Hauler side: `site_supply.ingot_wants()` (§2i-1). Fabricator side: a `load_inputs()` take of a Smelter output that moves 0 units calls `wake_local_smelters()` → `script_parking.wake_for_visit(id, hold=False)` for every parked Smelter at its outpost, at most once per item per `SMELTER_WAKE_THROTTLE_TICKS = 100`.
- **Dock order remainder = one helper, per order**: `production._dock_order_remaining()` → `{order_id: {item_id: required − shipped − Σ dock.count() over every dock serving that order}}`. Every dock-demand site (`get_fabricator_targets()`, `get_material_demands()`, `get_smelter_demands()`, `dock_remaining_requirements()`) reads it. Deduped per order id because several docks can share one order; loaded-but-undispatched units subtracted because they're in neither Inventory nor `shipped`.
- **Ore intake caps** (Smelter Step 3, `lib/smelter.py`): take amount =
  `max(0, min(SMELTER_INPUT_CAP − in_buf, SMELTER_LOAD_CHUNK_SIZE, max_ore_for_share − in_buf,
  prefill_cap − in_buf, fair_total − in_buf))`.
  - `share = ceil(demand_qty / workers)` = this Smelter's slice of current total demand;
    `max_ore_for_share` converts it to ore units via `(qty * units_per_run + output_count - 1) //
    output_count`.
  - `prefill_cap = craft_prefill_units(recipe, ore, SMELTER_PREFILL_SECONDS)` —
    `SMELTER_PREFILL_SECONDS = 30` (`lib/production_core.py`, with `SMELTER_INPUT_CAP = 50`; both also bound the
    Smelter's `smelter.wants` level for the Drone Depot's direct feed, §2h), split out from the shared `INPUT_PREFILL_SECONDS` so Smelters can
    be tuned alone. At 0.08 h/craft (2 s) that's 15 ore.
  - `workers` = every Smelter on the network holding the recipe (`smelter_recipe_peers(recipe_id)`).
  - **Fair-share cap** (`fair_total`): `(available local ore + Σ input buffers of every Smelter on this
    recipe at the same outpost, this one included) // local_workers`, from
    `production.smelter_recipe_peers(recipe_id, outpost_id)` → `(workers, buffered)` scoped to that
    outpost. Plentiful stock never binds; scarce stock splits evenly among machines sharing it.
- **Recipe switching hysteresis** (`select_needed_ore()`): while current recipe still demanded + sourceable, Smelter keeps it outright if it holds (or can take) claim; joiner (peer holds claim) may move to *unclaimed* recipe only if that recipe's demand ≥ `switch_min_demand()` = one `SMELTER_PREFILL_SECONDS` window of output (15 units for 2 s 1:1 recipe); each switch ejects the buffer and skips a step. Smelter releases old recipe's claim on switch.
- **Join gate** (same function): pile-on joining recipe peer already claims needs
  `demand ≥ switch_min_demand() × (workers after joining)`; else Smelter idles, outcome `demand_covered_by_peers`.
- **One `SourceCache` per Fabricator `step()`** too, built after the output/byproduct drains: `get_fabricator_active_recipe()` runs once and feeds `eject_excess_inputs()`/`load_inputs()`; `choose_recipe(cache)`, `target_reason(item, cache)`, `blueprint_demand_items(cache)`, `get_manual_order_blocking_items(outputs, orders, cache)` and `take_item(cache=)` share it.
- **One `SourceCache` per Smelter `step()`**: stock snapshot, recipe lists, `get_fabricator_targets()` (memoized on `cache._fabricator_targets`) computed once per step.
  `get_fabricator_targets()`, `get_fabricator_active_recipe()`, `get_material_demands()`,
  `_cascade_blueprint_demand()`, `_cascade_fabricator_output_demand()` all take optional `cache=None` (same behavior without).

### 2a-0-6. Per-site demand and order trees (`lib/production_sites.py`, `lib/site_plan.py`)

A fab site = outpost with ≥ 1 Fabricator (`fab_site_counts(cache)` → `{site_id: Fabricators}`, site id = `claim_site_id()`). Each root target's whole tree builds at the sites planned for it; a site's stock counts only for its own trees.

- **Roots and consumers**: `fabricator_root_targets(cache)` → `(roots, consumers, fabricator_outputs)`: the §2a-1 sources before the intermediate cascade, plus `{item: {site_id: qty}}` where each root is consumed (dock order items at the dock's outpost via `_dock_order_sites()`; a blueprint's own `required_item` (`blueprint_required_items()`: pending/paused jobs, minus units aboard vehicles) at `construction_site_id()` = `home` of the latest-reporting `role == "constructor"` in `fleet.status`, else home — one Constructor home assumed; everything else at home). Intermediates below a blueprint item are no consumer root. `get_fabricator_targets()` = roots + cascade, unchanged.
- **Site targets**: `get_site_fabricator_targets(site_id, cache)`. Fabricators at home only → `get_fabricator_targets()` itself. Otherwise per buildable root: `root_remaining()` = target − `network_stock()` (`held_stock()` at every outpost, cargo aboard haulers included, so a part on its way home isn't built again) − network pipeline; split across its planned sites by `split_units()` (by Fabricator count, floor plus remainder, first listed site gets the remainder); site seed = local stock + site pipeline + share; intermediates cascade from the seed against local stock only.
- **Shared site targets** (archive `production.site_targets`): a site's targets and ship plan, computed by any Fabricator, Smelter or the panel, are reused by every script for `SITE_TARGETS_FRESH_TICKS = 150` ticks (stamped with the tick the computation started; only an entry computed under the current `fabricator.site_plan` counts). A stale entry is recomputed by the script that takes its lease (`SITE_TARGETS_LEASE_TICKS = 300`); while the lease is held the others use the stale entry up to `SITE_TARGETS_MAX_STALE_TICKS = 600`. Entries not refreshed in `SITE_TARGETS_PRUNE_TICKS = 6000` are dropped on the next write. `get_site_ship_plan()` always computes (then shares): reserved hauls must come off at once. No tick (clock unreadable): computed locally, not shared.
- **Ship-before-craft** (`ship_units()`, `SHIP_OVER_CRAFT_SECONDS = 300`, `SHIP_SURPLUS_FACTOR = 10`): during that cascade each non-root item short at the site is first covered by units in flight to it (`logistics_requests.in_flight()`), then by shipping when spare elsewhere (`site_spare_elsewhere()`: other outposts' `outpost_free_tiers()` need tier, minus what another fab site keeps for its own targets, `_site_base_targets()` = the same cascade without shipping) is > 0 and either spare ≥ `SHIP_SURPLUS_FACTOR` × shortfall, or `local_make_seconds()` is `None` (no Fabricator/Smelter of that kind at the site, or a missing input no recipe makes) or ≥ `SHIP_OVER_CRAFT_SECONDS`. `local_make_seconds()` = crafts × `craft_seconds()` plus making each locally short input the same way (fluids count as available, one machine's time, depth 6). Delivery time is not estimated. Covered units come off the item's target and are not cascaded into its inputs; the ship part is the site's ship plan (`get_site_ship_plan()`), requested by §2i-1. Roots are never shipped (§2i-1 consumer site moves them).
- **Plan**: archive `fabricator.site_plan` (`production.SITE_PLAN_KEY`) = `{root_item: [site_id, ...]}`, written by `site_plan.plan_sites()` once per storage tick in headless `orchestrator_automation.py`, only on change. Unplanned roots fall back to `default_root_sites()` (consuming fab site, else home, else first fab site). New root: `min(fab sites, max(1, remaining // SPLIT_UNITS_PER_SITE))` sites, `SPLIT_UNITS_PER_SITE = 20`, ordered by most consumed there, least loaded (planned roots per Fabricator), home, id. Sticky while it has units left; dead sites dropped, replanned once none remain; entry removed once built; cleared when only home has Fabricators.
- **Hauling finished roots**: §2i-1 consumer site.

### 2a-0-3. Multi-Dock Support (`lib/production_docks.py`, `lib/fabricator.py`)

`discover_supply_dock_ids()` + `_all_dock_orders()` (`[(dock, order), ...]`) feed every dock's active order into `get_fabricator_targets()`,
`get_material_demands()`, `get_raw_material_reason()`. No claim coordination (unlike Fabricator recipes) — fulfillment inherently per-dock; several docks may serve same order, share shipped progress (`docs/components/supply_dock.md`), explicitly fine. `find_dock_order_requiring(item_id)` consolidates "which dock's order wants this item", shared by `get_raw_material_reason()` + `lib/fabricator.py`'s `target_reason()`. §2a-0-5 covers which order each dock gets.

### 2a-0-4. Multi-Fabricator active-recipe input demand (`lib/production_demand.py` `get_material_demands()`)

"Selected Fabricator recipe = explicit production intention" block loops `discover_fabricator_ids()` (fallback `["fabricator_1"]`), sums each Fabricator's own `get_fabricator_active_recipe()` input demand, not just first discovered Fabricator. Safe to sum: when several Fabricators share claimed recipe, `get_fabricator_active_recipe()` already divides `crafts_remaining` by worker count (§2a-0-2), so each adds only fair share.

### 2a-0-5. Multi-Dock order planning & weekly-deadline feasibility (`lib/supply_dock.py`)

Central planner `plan_dock_assignments(clock=None)` runs **once** per cycle from orchestrator_automation.py's AUTOMATION section (checked every `DOCK_PLAN_TICK_INTERVAL = 50` ticks, ~5 s, ahead of the storage pass's feeder-bound sweeps; replans only when `plan_signature()` changed or `DOCK_PLAN_MAX_TICK_INTERVAL = 600` ticks passed, see `docs/cheatsheet/panels.md`), not each dock re-scanning full Earth Order board every cycle. `set_order()`/`clear_order()`/
`set_enabled()` all `*(self only)*` hardware calls, so planner only decides — writes `{dock_id: order_id or None}` to `"supply_dock.order_plan"` archive key (`ORDER_PLAN_ARCHIVE_KEY`); each dock's `SupplyDockController.step()` reads its entry via `desired_order_id()` and does actual `set_order()` itself.

- **Campaign score** (`_score_campaign_order()`): 10, +50 for a recipe/tech unlock, + readiness share × `CAMPAIGN_READINESS_WEIGHT = 30`; key unlock orders `EARLY_UNLOCK_ORDER_IDS = ("helios_01", "vestibule_01", "helios_02", "spire_intake_2")` (Titanium Ingot > Power Line > Gas Pipe > Liquid Pipe Segment; Power Line needs Titanium Ingot) add `EARLY_UNLOCK_STEP = 31` × (4, 3, 2, 1) (`early_unlock_weight()`), so readiness never reorders them; + the look-ahead bonus below. Weekly: 5 + readiness share × 20.
- **Stability**: dock holding still-`can_fulfill_order()`-true order keeps it regardless of ranking — mid-shipment order not cleared over marginal priority diff. The held order also drives Fabricator demand (`production._all_dock_orders()`), so a dock never drops an order just because nothing is stocked yet. One exception, the **local cask rule**: an empty dock (`total() == 0`) whose outpost's Lead Casks hold still-owed hot units of another candidate order (`_cask_order_ids()` / `_local_cask_units()`) leaves its order for that one. The dock applies it only for a central plan entry (`plan_assigned`); the per-dock fallback never moves a dock off a fulfillable order.
- **Idle dock ranking: key unlocks, then local stock, then spread inside the outpost, then priority**: candidates the dock's site serves (Dock site roles below) re-sorted before each idle-dock assignment by `(not shippable from a local cask, not a key unlock order, local stock rank descending, docks at the same outpost on this order ascending, role share descending, priority descending, docks on this order network-wide ascending, dock-site affinity descending)`. Local stock rank (`_local_supply()`) = still-owed units the dock's outpost holds unpromised, in `LOCAL_STOCK_STEPS = 10` steps of the order; unpromised = less Construction Blueprint reservations (home only, like loading) and less units that docks already planned this pass at the same outpost claimed (`_promise()`). A weekly order ranks on local stock only when fully covered (a partly shipped weekly order expires unfinished). So across outposts a dock joins an order its site already stocks, or else the higher priority one; inside one outpost docks spread across orders. `pick_best_order()` sorts the same way without the spread counts or promises. Affinity (`_dock_affinity()`) = still-owed units already stocked at the dock's outpost + 1 per item whose tree `fabricator.site_plan` builds there; tie-break only. Local stock, affinity and readiness all count `SourceCache.held_stock()` (Warehouses, Drone Depots, home Inventory), the same count Fabricator netting uses, so dock and Fabricator agree on "enough"; `pick_best_order()` builds one `SourceCache` for the pass. Scored per idle dock before the sort (a remote outpost's first `held_stock()` reads its Warehouses and Depots), so the sort key only reads a dict.
- **Dock site roles** (`DockRoles`, one per pass): the buildings at a dock's outpost decide which order items it ships itself. Fabricator → crafted items (Fabricator recipe outputs, `ROLE_FAB`); Smelter → every raw ore and Smelter output, resource marker naming the outpost (`outpost_mining.assigned_ores_by_outpost()`) → that ore (`ROLE_MINE`); Lead Cask → `lead_cask.HOT_ITEMS` (`ROLE_CASK`). An item with none of these kinds counts as covered everywhere; an unresolvable site covers everything. A dock takes an order (planner and `pick_best_order()`) only when the order has no role-bound still-owed item or the dock covers at least one; the sort ranks the covered share (`share()`) after the spread count and before priority. The rest of a mixed order reaches the dock's outpost as a site-supply consumer request (§2i-1). Stability exception: an empty dock leaves a held order it covers nothing of; the plan entry is then another order or `None`, and `step()` clears the order (`plan_assigned` only). A loaded dock keeps it.
- **Docks at any outpost**: `discover_supply_dock_ids()` is network-wide. Off home a dock connects to a local Warehouse (`local_port_target()`, none → one warn), loads from local stock only (`SourceCache.local_stock()`, `take_item(outpost=)`, no blueprint reservation) and drains to a local Warehouse. Its order items are consumed at its outpost (§2a-0-6), so their trees build there and §2i-1 hauls in the rest.
- **Weekly-deadline feasibility**: `_weekly_infeasible(order, current_day, dispatch_capacity_per_hour)` skips Weekly Earth Order entirely when `remaining_units > dispatch_capacity_per_hour *
  hours_remaining` (`hours_remaining = (order.expires_day - current_day) * 24`) — i.e. even shipping flat-out with all known docks' combined `dispatch_rate()`, remainder can't leave before `expires_day`. Dispatch-capacity ceiling only (not production-rate forecast — upstream recipe throughput/worker counts/deficits = later TODO). Returns `False` (don't block) when needed input missing. Campaign orders (no `expires_day`) unaffected.
- **Stale entries**: plan can name an order that completed after it was written. `desired_order_id()` checks the entry with `orders.get_order()` (`order_is_active()`); not `"active"` → falls back to `pick_best_order()` instead of calling `set_order()` on it. A `set_order()` result `"completed"`/`"unknown_order"` is logged at debug, not warn.
- **Console**: standby and shipping lines print only when the dock's state changes (`report()`), not every `poll_interval`.
- **Fallback**: `SupplyDockController.desired_order_id()` uses archive plan when this dock's id present, else own weekly-feasibility-aware `pick_best_order()` — soft fallback (unlike Solar/Smelter hard dependency in §1a-1).
- **Hot cargo** (Raw Uranium, Fuel Rods, `lead_cask.HOT_ITEMS`): an order needing one goes only to a dock whose outpost has a Lead Cask (`_servable_at()`, planner and `pick_best_order()`); the dock loads it from that outpost's casks (`lead_cask.take_from_casks()`), affinity counts cask stock, and leftovers eject to a cask (`lead_cask.unload_target()`). Sourceability (`production.can_source_item()`): a hot item in any cask, Raw Uranium with a live uranium site in `weather.aftermaths`, Fuel Rods / Nuclear Batteries via the first Fuel Assembler's unlocked recipes (`SourceCache.fuel_assembler_recipes()`; the recipe index and Fabricator cascades stay Fabricator/Smelter-only). Readiness (`_order_readiness()`) counts hot items from Lead Casks network-wide (`SourceCache.cask_stock()`, fallback `lead_cask.network_cask_stock()`).
- **Shared scoring**: `_score_campaign_order()`/`_score_weekly_order()`/`_order_readiness()` module-level, used by planner + per-instance fallback — no ranking drift. `_order_readiness(order, reserved, stock)` takes `held_stock` of the pass's `SourceCache` (a fresh one when None).
- **Key unlock orders** (`EARLY_UNLOCK_ORDER_IDS`, `key_unlock_bonus()`): unlock path in [docs/gameknowledge/unlock_paths.md](../gameknowledge/unlock_paths.md). A current campaign order that is not itself a key order adds the weight of the nearest key order behind it in its contractor's queue (`orders.list_upcoming_orders()`) divided by 1 + the orders in front of that one, so `spire_intake_1` earns half of `spire_intake_2`'s. Key orders sort right after the local-cask rule, before local stock and the spread count, so idle docks that serve one take it first; an empty dock (stability exception, central plan only) leaves a non-key order for a key order it serves (`_key_order_ids()`). A loaded dock keeps its order.

### 2a-1. Fabricator demand tracking (`lib/production_cascade.py` `get_fabricator_targets()`)

Single source of truth for what Fabricator builds, feeds `get_material_demands()`. Ore demand comes from the site supply ore requests (§2i-1), home included. Five demand sources folded into one `{item_id: quantity}` dict, then cascaded into Fabricator-built inputs (`_cascade_fabricator_output_demand()`). An item whose recipe has an input with no source (none on the network and `can_source_item()` false, e.g. a still-locked Pressure Valve under Pipe Bridges) is not cascaded, so its other inputs are not built to sit stranded. No standing Fabricator stock table: standing stock is requested per site (§2i-1 stockpiles and construction stock) and reaches the Fabricators as upgrade/backlog orders.

1. Active Supply Dock order's `requires`, for items Fabricator can build (`max()`'d vs other sources, not summed), plus the reserve at the Constructor's home (`builder_reserve()`: units held there of each request entry with a `keep`, capped at that keep): a dock order builds its own units instead of counting the construction stock.
2. **Pending/paused Construction Blueprints**, via `_cascade_blueprint_demand()` (§2a-0-1), `max()`'d vs existing target — not summed (targets = steady-state floor, not additive per source).
3. **`fabricator.manual_orders`** archive key (`{item_id: quantity}`, e.g. `{"drone_small": 2}`) — ad-hoc build requests, edited directly (no default seeded). Quantity = units still to build, not a stock floor: folds into target as `network_stock() + quantity` (`max()`'d with other sources; `get_manual_order_blocking_items()` seeds the same way), so units already built never satisfy the rest. ALSO queue priority in `choose_recipe()`: picked ahead of any other demanded recipe regardless of shortfall. Counted down (dropped at 0) by `production.consume_manual_order()`, called from `drain_output()` with qty actually drained. Units drained off home move to archive `fabricator.manual_transit` (`{item: {"units", "base"}}`, base = home stock then): `fabricator_root_targets()` keeps `base + units` as the item's home consumer want (no build target), so §2i-1 hauls them home; `reconcile_manual_transit()` drops the entry once home stock reaches `base + units` or no unit is left off home (`network_stock() - stock()`). Key must exactly match recipe's `output_item` (hand-typed, no write validation) — `get_fabricator_targets()` prints one-time warning (per-script-run, `_WARNED_UNKNOWN_MANUAL_ITEMS`) when key doesn't match default Fabricator's unlocked recipe outputs (heads-up only, can false-positive for other Fabricator or not-yet-unlocked recipe).

4. **`fabricator.upgrade_orders`** archive key — `{requester_id: {item_id: quantity}}`, written only by code (`production.set_upgrade_order()`): the fleet upgrade coordinator (requester `"fleet_upgrade"`, Depot kits/chassis) each drone (its own id, better Cargo Pods/Oil Tanks/missing loadout modules) and the planting Harvester (requester `"field_keeper"`, field-machine kits, §1k) the Bio Caster (requester `"bio_caster"`, forge materials for all open Volcanic orders, §1g) and the COMMISSION coordinator (requester `"fleet_commission"`, the kit of the drone job being crafted, §2k-2) and the Plant Terraformers (requester `"plant_terraformer"`, next `NEED_CYCLES` batches of Fertilizer/Growth Accelerant, §1k) and the Fuel Assemblers (requester `"fuel_assembler"`, Lead Plates for the next crafts, §1n) and the planting Harvester's Yield Amplifier (requester `"field_amplifier"`, §1k) and the crafted site stockpiles' need levels (requester `"site_stock_need"`, §2i-1) and the construction stock's need levels (requester `"construction_stock_need"`, §2i-1). Summed across requesters by `get_upgrade_orders()`, `max()`'d into the target. Each requester replaces/clears only its own entry; entries of drones that no longer exist are pruned by `FleetUpgradeCoordinator._prune()`; non-drone requesters must be listed in `production.STANDING_ORDER_REQUESTERS = ("field_keeper", "bio_caster", "fleet_commission", "plant_terraformer", "fuel_assembler", "field_amplifier", "site_stock_need", "construction_stock_need")` or they get pruned too. See §2k.
5. **`fabricator.backlog_orders`** archive key — same `{requester_id: {item_id: quantity}}` shape, written only by code (`production.set_backlog_order()`, summed by `get_backlog_orders()`, `max()`'d into the target): filler work: the Plant Terraformers' 24 h Fertilizer/Accelerant buffer (§1k), the site stockpiles (`"site_stock"`) and the construction stock (`"construction_stock"`, §2i-1). No pruning; each requester clears its own entry. Site orders (`production.SITE_ORDER_REQUESTERS = ("site_stock", "site_stock_need", "construction_stock", "construction_stock_need")`) raise the Fabricator target only; their sites request the items, so home is no consumer.

`choose_recipe()` priority has **six tiers** (biggest shortfall first within each): (0) manual-order-blocking intermediate, (1) manual order, (2) **Construction Blueprint demand** (`production.blueprint_demand_items()` = `{item: gross demand}` for every item `_cascade_blueprint_demand()` reaches — building new things beats upgrading working old ones; only while held stock + pipeline is below that demand, ranked by that blueprint shortfall, so the rest of a bigger target such as construction stock falls to its own tier), (3) **fleet upgrade order** or an input it is blocked on (`get_manual_order_blocking_items(outputs, get_upgrade_orders())`), (4) everything else (Earth/Supply Dock orders, intermediates), (5) **backlog order** whose upgrade order is met and no Supply Dock order needs it (`FabricatorController.backlog_only()`), so only idle Fabricator time goes to it. **Sticky recipe**: the current recipe stays while it is still short, sourceable and claimable and no sourceable candidate of a better tier exists; a bigger shortfall in the same tier doesn't switch (a switch ejects the staged inputs, `eject_excess_inputs()`, and reloads: two feeder trips per unit). A backlog item whose upgrade order is still short ranks tier 3; its intermediates rank as usual (tier 4). Tier 0 detail: `production.get_manual_order_blocking_items()` outranks even manual orders. = set of Fabricator-output items a manual order transitively needs as INPUT (e.g. `machine_frame` under manual `drone_service_station_kit` order) currently short of stock — found via same shortfall-only BFS as `_cascade_fabricator_output_demand()` (§2a-0-1), seeded from manual orders only. Needed because `can_source_item()` only checks that some recipe path exists for an intermediate, not that anything is producing it.

### 2a-1b. Sourceability caching across a pass (`lib/production_source.py` `SourceCache`)

`can_source_item()`, `can_source_fluid()`, `can_fulfill_order()` (§2a-0-5) each walk real game-API calls (Smelter/Fabricator discovery + `list_recipes()`, `outpost.buildings()`,
`journal.surveyed_sites()`, per-Warehouse `count()`), not free local compute.

`SourceCache` (instantiate once per pass, thread through every call) memoizes:
- `smelter_recipes()`/`fabricator_recipes()`/`surveyed_sites()` — each game call fires at most once per cache instance.
- `can_source_item()`/`can_source_fluid()` results per item/fluid-key — shared sub-item (e.g. Steel under both Circuit Panel and Iron Ingot) resolves once, not per branch. Separate `_item_stack` set does cycle detection so memo never poisoned with in-progress answer.
- Stock snapshot: `scan(outpost)` = one `stock_scan.scan()` per outpost per pass (`.stacks()` once per Inventory/Warehouse/Bin/Depot stockpile, `STOCKS_CHUNK` stores per atomic call, plus the home Crop Automators' Forage via `storage.crop_automator_forage()`), kept in `_scans`; every stock method is a scope over that scan, so Forage-fed recipes (Reinforced Biopolymer, Enrichment Compound) stay sourceable while the field keeps its Forage; `building_stock()` = holders among Inventory/Warehouses/Bins. Total cost `1+W` calls per pass regardless of distinct items — strictly better than `.count()`-per-item `total_stock()` (`D*(1+W)`).

- **Stock scopes** (`lib/stock_scan.py`: store kinds `INVENTORY`, `WAREHOUSE`, `BIN`, `DEPOT`, `AUTOMATOR`; scopes `LOCAL` = Inventory (home) + Warehouses + Bins + Automator Forage, `HELD` = `LOCAL` + Depots, `DEPOTS`, `STORES` = Warehouses + Bins): `stock(item)` = `LOCAL` at home; `local_stock(item, outpost)` = `LOCAL` there, what a machine port can `take()`; `depot_stock(item, outpost)` = `DEPOTS`; `held_stock(item, outpost)` = `HELD`; `network_stock(item)` = `held_stock()` at every outpost + cargo aboard haulers. `logistics_requests.outpost_stock()` and `PlanReads.stock()` = `HELD`, from the same scan. `stock_scan.held_units(item, outpost)` = a one-off `HELD` read (seed sweep, battery need, home salt). `tests/test_stock_scope.py` pins every counter's number against one world. Rule: **netting counts `held_stock()`** (Fabricator targets, `_stock_fn()` cascades, Supply Dock readiness/local supply/affinity, `can_source_item()`, fleet intent, manual transit); **loaders count `local_stock()`** (`load_inputs()`, dock loading): a Depot pushes its freight to local consumers and stores (vehicles_drones.md §2h), machines never pull from it. Ground haulers are the exception: they `take()` Depot stock above `depot_holds()` (§2i free stock).
- `_cascade_blueprint_demand()` result (blueprint + fleet-cargo walk) on `cache._blueprint_demand`; callers get a copy.

All three call sites default `cache=None` (private one-off `SourceCache()`), but hot paths build + share one: `plan_dock_assignments()` one per pass; `FabricatorController.step()` one per step.

**Recipe input table** (across passes, per script): `production._recipe_index()` builds `{output_item: {input_item: qty per output unit}}` from the Fabricator + Smelter recipe lists (first recipe per output wins, Fabricator first) and keeps it `RECIPE_INDEX_TTL_TICKS = 6000`, rebuilt early when a list's length changes (a research unlock); also memoized on `SourceCache._recipe_index` for the pass. `_recipe_inputs_for()` is a dict lookup on it (shared, read-only). Replaced a scan of every recipe per item per call (~40% of a Smelter step).

**Building discovery memo** (across passes, not on `SourceCache`): `production._discover_building_ids()` (Smelter/Fabricator/Supply Dock discovery) and `storage.discover_storage_buildings()` reuse their result for `DISCOVERY_TTL_TICKS = 20` ticks (~2 s) per `(type, outpost)`, so a new building is seen at most that late. A Smelter step alone runs about a dozen discoveries; `total_stock()` runs one per call. Cache = one-pass snapshot only — never held across ticks or reused between passes.

### 2a-1c. Recipe switch with a paused unit (Smelter + Fabricator)

`is_running()` reads `False` while an unfinished unit waits (e.g. output full), but `get_progress()` stays > 0. The game then refuses `set_recipe(<other recipe>)` and `clear_recipe()` with `busy`; re-setting the same recipe keeps the progress. Progress is never lost, so the controllers call `set_recipe()` on `not is_running()` and retry next poll on `busy`.

### 2a-2. Fabricator input-stockpile ejection (`lib/fabricator.py` `eject_excess_inputs()`)

`set_recipe()`/`clear_recipe()` both leave input stockpile untouched — only built-in clear is `InputSlot.flush()`, which **permanently discards** material. `eject_excess_inputs()` runs every `step()`, before recipe selection, recovers stranded/excess staged material via `InputSlot.eject(destination, item_id, count)` (routes to least-full Warehouse with room via `storage.best_unload_target()`, or Inventory — never `flush()`) in two cases (both off currently-set recipe via `production.get_fabricator_active_recipe()`):

1. Staged material active recipe doesn't need (leftover from prior recipe, or no recipe) — eject all.
2. Staged material active recipe DOES need, beyond `required_per_craft * crafts_remaining` (same cap `load_inputs()` loads to) — eject excess only.

`eject()` transactional, safely no-ops on portion reserved for in-progress craft, so unconditional every-step call harmless.

### 2a-3. Fabricator fluid-input connections (`lib/fabricator.py` `ensure_fluid_connections()`)

Recipe's `fluid_inputs` (e.g. `{"water_in": 1.0}`) delivered via `FluidPort` connection, not Inventory/Warehouse take. `ensure_fluid_connections(recipe)` runs every `step()`, one `fluid_routing.FluidInputRouter` per fluid port (§1b **Input vs output routers**):

- Per `fluid_key` active recipe declares, `production.FLUID_SOURCE_TYPE_IDS[fluid_key]` names every building type that can feed it (e.g. `water_in` accepts `water_pump`,
  `steam_condenser`, `liquid_tank`, `bulk_liquid_reservoir`) — same mapping `can_source_fluid()` uses. Discovery is `production.discover_fluid_sources()` (§1b **Candidate helpers**).
- **Generic Liquid/Gas Tank existing ≠ proof it can supply given fluid** — buffers latch onto whichever fluid piped in *first*, hold only that until drained to `0`.
  `production.BUFFER_FLUID_TYPE_IDS` + `fluid_building_is_viable(fluid_key, type_id, building)` gate both `can_source_fluid()` and this discovery loop identically: dedicated producer always counts (fixed one fluid); buffer counts only once own `.fluid()` latched to needed fluid (`production.FLUID_LATCH_IDS`). Resolves bare `BuildingRef` to live component via `get_component(ref.id)` first when passed object has no `.fluid()`.
- **No `is_stalled()` on Fabricator itself** — reachability inferred from port's own `flow_rate()` staying `0` for `FLUID_STALL_STREAK_BLACKLIST_THRESHOLD=5` *consecutive* ticks while room to receive (`level() < capacity()`, `fluid_routing.port_starved()`, shared by every input router on a machine without `is_stalled()`) — legitimately full port also reads `flow_rate()==0`, must NOT count as stall. Same per-entry blacklist expiry as other connect/blacklist controllers (`FLUID_RESCAN_INTERVAL_TICKS=150`); `FLUID_DISCOVERY_CACHE_INTERVAL_TICKS=100`, `FLUID_NEUTRAL_GRACE_STEPS=5`. Candidates ranked own-outpost-first.
- One router per `fluid_key` (`_fluid_routers`, created lazily) — recipe can need multiple fluids at once (oil-refining needs `oil_in` + `water_in`), independent sources.
- **Fluid-only recipe** (`is_fluid_only()`: fluid inputs, no item inputs, e.g. `craft_tar`) never goes idle while fluid flows. Once its `crafts_remaining` is 0, `step()` skips `ensure_fluid_connections()`, `stop_fluid_feed()` disconnects its fluid ports, and the recipe switch/clear runs even while `is_running()` (`busy` → debug, retry next poll). The router reconnects when a recipe needing that fluid is active again. It also pauses while its fluid's tanks are low: `fluid_low_reason()` reads `fluid_routing.fluid_reserve_fraction(fluid, curr_tick=now)` every `FLUID_ONLY_RESERVE_REFRESH_TICKS = 100` into a latch that pauses below `FLUID_ONLY_PAUSE_BELOW = 0.05` and resumes at `FLUID_ONLY_RESUME_AT = 0.20` (no tank of that fluid: never paused). A paused recipe is cut like a met one and skipped by `choose_recipe()` (debug line; the flip logs once at info). Why: the pause keeps a reserve for the consumers that never pause (Oil Generators on last resort, recipes with fluid plus items); throughput is set by the supply either way ([gameknowledge/fluids.md](../gameknowledge/fluids.md), "What to do in game").

### 2c. Storage Management (`lib/storage.py`)

Makes whole production chain aware of storage buildings, not just central home `"inventory"` endpoint. Scope (`STORAGE_TYPE_IDS`, Warehouses first): Warehouse (5 material-locked slots × 2,000), Large Warehouse (15 × 2,000), Storage Bin (1 × 500). `discover_storage_buildings()` wraps each bin in `BinStore`, a Warehouse-shaped view (one slot; `space_for(item)` = `space()` while empty or latched to that item, else 0; `materials()`, `slots()`, `capacity()`, `total()` derived), so every caller (unloading, `take_item()`, stock reads, sweeps, drone buffers) handles bins like Warehouses. An early outpost with only bins therefore unloads into them. Everything defaults to home outpost, matching Inventory only participating at Nocturna Base.

- `total_stock(item_id, outpost=None)` = Warehouses' and Bins' `count(item_id)` at `outpost`, plus `inventory.count(item_id)` at home only; no Drone Depots. A one-off loader/count read; netting counts `stock_scan` `HELD` (`SourceCache.held_stock()` §2a-1b, `logistics_requests.outpost_stock()` §2i). `inventory_count(item_id)` = home Inventory alone (0 if unreadable), for kit/part checks (fleet commission/upgrade, tank/warehouse swaps, wildlife MK2 packs).
- `outpost_is_home(outpost=None)`: `None` counts as home (every helper's default); reads `OutpostRef.is_home` (bool) or the Outpost component's `is_home()`. `local_port_target(outpost=None)`: resting port endpoint for a machine there (`"inventory"` at home, first local Warehouse id elsewhere, `None` if none).
- `best_unload_target(item_id, min_amount=1)`: among Warehouses and Storage Bins at `outpost` with `space_for(item_id) >= min_amount`, ranks by contents (`materials()`), never by recent `"busy"` answers. Sort key `(opens empty bin, clash, not holder, ...)`; among holders (Warehouse or latched Storage Bin) the one holding the most of the item wins (one `count()` per holder), so deliveries grow the main stack and never feed a stray; among new stacks `(neighbour heat, fill_percent())`. `take_item()` drains the emptiest bin, so two bins of one item converge into one. Opening an empty Storage Bin ranks after every Warehouse with room, even a clashing one: bins mean slots are tight, so a feeder wait beats locking a bin to one item (a bin already latched to the item ranks like a Warehouse holder). Then: a Warehouse without a **recipe partner** of the item that already holds it, then one without a partner (new stack), then the lowest clash (`item_heat(item) × item_heat(partner)`), holder first. An item stuck next to its partner therefore splits off once into a partner-free Warehouse, and every later delivery goes to that new stack; one Warehouse, or no partner-free one with room, gives plain consolidation. Neighbour heat (sum of `item_heat()` of the other contents) only counts for an item with heat > 0. `holders_only=True` skips every store not holding the item (no new stack, no Inventory). If nothing qualifies: `"inventory"` at home, `None` elsewhere (cargo stays aboard / staged).
  - **Partners** (`SMELT_PARTNERS`, `recipe_partners()`): each ore and its Smelter product (`iron_ore`/`iron_ingot`, `silicon`/`glass`, `titanium`/`titanium_ingot`, `cobalt`/`cobalt_ingot`, `lead_ore`/`lead_ingot`, `rare_earth`/`rare_earth_core`, `neutronium`/`neutronium_bar`). A Smelter takes the ore and sends the product at the same time, and a Warehouse handles one material operation at a time.
  - **Heat** (`ORE_HEAT_ORDER`, `item_heat()`): assumed transfer volume, hottest first: `iron_ore` 7, `silicon` 6, `titanium` 5, `cobalt` 4, `lead_ore` 3, `rare_earth` 2, `neutronium` 1; a product has its ore's heat, anything else 0. At home, a `must_stay_in_inventory()` item goes to `"inventory"` first while it has `space_for()` room and no active Supply Dock order there owes it (`_inventory_first()`), so hauled-in kits/modules skip the reclaim sweep. `vehicle_cargo.py`'s `unload_cargo()` picks destination **per stack**.
- **Top-up** (`top_up_target()`, `top_up_bin()`): when no holder (bin or Warehouse) has room for a whole stack, the fullest Storage Bin latched to the item takes what fits first; only the rest goes to `best_unload_target()` (possibly a new bin). Used by `drain_port_to_storage()` (not with `allow_partial`) and `vehicle_cargo.unload_cargo()`.
- `drain_port_to_storage()` sends each staged stack to `best_unload_target()`; a Warehouse answering `"busy"` (material endpoint lock, e.g. the one a blend was just taken from) is passed to `best_unload_target(exclude=, holders_only=True)` so the next-best holder of the item is tried, up to `BUSY_TARGET_RETRIES = 3` extra targets (the busy one is also `mark_busy()`'d). A retry never opens a new stack (Warehouse slot or empty Storage Bin); the stack waits for a busy holder instead. The Inventory rebalance direct move follows the same rule after a `"busy"` answer. All busy: the stack stays staged and callers' Inventory fallbacks apply.
- `take_item(port, item_id, amount, outpost=None, cache=None, report=None)`: single function behind every `machine.input.take(item_id, amount)` call site. Tries **only endpoints holding item** (`_holder_candidates()`): Inventory first (home only — no own Auto Feeder, never locks), then Storage Bins by least stock (empty bin unlatches its material), then Warehouses by most stock; any endpoint answering `"busy"` within `TAKE_BUSY_COOLDOWN_TICKS = 20` (~2 s) moved last (still tried as last resort). No API to ask "is Warehouse busy?" upfront — `"busy"` rejection returns immediately (no feeder wait), so it is the probe; remembered per script in module-level `_recent_busy`. With `SourceCache`, holders come from its one-shot `building_stock(item_id)` snapshot (home only); else one `.count()` per building. `report` gets `{"sources": [(id, status, moved), ...]}`.
  Feeder time per transfer (simworker `hb()`/`mb()`): `max(1, round(units / speed × 0.01 h × 600 s/24 h × 10 ticks/s × fast))` ticks = **2.5 ticks/unit**, no fixed part beyond the 1-tick floor. `speed` = the faster endpoint's factor: Drone Depot 1/2/4 (S/M/L, ×2 with `depot_handling_unlock`), Plant Terraformer and Feed Maker by tier, every other store 1. `fast` = 0.5 after `research_fast_feeders` (400k TP), else 1. Locks every participating building for the duration.
- **Multi-Smelter Coordination** (`SmelterController`) — `production.discover_smelter_ids()` finds Smelters at runtime. Inventory-manager sweep runs centrally from orchestrator_automation.py's AUTOMATION section (§1a-1). Each smelter's `select_needed_ore()` claims its recipe (`claim_recipe()`/`release_recipe()`, `archive.transaction("smelter.recipe_claims",
  ...)`, per outpost like `fabricator.recipe_claims`, `RECIPE_CLAIM_STALE_TICKS = 600`; both machines share `lib/recipe_claims.py` `RecipeClaimMixin`) before crafting, so two smelters don't start same recipe while other demanded ore sits untouched. A claim this machine won is re-written only every `CLAIM_REFRESH_TICKS = 100` (Smelter and Fabricator, per instance `_claim_ticks`); in between `claim_recipe()` answers from memory. Losing the claim or `release_recipe()` clears the memory; a clock reading 0 always takes the full path.
  - **Pile-on fallback**: if only ONE ore demanded, `select_needed_ore()` collects every
    sourceable/demanded candidate, tries to claim each, and if none can be claimed exclusively,
    joins the first anyway rather than idling. Joined smelters split intake via the demand-share
    and fair-share caps (§2a-0-2) and self-throttle together as `get_smelter_demands()` nets down.
- **"Inventory manager" sweep** — `rebalance_inventory_to_warehouses()`, called once per `STORAGE_TICK_INTERVAL` cycle from orchestrator_automation.py's AUTOMATION section, home outpost only (Inventory exists only there): any **propertyless** Inventory item moved to Warehouse **entirely** when it spans more than `INVENTORY_REBALANCE_SLOT_THRESHOLD = 2` slots, or already split (some in Inventory, some in Warehouse — `_warehouse_item_ids()`). Skipped while home has no store (no non-retiring Warehouse or Storage Bin), so a home without Warehouses logs no "Could not clear" warnings.
- **Inventory free-slot reserve** — `storage.INVENTORY_FREE_SLOTS_KEEP = 4` empty Inventory slots stay free for Shop buys, `undeploy()` and module swaps. `inventory_room(item_id)` = `space_for()` minus the held-back empty slots × stack size (partial-stack room stays usable). Applied by: `best_unload_target()` (Inventory-first and home fallback need room ≥ `min_amount`, else None), `_send_to_best_target()`/`drain_port_storage_first()` (cap sent units), `drain_port_inventory_first()` (rest goes to a Warehouse, else stays staged), vehicle `unload_cargo()` (partial unload, rest stays aboard), Supply Dock cargo drain, `reclaim_inventory_only_items_from_warehouses()`. Not applied: rebalance swap eviction (net slot gain), deliberate pulls for immediate use (field keeper, wildlife planner, crop/field ejects).
  - **Exception**: `item_catalog.lookup(item_id).category` of `"equipment"`, `"module"`,
    `"portable"`, or `"upgrade_pack"` (`NON_WAREHOUSABLE_CATEGORIES`, `must_stay_in_inventory()`)
    are never swept — equipment and building upgrade packs apply from Inventory only;
    modules/portables must be in Inventory to equip a vehicle. `"construction_kit"` is NOT in this set (placed via blueprint construction, fine to
    warehouse).
  - **Direct move**: `inventory.transfer_to(best_unload_target(item_id, 1, exclude=tried))` with
    everything left, then the next-best pick for what didn't fit or answered `"busy"`, so the
    item joins its existing holder instead of opening stacks in several Warehouses.
  - **Swap fallback**: if no Warehouse has any room, evicts whichever Warehouse occupant is
    cheapest to bring back (smallest quantity) — only when `slots_freed > slots_reclaimed`
    (`slots_reclaimed = ceil(evicted_qty / inventory_stack_size())`), a genuine net reduction.
    `slots_freed` is computed from `remaining` (units still stuck *at swap-fallback time*, after
    any direct-move already ran). In practice a swap is only a net win
    for a small-quantity occupant (roughly `slots_freed * stack_size` units or fewer); a
    persistently-fragmented item logs `[storage] Skipping swap for <item>: ...` /
    `[storage] Could not clear...` / `[storage] Swap for <item> did not go through...` /
    `[storage] Freed a slot... but it still reports no room...` instead of silently continuing.
- **Bin consolidation** (`consolidate_storage_bins()`, once per storage pass from `orchestrator_automation.py`, every outpost): the smallest Storage Bin of an item held by 2+ bins at one outpost, at most `BIN_CONSOLIDATE_MAX_UNITS = 200`, moves into the fullest other bin of that item with room for the whole stack, `BIN_CONSOLIDATE_CHUNK = 20` units per call (`transfer_to()` blocks the calling script ~2.5 ticks per unit), one transfer per call over all outposts. Recently `"busy"` bins are skipped. The emptied bin unlatches.
- **Storage snapshot** (`storage.StorageSnapshot`, one per storage pass in `orchestrator_automation.py`): one `slots()` read per store per outpost (atomic, `STOCKS_CHUNK` stores per call), shared by the rebalance, reclaim, bin and stray sweeps. A sweep that moves units calls `touched(ids)`; those stores are read again on the next access. Other changes during the pass are accepted as stale (`transfer_to()` reports `"partial"`). `slot_layout(outpost, snapshot=None)` reads through one too.
- **Warehouse strays** (`consolidate_warehouse_strays()`, once per storage pass after bin consolidation, every outpost): a `"busy"` retry, partial drain or full slot can leave a small second stack of an item in another Warehouse. The smallest Warehouse holder of an item held by 2+ stores, at most `WAREHOUSE_STRAY_MAX_UNITS = 200`, moves `WAREHOUSE_STRAY_CHUNK = 20` units per call into `best_unload_target(item, count, exclude=[source], holders_only=True)` (biggest other holder with room for the whole stray). Runs only while the stray's Warehouse has no empty slot, the item has `WAREHOUSE_STRAY_MANY_HOLDERS = 3` or more holders, or the stray shares its Warehouse with a recipe partner (`recipe_partners()`); otherwise a second holder costs nothing and gives `take_item()` a fallback while one answers `"busy"`. Recently `"busy"` and retiring stores are skipped; one transfer per call.
- `inventory_stack_size()`: `10`, or `20` once `research.is_unlocked("research_high_density_storage")` ("Bigger Stacks").
- **Reverse sweep** — `reclaim_inventory_only_items_from_warehouses()`, called right after "inventory manager" sweep from `orchestrator_automation.py`'s AUTOMATION section: any Warehouse stock whose `item_catalog` category in `NON_WAREHOUSABLE_CATEGORIES` (`must_stay_in_inventory()`) moved back to Inventory regardless of slot pressure — safety net for gear landing in Warehouse other ways (manual stash), since nothing here ever *places* such item in Warehouse on purpose.
  Each slot moves with `property_match="exact"` so durability-bearing variant not merged with different variant of same `item_id`.
  - **Dock-demand exception** (`_items_demanded_by_active_dock_orders()`): an item still owed by any
    Supply Dock's active order is left in the Warehouse instead — `supply_dock.py` already ships
    straight from a Warehouse via `take_item()`/`total_stock()`, and a bulk Earth Order contract for
    a "deployable" equipment item can run hundreds of units deep, far more than Inventory has slots
    for. Self-contained (own `outpost.buildings("supply_dock")` scan) rather than importing
    `production.py`, which itself imports from this module.

### 2d. Outpost Ore-Assignment & Stock-Target Scaffolding (`lib/outpost_mining.py`)

Answers "which ores should vehicle stationed at outpost X mine?" and "how much before stopping?" — consumed by stationed-mining role (§2e). "Which ores" answered **live from Planet Map**, not archive list — every surveyed mineral site gets `"resource.poi_X_Y"` marker whose `.note` names responsible outpost.

- **Marker convention**: `RESOURCE_MARKER_PREFIX = "resource."`, id `resource.poi_{x:.0f}_{y:.0f}`, `icon="resource"`, `color="neutral"`, `label="{Item Name} - {Purity}"` (`_item_display_name()`/
  `RESOURCE_PURITY_LABELS` build it, `_item_id_from_label()` exact inverse). `.note` = responsible outpost id, or `""` when unassigned.
- **`sync_resource_marker(site, outpost_id=None)`** — places/updates one site's marker. `outpost_id=None` keeps current assignment (style-only refresh); pass explicit id (incl. `""`) to change.
- **Owner rule**: only outposts whose `autoplay.outpost_roles` entry holds `MINING_ROLE = "mining"` (`mining_outpost_ids()`) are picked automatically, the closest within `range_m` (default `resource_assignment_range_m()`, archive key `RESOURCE_ASSIGNMENT_RANGE_KEY = "outposts.resource_assignment_range_m"`, default `200.0`m). No mining outpost in range: site stays unassigned (no closest-outpost fallback). Operator assigns any other outpost by editing marker note. Never reassigns assigned site.
- **`auto_assign_new_site(site, range_m=None, owners=None)`** — call once per freshly-surveyed mineral site (`vehicle_survey.py`'s `scan_and_survey()` does automatically). Places/refreshes marker; assigns by owner rule only if unassigned.
- **`assign_unassigned_sites(range_m=None)`** — hands every unassigned marker to closest mining outpost in range. `orchestrator_automation.py` runs it every storage pass, so a new designation or new outpost picks up its sites.
- **`sync_mineral_site_markers()`** — `auto_assign_new_site()` for every surveyed mineral site. Markers need Cartography (140k TP): `orchestrator_automation.py` runs this once per run as soon as `markers` exists (backfill of pre-Cartography surveys).
- **`assigned_ores_for(outpost_id)` → `[item_id, ...]`** — read path, called every cycle by stationed-mining candidate builder (§2e).
- **`harvesting/sync_resource_markers.py`** — manual: forces backfill + sweep now.
- **`ore_stock_target(item_id)` → units** — one global `{ore: units}` dict under `mining.ore_stock_targets` (`ORE_STOCK_TARGETS_KEY`), same number at every outpost: mining-outpost stockpile, home floor, smelting-site ore buffer. Default `storage.default_stock_target()`: `BIN_STOCK_TARGET = 400` (80% of a 500-unit Storage Bin) until `research_warehouse` (`WAREHOUSE_TECH_ID`) is unlocked, returned without seeding; after the unlock `WAREHOUSE_STOCK_TARGET = 1800` (90% of a 2000-unit Warehouse slot), seeded into the archive on the first lookup of an ore, then editable. Both stay below one slot so a small overshoot (late Smelter batch, full Pioneer load) fits the slot already holding the item instead of opening a second one. Archive values seeded earlier keep their number. The old per-outpost `outposts.ore_stock_targets` is purged by `ArchiveCleaner.clean_retired_keys()`.
- **`RAW_ORE_ITEM_IDS`** — 7 mineable ore item ids (`iron_ore`, `silicon`, `titanium`, `cobalt`, `rare_earth`, `neutronium`, `lead_ore`); **`HOME_OUTPOST_ID = "outpost_home"`**.

### 2k-1. Warehouse → Large Warehouse Upgrade (`lib/warehouse_upgrade.py`, headless `builder_automation.py`)

The state machine shared with §2k-3 (gate, buy, deploy/adopt, status line, refusal counting, `TRANSIENT_UNDEPLOY_STATUSES`, kit selling) lives in `lib/building_swap_upgrade.py` `BuildingSwapUpgrader`; each subclass supplies its type ids/labels, `_start_next()` (group selection) and `_drain()`.

Same gate as §2k (FLEET card Drones-tab switch `fleet.upgrade["enabled"]` + mining-drill phase), plus `research_high_bay_warehousing` unlocked and the cash manager's grant for the Large Warehouse price (Shop catalogue, fallback `LARGE_PRICE_FALLBACK = 60000`; consumer `warehouse_upgrade`, planned = every remaining pair, §2l). **One swap at a time network-wide**, `SWAP_RATIO = 2`: two Warehouses at one outpost → one Large Warehouse (10 slots/20k → 15 slots/30k; fewer buildings for Auto Feeder consumers to walk). Outpost with the most plain Warehouses first; there, the two emptiest (`total()`). A lone leftover Warehouse stays. State in `fleet.upgrade["warehouse_swap"]` (status line `fleet.upgrade["warehouse_status"]`), restart-safe.

- `buying` (`shop.buy("large_warehouse")`, skipped if one is in Inventory; snapshot of the outpost's Large Warehouses) → `deploying` (`computer.deploy("large_warehouse", outpost)` or adopt a new one not in the snapshot; going over the outpost building count is accepted, it's brief) → `draining` → done. States run **back to back in one pass** (no sleep between buy, deploy and drain start): a freshly deployed empty Large Warehouse is the least-full store, so other unloaders and `orchestrator_automation.py`'s Inventory rebalance fill it within seconds. Refused deploy (`FATAL_DEPLOY_STATUSES`: `deploy_limit` etc.) or undeploy refused `MAX_ATTEMPTS = 5`× in a row → `blocked`; operator deletes `warehouse_swap` to retry. `TRANSIENT_UNDEPLOY_STATUSES = ("inventory_full",)` (no Inventory room for the returned kit) never count as attempts: the swap waits, and a swap blocked by one of them resumes by itself. Switch off only cancels a `buying` swap with nothing bought yet and no building deployed (not a re-buy).
- **Drain in passes, retiring stores**: each old Warehouse is emptied with back-to-back `transfer_to(new, item, ≤ DRAIN_CHUNK_UNITS = 200, properties=exact)` calls for at most `DRAIN_PASS_TICKS = 600` ticks per pass (checked between calls, so a pass can run one chunk over); then the step returns `draining, N unit(s) left` and the next pass carries on. An emptied Warehouse is undeployed immediately and its kit sold (`shop.sell("warehouse", n)`; only the kits this swap got back, counted in `to_sell`). While the swap is `deploying`/`draining` (`building_swap_upgrade.RETIRING_STATES`) or re-buying (`buying` with `new_id` set), its old stores not yet removed are in `storage.retiring` (`RETIRES_STORES = True` on the Warehouse and bin upgraders; any other state, a block included, releases them): `best_unload_target()`, `top_up_target()`, `local_port_target()`, the Inventory sweep and bin consolidation skip them; `take_item()` and stock reads still use them. Each script reads the set through a `DISCOVERY_TTL_TICKS` cache, so one late delivery can still land; stock that slips in is drained on the next pass (`undeploy()` answers `cargo_present`). Target = new Large Warehouse, else any non-retiring Warehouse/Large Warehouse at the outpost with `space_for > 0`. `"busy"` → retry after `BUSY_RETRY_S = 0.2` s, at most `MAX_BUSY_RETRIES = 50` in a row per chunk; `DRAIN_MAX_IDLE_PASSES = 5` passes with nothing moved → give the step back (`stuck with N unit(s)`).
- **Why its own Automation**: feeder ~2.5 ticks/unit (§2c) → a full pair takes tens of game minutes to drain, split into `DRAIN_PASS_TICKS` passes so the Automation's other steps keep running; Warehouses have no script slot. `builder_automation.py` idles `IDLE_SLEEP_S = 3` s between passes. Status line printed (info) whenever it changes beyond its numbers; per-chunk moves, target fallbacks and undeploy answers at `debug()`.
- **Storage Bins → Warehouse (`BinUpgrader`, same module, interim)** until the autoplay builder upgrades bins by slot demand (TODO.md). Same state machine and greedy drain; same FLEET switch but no mining-drill wait (`WAIT_FOR_DRILLS = False`): starts on the Warehouse unlock. Storage Bins → one Warehouse, planned by slot: per material, the emptiest latched bins are packed into Warehouse slots of at most `SLOT_UNITS = 2000` units each (any number of bins: 8 quarter-full bins → 1 slot), biggest slots first, at most `WAREHOUSE_SLOTS = 5` slots, plus every empty bin. Any bin starts a swap, so every bin goes; bins past 5 slots wait for the next swap. Warehouses bought per outpost ≤ ceil(bins / 4). Needs `research_warehouse` (`storage.WAREHOUSE_TECH_ID`); price from the Shop catalogue, fallback `LARGE_PRICE_FALLBACK = 3000`; consumer `bin_upgrade` (§2l). Outpost whose plan retires the most bins first. Drain targets follow `storage.best_unload_target()` with the retiring bins excluded (existing stack of the item first, so a material's bins merge into one slot; never opens an empty bin); fallback = new Warehouse, then other Warehouses/Large Warehouses. Each drain pass calls `storage.forget_storage_discovery()` so the routing sees the new Warehouse at once. **Re-buy**: other deliveries can take the new Warehouse's slots mid-drain; `STUCK_PASSES_BEFORE_REBUY = 3` drain steps in a row that end stuck with no store at the outpost having room (counter `stuck` in the swap dict, reset by any move) send the swap back to `buying` (`BuildingSwapUpgrader._rebuy()`, cash-gated by `_can_buy()`, old bins stay retiring); the new Warehouse becomes the drain target, the previous one stays as a fallback. The Large Warehouse swap never re-buys (`STUCK_PASSES_BEFORE_REBUY = 0`). State in `fleet.upgrade["bin_swap"]` (status `fleet.upgrade["bin_status"]`). Runs first in the Automation loop, before the Warehouse pair step.

### 2k-3. Liquid Tank → Large Liquid Tank Upgrade (`lib/tank_upgrade.py`, same headless `builder_automation.py`)

Same gate as §2k-1, plus `research_reservoir_engineering` unlocked and the cash manager's grant for the Large Liquid Tank price (Shop catalogue, fallback `LARGE_PRICE_FALLBACK = 15000`; consumer `tank_upgrade`, §2l). Kit and building type id `bulk_liquid_reservoir` (not `large_liquid_tank`). **One swap at a time network-wide**, `SWAP_RATIO = 5`: up to 5 Liquid Tanks of one liquid at one outpost → one Large Liquid Tank (100 t each → 1,000 t). Leftovers are swapped too (7 tanks → 2). A tank's liquid = its latch, else its `tank_assignments` entry; a tank with neither is skipped, and so is an exotic one (`wildlife_data.EXOTIC_FLUIDS`) once Wildlife is complete (`wildlife_common.wildlife_complete()`; the Wildlife planner undeploys those, [wildlife.md](wildlife.md)). Biggest (outpost, liquid) group first; there, the emptiest tanks. State in `fleet.upgrade["tank_swap"]` (status line `fleet.upgrade["tank_status"]`), restart-safe. Runs after the Warehouse step in the same loop; a Warehouse drain delays it.

- `buying` → `deploying` exactly as §2k-1 (snapshot, adopt, same blocking deploy statuses), back to back in one pass → `draining`.
- **Draining, non-blocking** (one check per pass): every pass re-asserts `fluid_routing.tank_assignments` — new tank → the liquid (replaces any blank `""` from `warn_about_unassigned_tanks()`), each old tank not yet removed → `RETIRING_ASSIGNMENT = "retiring"`. `tank_is_eligible_target()` rejects a retiring tank before its latch check, so producers' `FluidOutputRouter`s move to the new tank; consumers still pull from the old ones until they run dry. The new tank's `liquid_in` is connected to the first old tank; once `is_empty()` the port is disconnected, the old tank undeployed, its entry dropped and its `liquid_tank` kit sold (only kits this swap got back, `to_sell`); then the next old tank.
- Undeploy only once empty: undeploy drops the liquid a tank holds (fluid never blocks it, simworker `CD()` checks item bins only). A stopped drain (new tank full, or a producer that can't reach the new tank still feeding the old one) waits; the status line shows the level and `" (new tank full)"` / `" (still fed N t/h)"`. `cargo_present` = liquid slipped in, drain again; `TRANSIENT_UNDEPLOY_STATUSES` wait. Other undeploy refusals, `connect()` refusals or a broken link state (`BROKEN_CONNECTION_STATES`) `MAX_ATTEMPTS = 5`× in a row → `blocked`; operator deletes `tank_swap` to retry.

### 2i. Pull Logistics + Reverse Hauler (`lib/logistics_requests.py`, `lib/vehicle_cargo.py` `run_pull_loop()`)

Generic "bring X to outpost Y" demand. Requester publishes wants. Supply ("free stock"): outposts are read live (`outpost_free_tiers()`, no per-outpost script), field Mining Drills advertise via `drill.status` (§1j). Served by the Pioneer reverse hauler (below) and the floating drone hauler (§2j).

- **Requests** `logistics.requests` (§4): `set_requests(outpost_id, requester, {item: (target, have)})` or `(target, have, min)` replaces that requester's entries; entries older than `REQUEST_STALE_TICKS = 6000` ignored/pruned (dead requester can't pin stock; must exceed the slowest requester's publish gap — the field Harvester's care tours). Requesters publish through `publish_requests(outpost_id, requester, wants, tick, requests=None, buyable=False, skip_foreign=True, have_of=None)`: writes only when target/min/urgent/buy differ from that requester's published entries or they are `REPUBLISH_TICKS = REQUEST_STALE_TICKS // 2` (3000) old (`have` not compared, so it lags up to that); empty wants withdraws. `skip_foreign` leaves an item another requester owns at that outpost to it. Requesters that take an item anyway (`skip_foreign=False`): site supply + eviction, home salt (`pump_salt`), Seed Maker/supply; all others yield. `keep` (5th wants field, `request_keep()`) is compared too. `have_of(item_id)` fills `have` on a write only (Plant Terraformer: its stock read is a live walk). `outpost_deficits(outpost, live=True)` = target − local stock (`outpost_stock()`: Warehouses + Drone Depots + home Inventory + Crop Automator outputs for `forage`) − in-flight pickups. `network_deficits()` sums published `have`-based deficits (cheap, for drones).
- **Two demand tiers**: `min` = what the requester needs to keep working (need tier), `target` = stock it wants on hand (buffer tier above `min`); no `min` (or ≥ target) = all need. Ladder in one table (`TIERS` = `(NEED, BUFFER)`, `TIER_RULES` per tier: `level` asked for, `keep` held back from other outposts, `fair` = deficit capped at a fair share): `tier_deficits()`/`tier_free()` per entry, `outpost_tier_deficits()`/`outpost_tier_free()` → `{tier: {item: units}}`; the route planners walk `TIERS` too, so a new tier = one row. `outpost_deficits_tiered()` → `(need, buffer)` adapter (miners, site supply): need = min − stock − in-flight, buffer = rest up to target; in-flight = pickups bound there + mining yield reserved for there (`mining.reserved_yield`). Planners serve urgent, then tiers in `TIERS` order everywhere: `haul_rank(tier_units, meters, overhead_m, urgent_units=0.0)` = (urgent units, then per tier the units serving it or an earlier tier, the last = all units) per (route m + overhead), `tier_units` from `route_tier_units(deficits, route)`, compared by `rank_beats()` in that order, so any trip carrying need beats any buffer-only trip and more need per meter beats a bigger buffer load; `fair` tiers (buffer) are capped by `fair_share_tiers(dest, deficits, sources)` → `fair_tier_caps(dest, tier, deficit, supply)` = supply split in proportion to every requesting outpost's deficit at that tier (others from published `have`), rounding remainder to the largest. Per-source split via `plan_take(source, item, left, cap)` → `{tier: units}` (`left` = `route_left(deficits)`; each tier only from what `source_tier(source, tier)` frees after the earlier tiers' takes).
- **Pickups** `logistics.pickups` (§4): `reserve_pickup(..., source_id=)` per planned/loaded item and source (amount 0 drops the entry; `aboard=True` after a load marks the units as cargo, summed by `aboard_units()` for `SourceCache.network_stock()`; planned-only entries still sit at the source and don't count), `release_pickups(vehicle)` after unloading; stale after `PICKUP_STALE_TICKS = 36000`. Debits both ends: `in_flight(dest)` against the requester's deficit, `reserved_from(source)` against that source's free stock (so two haulers never plan the same units there).
- **Free stock** (`outpost_free_tiers()`): outpost = `stock_scan` `HELD` (Warehouses, Bins, Drone Depot stockpiles, + Inventory and Crop Automator Forage if home) − `reserved_from()`, capped by what the `loader` can load there: `LOADER_DRONE` (drone haulers) everything held, `LOADER_VEHICLE` (default: Pioneer haulers, site supply's "free elsewhere") `LOCAL` + each Depot's stockpile above `depot_holds()` = its hauler drone stage requests (`depot_stage.staged_for()`) + same-outpost Smelter wants (`smelter_wants_at()` `fill_to`, an upper bound). Other haulers' pickups count against those held-back Depot units first (a drone's stage request is its own pickup), so a staged claim is not deducted twice. Then minus what it keeps for itself: its own request's `min` (or its `keep` reserve when higher, `request_keep()`) when giving to another outpost's need, its full `target` when giving to a buffer. A planner source carries these as `"tiers"` (`outpost_tier_free()`) and `"available"` = the most any tier frees (`most_free()`); drills, pumps and the Shop carry `"available"` only (nothing held back, every tier). So a home salt buffer of 2000 still hands everything above its need (30) to an outpost whose Terraformer is short. `outpost_free_stock()` = buffer tier, `LOADER_VEHICLE`. Loading: a Pioneer takes from the stores first (`take_item()`), then the Depots (`take_from_depots(spare_holds=True)`, every Depot's status logged, nothing moved = warn). Drill = advertised `items` − `reserved_from()` (both tiers).
- **Reverse hauler**: standard Pioneer template, hauler role (no role module) → `run_pull_loop()`, the only Pioneer hauler mode (§2f); `HOME_BASE` = where it parks = where requests are delivered. Per cycle: cargo aboard → deliver home first; else `_pull_deficits_tiered()` = live request `{tier: {item: units}}` at `HOME_BASE`, home included (no extra ore demand) → `_plan_pull_route()`: `fair` tiers capped by `fair_share_tiers()`, then every source (other outposts + advertised drills + salt pumps) whose free stock covers a deficit tried as first stop, then nearest-neighbour chain from there (`_plan_pull_chain()`), tiers in order then largest deficits (`tier_rank()`), up to `PULL_MAX_STOPS_PER_TRIP = 3` stops / cargo capacity (so several Water Pumps chain into one salt run); best `haul_rank()` over (round-trip m + `PULL_TRIP_OVERHEAD_M = 300`) wins (need rate first), so a nearby source with small top-ups doesn't shadow far sources holding the real deficit. Stops after the first only chained if direct leg ≤ `PULL_CHAIN_MAX_DETOUR_RATIO = 0.75` × (prev → home → next), so it never drives past home; skipped stops wait for the next trip. Pickup legs pass `drive_with_recharge(min_throttle=PULL_MIN_LEG_THROTTLE = 0.3)`: a leg a full battery could only drive below 30% throttle (no closer charging station) is refused instead of crawling at the 10% floor; a refused first stop drops out of planning for `PULL_UNVIABLE_COOLDOWN_TICKS = 18000` (`_drop_unviable_sources()`). Each first stop's chain and its measures are one pure call (`_pull_candidate()`, chain checks returned as one debug text), run as a `lib/atomic.py` call when `logistics_requests.route_atomic_ok()` (below the drone hauler's **Plan**, `docs/cheatsheet/vehicles_drones.md`). Trip skipped if planned < `min(PULL_MIN_LOAD_UNITS = 10, reachable)`, reachable = deficit units some source actually holds (deficits nobody holds, or left to drones, don't hold back a small real delivery); 1 when the route carries an `urgent` item (`urgent_items()`, `urgent_units()`). Legs via `drive_with_recharge()` (already refuses a leg that can't reach a charging station afterwards); recharge at stops that have a station; unreachable stop → head home with what's aboard (its and later stops' pickup reservations dropped).
- **Drone yield switch** (`logistics.drone_yield`, FLEET card `vehicles_panel.py` "leave to drones", default off): `_pull_sources()` drops every source `drone_served_source(source, home_outpost)` flags — only while the switch is on, the hauler's `HOME_BASE` has a Drone Depot (drones deliver only to Depots) and `drone_haulers_present()` (a drone `role == "hauler"` entry — one with `engine` — in `fleet.status` younger than `HAULER_FRESH_TICKS = 6000`; else every source stays with the ground hauler). Flagged: field Mining Drills, and outposts with their own Drone Depot. Water Pump salt never (drones can't load it). Each skip logged at `debug()`.
- **Shop source** (`_shop_source()`, `_buy_and_take()`): only for a hauler whose `HOME_BASE` is not home, and only for deficits whose request is flagged `buy` (`set_requests(buyable=True)`, read via `buyable_deficits()`; today only remote Bio Lab reagents, §2g). A virtual source at the home outpost's coords (id `SHOP_SOURCE_ID:<home id>` = `"shop:<outpost>"`, so haulers for different outposts never trim each other in `claim_pickups()`), "available" = the whole buyable deficit, appended after the real sources so free stock at home wins a tie. At the stop it buys one Inventory stack at a time and `take_item()`s it before the next; a cash manager denial (consumer `pioneer_reagents:<name>`, operating, §2l) or a refused purchase (credits, Shop stock) ends that item. Drone haulers never see it.
- **Plays nice with other haulers**: planned units are reserved per source (`logistics.pickups`) and count as in flight against the destination's deficits, so a drone already bringing 800 ore → pull hauler sees 800 less demand, and vice versa. Demand-bounded: drills are only emptied as far as the destination's requests (smelting sites: `ore_stock_target()` buffer) reach.
- **Drill location** (`lib/drill_sites.py`): `drill_positions()` walks `journal.surveyed_sites("nocturna")`; each `MiningSite` with a `drill_id()` gives that drill the site's `x`/`y` (cached `DRILL_CACHE_TICKS = 3000`, like pumps). A drill on no surveyed site is skipped (warned once per hauler run). On arrival (`DRILL_ARRIVAL_PRECISION_M = 2.0`) `vehicle.input.connect(drill_id)`; refusal → warning, nothing loaded that stop. Loading via `take_from_drill()`; no recharge at drill stops.
- **Source retention**: `retain_amount(item, outpost_id)` = own request target if this outpost requests it, else, while any other outpost requests it at all (even when topped up — continuous consumers drain again soon), `max(LIFEFORM_STASH_CAP_T = 25, largest remote target)`, else 0. Used by Drone Depot staging (§2h) and Essence Liquifier feed (§1h). Pioneer haulers take from Warehouses first, then Depot stock above `depot_holds()` (§2i free stock); Depot buffer staging (§2h) puts life forms in Warehouses.
- **Water Pump salt** (`lib/pump_salt.py`): pumps are field structures on water wells, found via `journal.surveyed_sites("nocturna")` WaterWells with `has_pump()` → `pump_id()` + well `x`/`y` (cached `PUMP_CACHE_TICKS = 3000`). Salt read live from the pump's `output` (`PickupOutputSlot`). Added as `"kind": "pump"` sources only when `salt` is wanted, home pumps included; connect/take reuse `drill_sites.connect_to_drill()`/`take_from_drill()`, arrival precision `PUMP_ARRIVAL_PRECISION_M = 2.0`. Drones can't take it (`not_at_source`).
- **Drones**: request score in miner target order (§2h). Biosites are permanent (35 fixed, 7 per biome, 1–3 forms each, refill at same coordinate after rarity cooldown — docs/guide/biosphere_biomass_tier.md), so a requested rare form is found deterministically via `journal.biomass_coords()`.

### 2i-1. Factory Outpost Site Supply (`lib/site_supply.py`)

`publish_site_requests(tick)` runs once per storage tick in headless `orchestrator_automation.py`, one `logistics.requests` entry set per outpost under requester `SITE_SUPPLY_REQUESTER = "site_supply"`; pull haulers homed there serve it (§2i). Roles come from the buildings at the outpost, no setting.

- **Fab site** (≥ 1 Fabricator): gross = Σ local Fabricators' active recipe Smelter-output inputs × `crafts_remaining` − stockpile (`production.fab_site_gross_need()`). `D = gross − local ingots − local ore a local Smelter refines (1:1) − in-flight ingots and ore`. `S` = free ingots at every other outpost (`outpost_free_tiers()` need tier). Ingot request level = local + in-flight + `min(D, S)` (all need tier; holds local ingots back from other sites), or + all of `D` when no local Smelter can refine that ore. Rest `D − S` goes to the ore request. Preference local ingots > local ore > remote ingots > remote ore, except remote ingots go first (up to `S`, before local ore) when `production.ship_units()` says ship (§2a-0-6 rule: big surplus or slow/impossible local smelt); in-flight counts both sides, so no hysteresis.
  - **Raw inputs** (`raw_input_wants()`): every active-recipe input no Smelter or Fabricator makes (e.g. Forage, which only the home Crop Automators hold) still to stage (`fab_site_gross_need(..., None, ...)`) is requested at level = local + in-flight + `min(short, free at other outposts)`, all need tier; none free and none in flight, no request.
  - **Ship plan** (`ship_wants()`): each item of `production.get_site_ship_plan()` (§2a-0-6 ship-before-craft) is requested at level = local + in-flight + to ship, all need tier; an item this requester already asked for stays requested while units are in flight. A higher request of the same item wins.
- **Ingot buffer** (`ingot_wants()`, fab sites): every item of `production.fab_site_ingot_targets()` (§2a) is requested at target = max(buffer target, planned level), need level = max(planned need level, buffer need), published even with nothing to pull: the request is what makes `outpost_free_tiers()` keep the buffer from other sites' buffer tier and the need tier from their need tier. Local Smelters refill it in idle time; haulers bring it where none can.
- **Smelting site** (≥ 1 Smelter, home included): one ore request per ore with an unlocked Smelter recipe: target `max(ore_stock_target(ore), need level)`, need level = local + in-flight ore + ore short from `D − S`, or 0 when no local Fabricator needs that output (pure buffer); never below the ore's consumer request level (a dock order there).
- **Stockpiles** (`site_stock_targets()` / `stock_wants()`, any outpost, home included): `SITE_STOCK_TARGETS = {"fabricator": {"tar": 2000, "forage": 1000}, "refiner": {"tar": 2000}, "fuel_assembler": {"lead_plate": 200}}` per building type present, as buffer tier; need tier = max(`SITE_STOCK_NEED = {"refiner": {"tar": 150}}` (`site_stock_needs()`), whatever else the site planned for the item (ship plan)), 0 otherwise. Requested whether or not any is free elsewhere (the request nets against local stock). `SITE_STOCK_CRAFTED = ("lead_plate", "tar")` items a Fabricator can build are also ordered (`order_site_stock()`): a backlog order (requester `SITE_STOCK_REQUESTER = "site_stock"`, idle Fabricator time only) sized to the summed targets, and an upgrade order (requester `SITE_STOCK_NEED_REQUESTER = "site_stock_need"`, tier 3) sized to the summed need levels (tar: 150 per Refiner outpost, crafted by `craft_tar`, 5 t Oil → 2 Tar, when the Lubricant/Plastic/Rubber byproduct falls short). Both are site orders (`production.SITE_ORDER_REQUESTERS`): they raise the Fabricator target but make home no consumer (`fabricator_root_targets()`), so home doesn't pull the stockpiles back.
- **Construction stock** (`construction_stock_targets()` → `(targets, needs)`, the Constructor's home `production.construction_site_id()` only): archive `site_supply.construction_stock` (`CONSTRUCTION_STOCK_KEY`, `{item: {"target": n, "need": n}}`, read by `construction_stock_levels()`, need capped at target), seeded from `EARLY_CONSTRUCTION_STOCK` (`gas_pipe_segment`, `liquid_pipe_segment`, `power_line_segment` target 25 / need 5; `gas_pipe_bridge`, `liquid_pipe_bridge` target 2 / need 0) and replaced by `LATE_CONSTRUCTION_STOCK` (segments 100 / 10, bridges 5 / 0) once the mining-drill phase is reached (`drone_upgrade.upgrade_phase_reached()`), only while the stored value still equals the early one; no power line bridge, the power network is one grid. Editable in the archive; an edit stops the switch. Each level fits one plan-ahead chunk plus its reserve (autoplay `supply_tiers.plan_ahead_limits()`, [autoplay.md](autoplay.md)), plus, per extractor kind, one kit (`construction_plan.EXTRACTOR_KITS`) per untapped surveyed fluid site (`untapped_kits()`: no `pump_id()`/`cap_id()`; exotic by `medium()`, none once Wildlife is complete), at most `CONSTRUCTION_KIT_CAP = 5`. Requested like the stockpiles above (target as buffer tier, need level as need tier, `plan_site(..., extra_stock, extra_need)`); the items a Fabricator can build are also a backlog order sized to the targets (requester `CONSTRUCTION_STOCK_REQUESTER = "construction_stock"`, idle time only) and an upgrade order sized to the need levels (requester `CONSTRUCTION_STOCK_NEED_REQUESTER = "construction_stock_need"`, tier 3). Those Fabricator-built items also carry `keep` = their target (`mark_reserve()`): the reserve is not free for another outpost's need (`outpost_free_tiers()`), so a Supply Dock order elsewhere neither pulls it nor counts it (§2a-1); units above the target stay free. Stock no Fabricator builds gets no `keep` (a dock order for it would wait forever). Covers work that waits for stock before it is planned (the autoplay planner's plan-ahead jobs, [autoplay.md](autoplay.md) §11g).
- **Home**: planned like any other outpost (ingot, ore, stockpile and consumer requests); its Inventory counts as home stock.
- **Consumer site** (`consumer_wants()`, any outpost, machines or not): per root consumed there (§2a-0-6 consumers), level = local + in-flight + `min(consumed − local − in-flight, free at every other outpost)`, free = `outpost_free_tiers()` need tier (stock above that outpost's own request `min`/`keep`, minus other haulers' reservations), each outpost read once per pass (one `PlanReads` in `publish_site_requests()`); kept while units are in flight. A blueprint item or fleet upgrade order part (`get_upgrade_orders()`: commissioned drone kit, chassis swap) no Fabricator will add more of (`settled_items()`: nothing in `get_fabricator_pipeline()`, `root_remaining()` = 0) is flagged `urgent`, so haulers skip their minimum load for it; while more are being built it waits for the batch. Manual transit orders (`manual_transit_wants()`, units built off home) are always flagged `urgent` so completed units haul home immediately. Items of `production.RECURRING_ORDER_REQUESTERS = ("plant_terraformer", "field_amplifier", "site_stock_need")` (recurring consumables) are never urgent; Fuel Assembler Lead Plates stay urgent (`get_upgrade_orders(skip=...)`). An ingot request of the same item wins when higher.
- **Dock ore** (`dock_ore_levels()` / `publish_dock_ore_need()`): a consumer site pulls only units that exist, so a Supply Dock order for a Smelter output with too few units anywhere would never raise an ore request. Per Smelter output still owed (`dock_remaining_requirements()`), units = owed − `SourceCache.network_stock()`, charged as its ore to the first smelting site by id that refines it and has it assigned (`assigned_ores_by_outpost()`). Raw ore an order owes itself: owed − network stock, charged to the first site by id that has it assigned, a site whose dock owes it first. Archive `mining.dock_ore_need`. Its stationed miners rank that ore as need tier (`vehicle_mining.stockpile_need()`), ahead of stock-only ore. No logistics request: haulers move nothing extra for it.
- **Role switch drain / eviction** (`evict_stranded()`, requester `EVICT_REQUESTER = "site_evict"`): removing a site's Smelters withdraws its ore request, so its ore is free stock for any request. Ore at an outpost with no Smelter (home included) that it neither mines (`assigned_ores_for()`), requests nor consumes (a Supply Dock order there, `fabricator_root_targets()` consumers) is stranded; first-seen ticks in archive `site_supply.stranded` (`{outpost_id: {ore: tick}}`, pruned to what is stranded now), checked against this pass's planned requests (`planned_requests()`). After `EVICT_AFTER_TICKS = REQUEST_STALE_TICKS` (6000) it goes to its destinations (below). Withdrawn once gone. **Stranded goods** (same tracking, key and timing): ingots and intermediates — `item_catalog` category in `EVICT_GOODS_CATEGORIES = ("refined", "crafted")` that some Fabricator recipe takes as input (`evictable_goods()`), minus `storage.must_stay_in_inventory()` items and `CONSTRUCTION_ITEM_IDS` (pipe/power line segments and bridges; moved only by blueprint consumer demand) and `EVICT_HOLD_ITEM_IDS = ("tar",)` (also the Refiner's reagent; a Refiner outpost requests it through `SITE_STOCK_TARGETS`) — held in an outpost's Warehouses/Drone Depots (`held_item_ids()`) where there is no Fabricator (home included), not requested there and not a consumer root there (`stranded_goods()`). No `item_catalog` → no goods evicted. **Stragglers** (`stragglers()`, same tracking, key and timing): at most `STRAGGLER_MAX_UNITS = 50` of a finished good (category in `EVICT_GOODS_CATEGORIES`, Constructor items included, minus `must_stay_in_inventory()` and `EVICT_HOLD_ITEM_IDS`) at an outpost other than home or a storage outpost that it neither requests nor consumes, and that its Fabricators neither stage (`fab_site_gross_need()`) nor hold in their site targets (`get_site_fabricator_targets()`; a root built there for another site counts only while `get_fabricator_pipeline(cache, site_id)` shows a local Fabricator making it). Requested like stranded goods, but **urgent** (haulers skip their minimum load); when the destination already requests the item (construction stock at the Constructor's home), that request is flagged urgent instead. Stranded ore/goods keep their own rule where both match. **Destinations** (`evict_candidates()`), tried in order until the units are placed: users first (ore: home if a home Smelter refines it, then every smelting site that does, by id (`smelting_sites()`); goods: home if home has a Fabricator (then home is never a source), then every fab site; Constructor stragglers (`CONSTRUCTION_ITEM_IDS`): `construction_site_id()` only), then the **storage outposts** (`storage_outposts()`: not home, a Warehouse or Storage Bin, a Drone Depot (`item_tiers.DEPOT_TYPE_TIERS`, the drone haulers' only destination) and no `storage.PENALIZED_TYPES` building), nearest first, never from one storage outpost to another. Home is never a fallback: an item with no candidate is not stranded and stays where it is. **Room** (`evict_room()`, home uncapped): `storage.slot_room()` over `storage.slot_layout()` (each Warehouse slot, each Storage Bin as one slot) = room in the slots already holding the item, or its planned request target rounded up to whole slots when that is more (a 1800 ore target may fill its 2000 slot), else one empty slot while `EVICT_FREE_SLOTS_KEEP = 1` others stay empty (storage outposts keep none), minus units in flight there. Units that find no room stay. Home destination → home requests them (requester `EVICT_REQUESTER`), level = home have + in-flight + free there (need tier), skipped for an item another requester already asks home for; any other destination → `add_evicted()` raises its site-supply target by local + in-flight + the units sent (buffer tier, need level unchanged).
- Withdrawn (empty `publish_requests()`) once an outpost has no Smelter/Fabricator demand; unchanged requests follow `publish_requests()`'s republish rule.
- `production.get_smelter_demands()` nets against `SourceCache.network_stock()` (home Inventory + every outpost's Warehouses and Drone Depots + loaded hauler cargo, `aboard_units()`), so ingots a remote Smelter made aren't refined again at home.

### 2l. Cash Manager (`lib/cash.py`, headless `orchestrator_automation.py`, CASH card `cash_panel.py`)

One budget owner for every Shop purchase. State in one archive dict `cash.budget` (§4).

- **Consumers** call `cash.can_spend(consumer, cost, planned=, label=)` right before a buy and `cash.spent(consumer, amount)` after it (`cash.release(consumer)` when a buy fails or nothing is wanted any more). `spent()` keeps the ask with `planned − max(amount, cost)` while that is > 0; `cash.keep(consumer)` refreshes an existing ask without a grant (`BuildingSwapUpgrader.step()` calls it every pass while a swap runs), so the rest of an order stays the savings goal between buys. Ids are `<kind>` or `<kind>:<instance>`; priority and operating status match on the kind.

  | Kind | Where | Class |
  | :--- | :--- | :--- |
  | `bio_reagents:<lab>` | `bio.py` BioLabController, home Shop buy of missing reagents | operating |
  | `pioneer_reagents:<pioneer>` | `vehicle_cargo.py` `_buy_and_take()` (remote-home hauler Shop pulls, §2i) | operating |
  | `crop_automator` | `harvester_machines.py` `buy_automator_kit()`, planned = wanted × price | capital |
  | `bin_upgrade` | `warehouse_upgrade.py` `BinUpgrader` (§2k-1) | capital |
  | `warehouse_upgrade` | `warehouse_upgrade.py` (§2k-1) | capital |
  | `pioneer_commission` | `fleet_commission.py` `_buy_missing()` (§2k-2), planned = cost × (1 + queued jobs) | capital |
  | `drone_commission` | `fleet_commission.py` crafting state: drone parts only the Shop sells (`spec["buy"]`, e.g. the miner's Portable Bio Extractor), §2k-2 | capital |
  | `tank_upgrade` | `tank_upgrade.py` (§2k-3) | capital |
  | `pioneer_upgrade:<pioneer>` | `pioneer_upgrade.py` auto tier upgrades (§2b-1); manual Sport Nav stays a plain affordability check | capital |

- **Decision** (`decide()`, live inside one `archive.transaction()`): `free = balance − other consumers' holds − floor`; deny if `cost > free`. Operating kinds (`OPERATING`) use floor 0 and skip the goal check: reagents come before everything. Capital kinds use the floor, then the **savings goal**: the highest-priority other capital ask ranked above this one that holds nothing yet; deny if `cost + goal planned total > free` unless `cost ≤ SMALL_RATIO = 0.10` × goal's next cost. A grant sets a hold of `cost` for `HOLD_TICKS = 600`; every call refreshes the consumer's ask (dropped after `ASK_STALE_TICKS = 3000`). Only cash on hand is granted, never forecast income.
- **Priority**: `cash.budget["priority"]`, reordered with the CASH card's top/^/v/bottom buttons (act on the selected list row); default `DEFAULT_PRIORITY = [crop_automator, bin_upgrade, warehouse_upgrade, pioneer_commission, drone_commission, tank_upgrade, pioneer_upgrade]`; a stored list without a newer default kind gets it appended. Unknown kinds rank last.
- **Floor** = `max(MIN_FLOOR = 1000, operating burn/h × FLOOR_HOURS = 12)`. With no manager pass for `MANAGER_STALE_TICKS = 1200` (panel down, or tier < 4), capital kinds use `LEGACY_RESERVE = 100000` instead.
- **Manager pass** (`CashManager.step()`, first thing each `orchestrator_automation.py` storage pass): balance sample every `HISTORY_STEP_H = 0.25` game h into `history`, kept `INCOME_WINDOW_H = 24` h; spend log (`spent`, ≤ `SPEND_LOG_LEN = 200`). Gross income/h = (balance change + logged spend) / span, burn/h = operating spend / span, both `None` below `MIN_RATE_SPAN_H = 1` h. Sales (kit resale) count as income. `pipeline`: campaign reward still to earn (`reward × unshipped fraction`), already-shipped share, weekly board remainder; shown only. `queue`: every ask, operating first then by priority, with `eta_h` = cumulative unheld cost + floor − balance over income/h (`None` without an income rate); `planned` = sum of planned totals.

### 2m. Early Build Order (`lib/early_buyer.py`, headless `orchestrator_automation.py`)

Plays the base build order from the lib tier (Data Archive, 70k TP) until the Control Room (150k TP). Before that, tier-0 `power/solar.py` plays the same order from Ship Computer (10k TP). `EarlyBuyer.step()` runs from `between_steps()`, once per `EVAL_TICKS = 50` (~5 s); info status line at most every `HEARTBEAT_TICKS = 200`.

- **Build order** (`STAGES`, from the headless build-order search, [early_optimization.md](../autoplay/early_optimization.md)): O2 to 2.2 ppt → heat to 12 HU → O2 to 10 ppt → pressure to 1.2 kPa → pressure tail (`TAIL_STAGE`). The first stage with an unmet target is active. Each pass sells the other pillars' generators (and stray kits in Inventory), keeps `POWER_KEEP` (3 batteries, 6 solar; `TAIL_POWER_KEEP` 5/10 in the tail; one filler generator is sold for each missing power building with no free slot), then fills every free base slot with the active pillar's generator, one buy at a time. A fresh deploy is switched on once; breakers are otherwise PowerGridManager's (§1a).
- **Pressure Mk II tail** (from 1.2 kPa, `MK2_RESEARCH` unlocked): once the tail's power counts stand, buys `MK2_PACK` one at a time and applies it with `computer.upgrade()` to every Pressure Generator below Mk II (`tier()`). The build order fixes the count: with 15 power buildings, the Charging Station and the Bio-Loop, 6 generators are left. A refused buy or upgrade ends the pass.
- **Charging Station** (Charging Station researched): bought with the Rovers (wanted count above 0, Rover + Deep Extraction researched) or a Pioneer (due and buildable, below), whichever is ready first, so a missing Drill Module research never holds back the scout; with no free slot one filler generator is sold for it.
- **Rovers**: `ROVERS = 0` by default: a Rover mines only H1 ore and arrives close to the scouts ([unlock_paths.md](../gameknowledge/unlock_paths.md)); the archive's `rovers` asks for some. That many chassis once a station stands. `ROVER_GEAR` (nav, sonar, drill) bought into Inventory for each Rover lacking that kind at any tier; a buy refused with `inventory_full` first sells (else drops) the largest ore, else ingot, stack. Each Rover mounts its own gear at start (`lib/rover.py` `fit_rover_loadout()`, `ROVER_LOADOUT`, `LoadoutFittingMixin` §2k-2).
- **Pioneers**: at `PIONEER_TP = 100000`, one job per evaluation on the commission queue (§2k-2) for the first role of `pioneer_order()` that queued jobs plus deployed Pioneers don't cover: one `scout`, then `CONSTRUCTORS = 1` `constructor` (so an outpost can be founded before the Control Room), then `scout` up to `SCOUTS = 3`. A deployed Pioneer counts as `constructor` with `constructor_module` mounted, else as `scout`; one still being fitted counts as its job. A role is queued only once `build_spec()` can build its whole preset (a blocked job needs the FLEET card's Commission tab to cancel, which doesn't exist yet); a locked role is skipped for the next one. Spare scouts are retired later (TODO.md, manual-run item E). The coordinator buys through the cash manager (§2l), so it waits for the floor.
- **State** `early_buyer` (archive dict): `done` (Control Room researched; idle for good), `generators` (default True), `rovers` (default `ROVERS`), `pioneer` (default True), `scouts` (default `SCOUTS`), `constructors` (default `CONSTRUCTORS`). The headless build-order search sets `generators` False: its plan places the buildings (`run.mjs --lib-tier --policy`, §10b).
