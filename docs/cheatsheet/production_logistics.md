### §1j Field Mining Drill Telemetry (`lib/mining_drill.py`)

A drill needs no control. It extracts on its own; the only script surface is `drill_rate()` and a read-only `PickupOutputSlot` stockpile (docs/components/mining_drill.md). One controller (`MiningDrillController`) serves all three variants (`mining_drill`, `mining_drill_industrial`, `mining_drill_heavy` thin scripts).

- **Who publishes**: orchestrator_automation.py, every `DRILL_TELEMETRY_TICK_INTERVAL = 600` ticks, for every drill (`publish_all_drills()`: power-grid members of a drill type plus existing `drill.status` entries; one `MiningDrillController` per drill kept across passes so warnings fire once per change). A drill's own script publishes once and ends — the drill mines without a script, and a running script costs every script budget (dev_workflow.md §1d-1).
- **Poll**: `POLL_INTERVAL_S = 60.0` (Mk I: 2,000 units at 25 t/h = ~80 h to fill; Heavy: 5,000 at 200 t/h = ~25 h). Capacity always read live.
- **State**: `drilling` (rate > 0), `full` (rate 0, count ≥ capacity), `stalled` (rate 0 with room left: unpowered, no deposit, or deposit too hard; API can't tell these apart). Warn once per transition into `full`/`stalled`; info on recovery.
- **Near full**: fill ≥ `NEAR_FULL_FRACTION = 0.8` while drilling → one warning with time-to-full, re-armed once fill drops back under it.
- **Time-to-full**: `(capacity − count) / drill_rate()`, assumes 1 stockpile unit = 1 t (unverified).
- Thin script passes `drill_type` (published as `type`).
- **Telemetry** `drill.status` (§4). Drills sit on mineral sites, not the outpost network, so `ArchiveCleaner.clean_machine_status()` can't prune them; the age rule of `archive.publish_status()` (archive_ipc.md §4) does.
- **Pickup advert**: the `drill.status` entry's `items` is what the reverse hauler (§2i) reads as the drill's free stock; its position comes from its `MiningSite` (§2i "Drill location").

### §1m Weather Station Signal Decoding (`lib/weather_signals.py`)

Recovers storm aftermath coordinates (Raw Uranium from dust storms, Storm Glass from thunderstorms; docs/guide/weather_system.md) and publishes them for drone collection (collection: §2j-1 in `vehicles_drones.md`).

- **Reception** (simworker `Fre()`): a powered station hears every `broadcast` copy plus its own biome's dust channel, planet-wide (no distance check). Thunder: 4 packets, all broadcast, so one station suffices. Dust: `DUST_PACKET_TOTAL = 8` packets, packet 1 broadcast, the other 7 spread over all 5 biome channels, so a dust message completes only with one powered station in **every** biome. Missing biomes are warned on change.
- **One running script**: `signal_receiver` is a read-only property, so the leader (lowest id among powered stations) reads every station's receiver; every other station's script ends at once. Stations re-discovered (and leadership re-checked) every `STATION_REFRESH_SWEEPS = 10` sweeps. Weather Stations are in no shed tier (§1a).
- **Sweep**: every `SWEEP_GAME_HOURS = 1.0` world-clock hour (`game_clock.real_seconds_per_hour()`). Messages stay audible until storm end + `SIGNAL_GRACE_GH = 4.0`.
- **Validation**: valid copy = `sum(ord(c) for c in data) == checksum` and `data` = `event_id|number|total|dx|dy` matching the copy's fields. Noise copies reuse the valid checksum with a changed dx/dy. Coordinate = sum of dx/dy over packets 1..total (absolute world x/y).
- **Timing**: aftermath appears at storm end = `expires_at_gh − SIGNAL_GRACE_GH` (`ready_gh`) and lasts `AFTERMATH_WINDOW_GH` = uranium 48 h, storm_glass 96 h. The coordinate is usually known before `ready_gh`. Units: uranium 14–28, glass 2–4 (`AFTERMATH_UNITS`); one `collect()` takes at most 5.
- **Archive** (§4): `weather.signals` (incomplete messages, kept across restarts; dropped when their window closes) and `weather.aftermaths` (decoded sites, pruned after `expires_gh`). The leader's Signal Board shows the newest decoded site via `resolve()`.

### §1n Fuel Assembler (`lib/fuel_assembler.py`) and Lead Casks (`lib/lead_cask.py`)

One script per Fuel Assembler (thin `nuclear/fuel_assembler.py`). Recipes (simworker): `craft_fuel_rod` = 4 Raw Uranium + 2 Lead Plates, 6 game h, 1,800 W; `craft_nuclear_battery` = 4 Raw Uranium + 3 Lead Plates, 4 game h, 1,200 W. Stockpile 40 units mixed, output buffer 5.

- **Demand, Fuel Rods first**: target = local consumer reserve (`lead_cask.consumer_rod_reserve()`: `ROD_RESERVE = 1` + `RODS_PER_REACTOR = 2` × Reactors + `RODS_PER_MK4 = 1` × Mk IV `temp_heater`/`pressure_generator`/`oxygen_generator` (`tier() >= 4`), constants in `lib/lead_cask.py`) + rods owed to Supply Dock orders, all at this outpost. Supply Docks take only cask rods above that reserve less the rods staged in the consumers (`lead_cask.rods_for_orders()`), so an Earth order never drains a Reactor's buffer. Have = rods in this outpost's casks + those consumers' `input.count()` + output buffer + a craft in progress. **Nuclear Batteries** next: `fabricator.manual_orders` entry (counted down on delivery) + max(0, dock orders + blueprint need − network stock) − pending.
- **Pick**: first short recipe whose one craft the stockpile plus local stock covers (uranium in this outpost's casks, plates via `storage_take.takeable_stock()`). Without a Fuel Rod cask only batteries are picked. A running craft or one with progress is never switched (`set_recipe()` answers `busy`). Both recipes share inputs, so a switch keeps the stockpile.
- **Staging**: inputs for min(shortfall, `STAGED_CRAFTS = 2`) crafts. The input port takes one source at a time: uranium via `lead_cask.take_from_casks()`, plates via `storage_take.take_item()`.
- **Power gate**: inputs are staged only while the grid's reserve (lower of battery fraction and `power.reserve_fraction()`) ≥ `START_RESERVE_FRACTION = 0.6`, so crafts run as bursts on a full bank; a staged craft runs to completion. Hard-shed in Power Guard tier 1 (§1a); `power.shedded` also stops new staging. **Rod emergency** (a Reactor at this outpost in `lead_cask.rod_emergency()`, power_fluids §1a-0): rods only, staged whatever the reserve or `power.shedded`; the Power Guard keeps the assembler powered while other loads shed by reserve as usual. Waiting for 0.6 would stall: the oil generators throttle down once the bank recovers past their stop line, below it.
- **Lead Plates**: every Fuel Assembler outpost keeps a 200-plate stockpile (`site_supply.SITE_STOCK_TARGETS`, §2i-1). At home only, a standing order (requester `"fuel_assembler"`, `UPGRADE + 90`, §2a-1 item 4) also asks for the plates of the next `PLATE_ORDER_CRAFTS = 2` short crafts, cleared when nothing is short; off home it would pull plates home (orders-book roots are consumed at home). One shared requester: a second assembler overwrites the entry (harmless, see sizing). A heartbeat entry (`ORDER_STALE_TICKS`, item 4 below), so it lapses once no assembler script runs; a parked assembler wakes within the window.
- **Output**: Fuel Rods first straight into a local Supply Dock whose order owes them (`production.dock_owed_at()`), capped by `lead_cask.rods_free_to_ship()` (cask rods + rods in hand beyond the local consumers' reserve, the floor `rods_for_orders()` leaves the docks), the rest into this outpost's `fuel_rod` cask; Reactors and Mk IV generators pull from it. Nuclear Batteries: local dock order first (`dock_delivery_targets()`), then `storage_unload.drain_port_storage_first(include=)`, `consume_manual_order()` on the stored units.
- **Idle** (nothing short): clears the recipe (needs an empty output buffer) and parks (`script_parking` kind `fuel_assembler`, wake after 3000 ticks). Poll `ACTIVE_POLL_S = 5.0`, `IDLE_POLL_S = 20.0`.
- **Sizing**: after the Weather Program unlock, dust storms come every 48 game h (simworker `rw()`), 14–28 Raw Uranium each: about 10.5 U/day if every one is decoded and collected, about 2.6 rods/day. One assembler makes 4 rods/day (6 h craft); a Reactor at heat 1.0 burns 1/3 rod/day, a Mk IV 0.1 rod/day. Uranium, not assembler time, is the limit (about 7 Reactors at full heat), so one assembler is enough.

**Lead Casks** (`lib/lead_cask.py`, tier 4, shared by the assembler, `drone_weather`, `supply_dock`, `terraforming` and `production`). A cask holds one hot item and unlatches when empty. A Depot unloading hot cargo takes the **first** cask at its outpost that is empty or holds that item with room (simworker drone `unload`), so scripts cannot pick the cask; roles are enforced by planning and repair:
- `lead_cask.roles` (§4): `{cask_id: "fuel_rod" | "raw_uranium"}`. `ensure_rod_cask()` (called by the assembler every step) gives one cask per outpost the `"fuel_rod"` role: a cask holding rods, else an empty one, else the least-full uranium cask. Needs at least 2 casks at the outpost. Entries of casks that no longer exist are pruned on write.
- `room_for()` (drone uranium collection, `drone_weather.cask_room()`) leaves out casks reserved for the other item.
- `repair()` moves Raw Uranium out of a `"fuel_rod"` cask with `transfer_to()` into other casks; `take_from_casks()` drains such a misfiled cask first. With every other cask full, the assembler stages that uranium into its own stockpile (`unlatch_rod_cask()`, up to `UNLATCH_STAGE_UNITS = 24` Raw Uranium staged; sets the rod recipe when none is set), so finished rods can still leave the output buffer. The cask unlatches when empty and the next rod latches it.
- `unload_target()`: cask for an eject of hot cargo (role allows it, room left), used by `supply_dock.drain_dock_cargo()`.

### §2a-0 Supply Dock cargo draining (`lib/supply_dock.py` `SupplyDockController`)

`set_order()` rejects with `"cargo_present"` while any cargo loaded in dock's 5 slots —
`clear_order()` deliberately does **not** drain cargo, only releases order assignment.
`drain_dock_cargo()` ejects every non-empty slot to Inventory (off home: a local Warehouse via `best_unload_target(outpost=)`, none with room → left in the dock); `step()` calls it (retries next
cycle) whenever `curr_order` is `None` but `dock.total() > 0`, before trying `set_order()`.

### §2a-0-1 Construction material demand cascade (`lib/production_cascade.py`)

`_cascade_blueprint_demand()` = single source of truth for "how much of any item — finished or
intermediate — active construction ultimately needs":

- Seeded from `required_item`/`required_count` across every pending/paused Construction Blueprint
  job (summed, deduped by job id).
- Seed netted against units already aboard ground vehicles (`_vehicle_cargo_counts()`, via
  `fleet.vehicles()` + live `cargo.stacks()`): a constructor Pioneer loads a whole chained-job batch
  while every job stays pending until built, so without this the Fabricator re-crafts the batch.
  Cargo a hauler pickup already reports aboard (`logistics_requests.aboard_units()`, counted as
  network stock) is not netted again.
- Breadth-first propagated down through Fabricator/Smelter recipe `inputs` (`recipe_inputs_for()`).
- **Only each tier's shortfall propagates down** — demand beyond item's current
  `inventory.count()`, so on-hand stock counted once. Example: 10 `power_line_segment` needed,
  3 in Inventory → 7 to build → 7 `titanium_ingot` needed, 5 in Inventory → only 2 propagate →
  4 `titanium_ore` needed (2:1 smelt ratio), not 20.
- Known limitation: item reachable via multiple paths nets shortfall against same Inventory
  snapshot independently per occurrence, slightly overstating demand under diamond-shaped recipe
  dependency — not worth full MRP-style solve for game's shallow (2-3 tier) chains.

Two consumers read cascade differently:
1. `fabricator_target_ladders()` (§2a-1; `get_fabricator_targets()` = its flat totals) uses **raw, uncapped demand** (each blueprint job's units at its `blueprint_prio()`) for items Fabricator can
   build.
2. `get_construction_material_reservations()` nets against current stock
   (`min(inventory.count(item_id), demand)`) — protect-from-shipping amount.
   `supply_dock.py`'s `step()`/`pick_best_order()` subtract this before deciding how much to
   `take()` or how "ready" order looks. Demand = `dock_protected_wants()` (blueprints +
   `outranking_order_wants()`). A dock away from home loading in `step()` subtracts
   `remote_dock_reservations()` instead: those order-book floors still missing from home held
   stock, protected in its outpost's stock while site supply hauls them home.

Deliberately conservative: job's full cascaded demand stays reserved while pending/paused, even
after cargo loaded (cargo not tracked here).

### §2a-0-2 Multi-Fabricator Support (`lib/production_core.py`, `lib/production_sites.py`, `lib/fabricator.py`)

`production.discover_fabricator_ids()`/`_default_fabricator()` find Fabricators at runtime (no hardcoded ids), network-wide (every `outpost_network.outposts()` entry; pass `outpost=` for one outpost). `discover_smelter_ids()` and `discover_supply_dock_ids()` same. `claim_recipe()`/`release_recipe()` (`lib/fabricator.py`,
`STALE_TICKS=600`, archive key `"fabricator.recipe_claims"`, shape `{outpost_id: {recipe_id: {"fabricator": id, "tick": n}}}` via `production.site_recipe_claims()`/`claim_site_id()`, so only machines at the same outpost block each other; flat per-recipe entries are dropped on the next write) stop multiple Fabricators converging on same recipe: `choose_recipe()`'s candidate loop claims each sourceable candidate in rank order (§2a-1), next on claim fail.

#### Fabricator split, holdings and drains

- **Pile-on fallback + even split**: if NO candidate exclusively claimable (only one recipe demanded), `choose_recipe()` joins the top-ranked one anyway, no idle.
  `get_fabricator_worker_ids(recipe_id, site_id)` (sorted live roster of Fabricators on that recipe at that fab site) splits `crafts_remaining` floor-plus-remainder: first `crafts % workers` ids get one extra, shares sum exactly (a worker may get 0 and idle). The join gate counts the same site only (`get_fabricator_worker_count(recipe_id, site_id)`).
- **Pipeline netting**: every "still needed" (`get_fabricator_active_recipe()`, `choose_recipe()`) = site target (§2a-0-6) − `SourceCache.held_stock(item, outpost)` (`local_stock()` + that outpost's Drone Depot stockpiles, `depot_stock()`; loaders such as Smelters and Supply Docks use `local_stock()`, since `take_item()` doesn't reach Depots) − `production.get_fabricator_pipeline(cache, site_id)` = output-buffer stacks + one craft's output per running craft of every Fabricator at that site − `SourceCache.staged_units(item, site_id)` = units in those Fabricators' input stockpiles. **Producer holdings**: `SourceCache.fab_have(item, outpost)` = `held_stock()` + `pipeline_units(item, site_id)` (output slots + one craft per running craft) + `staged_units(item, site_id)` (Fabricator stockpiles, Smelter input slots), over Fabricators and Smelters; `network_have(item)` = `network_stock()` + the same over every site. One read of each machine per pass (`fabricator_holdings()`, `smelter_holdings()`; Smelters only read for an item a Smelter recipe takes or makes). Moving a unit from storage into a machine, or from a craft into storage, leaves these unchanged, so loading inputs never reads as a new shortfall. `get_fabricator_pipeline()` stays Fabricator output only ("a Fabricator is making it").
- **Outpost-aware machines** (off-home Smelter/Fabricator): ports rest on `storage.local_port_target(outpost)` (`"inventory"` at home, else first local Warehouse; none → one warn, no connect). `take_item(outpost=)` pulls from local Warehouses only, output drains and `recover_input()`/`eject_excess_inputs()` go to a local Warehouse (`best_unload_target(outpost=)`), Smelter ore stock = `SourceCache.local_stock(item, outpost)` (home: `stock()`; elsewhere that outpost's Warehouses, one `.stacks()` sweep each per pass). Dock raw-ore reserve applies to home Smelters only. Smelter demand = `get_smelter_demands()` (netted vs `network_have()`), and at every site (home included) merged per level (max) with `production.site_smelter_demands(outpost)` and the ingot buffer (`site_ingot_ladders()`) into one map (`SmelterController.demands()`): `site_smelter_demands()` = local Fabricators' active-recipe need (`fab_site_gross_need()`, at the recipe's prio) − local stock − in flight, so a site short of glass that sits at another outpost still smelts its own. Fabricator demand is per fab site (§2a-0-6). `production.machine_outpost_id(machine)` = `machine.outpost.id`.
- **Output drain**: Fabricator `drain_output()` first pushes each output stack straight into a local Supply Dock whose order still owes it (`production.dock_delivery_targets(item, count, outpost)`: `dock_owed_at()` = required − shipped − what this outpost's docks on that order hold; only held stock + count beyond `dock_protected_wants()` may ship: gross Construction Blueprint demand plus `outranking_order_wants()`, the order-book floors at `BUILD` or above, which outrank every dock order's `ORDER` band, e.g. a COMMISSION kit at `MANUAL`), via `storage_unload.push_to_targets(port, item, count, [(id, cap)])` (connect refused / busy / nothing taken → next target; returns `[(id, moved)]`). The rest goes `storage_unload.drain_port_storage_first()`: local Warehouse first, then `local_port_target()` (Inventory at home); Inventory-only items still land in Inventory (`best_unload_target()` → `_inventory_first()`). `consume_manual_order()` counts only the stored units. Smelter `drain_output()` pushes first into local Fabricators short of the ingot (`production.fabricator_wants_for()`, the `fabricator.wants` archive key, the want with the highest prio first, then the largest; less what this Smelter already pushed against the same entry tick), then a local dock order (`dock_delivery_targets()`), then storage. Smelter (`drain_output()`, `recover_input()`), Fuel Assembler batteries, Seed Supply and Feed Maker drain storage-first too; `drain_port_inventory_first()` (Inventory first, a Warehouse only on `INVENTORY_FULL_STATUSES = ("partial", "target_full", "slots_full")`) serves the Seed Maker. Every port send goes through `send_stack(port, item_id, count, target) -> (moved, status, message)` (connect if needed, then send).
- **Material slots**: a multi-material input stockpile holds only so many distinct materials, per type (simworker `defaultItemStackSlots`): Fabricator 8, Feed Maker 8, Crop Automator 8, Waste Processor 10, Plant Terraformer 6, Habitat 5, Bio Lab 4, Bio Caster 4, Fuel Assembler 3, Seed Maker 3, Drone Depot 3/4/6 (only the Depot reports it, `slot_capacity()`). `take()` of a new material past the cap answers `slots_full` with unit room left, so a loader that leaves stray materials behind jams. `storage_take.hit_slot_cap(report)` spots it in a `take_item(report=)` result, `storage_unload.eject_unneeded(port, keep, target)` ejects every stack not in `keep`. Users: Feed Maker (`eject_strays()`), Crop Automator (`eject_unused_seeds()`); Fabricator, Bio Lab and Seed Maker eject every unneeded input each step anyway. Test fakes enforce the same caps (`tests/game_stubs.py` `MATERIAL_SLOTS`).

#### Load sizing and polling

- **Load chunking**: `load_inputs()` capped to `FABRICATOR_LOAD_CHUNK_SIZE = 10` units per call. `lib/smelter.py` ore top-up has matching `SMELTER_LOAD_CHUNK_SIZE = 10` (lifted to the prefill window while that window is stretched, see Ore intake caps); Supply Dock loading uses `supply_dock.load_chunk()`: per item, `rate × gap × SUPPLY_DOCK_LOAD_LOOKAHEAD (2.0)` − dock cargo, where `rate` = `dispatch_rate()` and `gap` = game hours since the previous `step()` (default `SUPPLY_DOCK_DEFAULT_GAP_HOURS = 0.5`, clamped to `SUPPLY_DOCK_MAX_GAP_HOURS = 2.0`). It is at least `SUPPLY_DOCK_LOAD_CHUNK_SIZE = 10` and at most the unreserved stock ÷ the docks the central plan puts on that order (never under the chunk), capped by need.
- **Poll cadence** (Smelter and Fabricator `run()`): `step()` returns whether the machine is active (running, buffers non-empty, or it loaded/drained/ejected/set a recipe this step); `run()` sleeps `ACTIVE_POLL_SECONDS = 1.0` then, `IDLE_POLL_SECONDS = 2.0` otherwise. A script's step allowance depends on how many scripts run, not on how busy they are (docs/BENCHMARK.md, Load dependence), so a faster poll costs only this script's own steps. A Smelter that sets a new recipe tops up ore in the same step. Fabricator `load_inputs()` logs one `Loaded …` line per call, Smelter `drain_output()` one `Sent …` line per call.
- **Smelter refill hysteresis**: a running Smelter with `in_buf >= max(units_per_run, prefill_cap // 2)` skips the take (outcome `buffer_ok`), so top-ups come in larger batches instead of a feeder wait for 1–2 units every poll.
- **`production.craft_prefill_units(recipe, item_id, prefill_seconds=INPUT_PREFILL_SECONDS)`**
  (`INPUT_PREFILL_SECONDS = 30`, no archive state) = real fairness mechanism. Asks "how much staged to keep crafting next ~30 real seconds", not "how much left to load": `ceil(prefill_seconds / craft_seconds(recipe))` crafts' worth, floor one craft's requirement. Fabricator only: while the last `load_inputs()` pass left an input below one craft (`_short_inputs`), every other input of that recipe loads one craft's worth at most, so a machine that can't craft doesn't hoard scarce inputs. `craft_seconds()` converts `recipe.duration_game_hours` via
  `game_rules.SECONDS_PER_GAME_HOUR` (`DAY_CYCLE_DURATION_SECONDS` 600 / 24 = 25 s), times `source_speed / speed` (`machine_speed(machine)` from `MACHINE_TIER_SPEED = (1, 2, 4)` for Mk I/II/III). Since v0.1.31 a `Recipe`'s `duration_game_hours` includes the tier of the machine it was read from (Mk I time / that machine's speed, as the Feed Maker's always did), so `source_speed` normalizes it to Mk I and `speed` rescales it to the machine that runs it. Both controllers read the recipe from their own machine and pass neither (`craft_prefill_units()` takes no speed). `production_sites.local_make_seconds()` reads it from `SourceCache` (the first Smelter/Fabricator, `recipe_source_speed(kind)`) and runs it on the site's fastest machine of that kind (`_site_speed()`). `lib/smelter.py` ore top-up + `lib/fabricator.py`'s `load_inputs()` both cap take with this, plus chunk-size ceilings above (simple per-call cap, not primary fairness). Supply Dock sizes by dispatch rate instead (`load_chunk()`, above; no recipe/duration for prefill window).

#### Smelter demand and dock holds

- **Smelter demand = whole order tree** (`production.get_smelter_demands(cache)` → `{smelter_output: ladder}`, used by `lib/smelter.py` instead of `get_material_demands()`). `get_material_demands()` only sees ingot demand through each Fabricator's *currently selected* recipe (per-worker split, each share netted vs full stock separately), and `_cascade_fabricator_output_demand()` stops at Smelter outputs, so it misses the order tree. Gross-then-net-once, level by level (§2a-p): each `fabricator_target_ladders()` entry with a deficit `D` at some level (`ladder_deficits()` against `network_have()`) adds `D × ratio` per recipe input that is Smelter output, at that level's prio; a target set directly on a Smelter output (the key unlock look-ahead, a dock order `fabricator_root_targets()` already folded in) counts as-is, level by level; dock orders for Smelter outputs not in the targets are added at the order's prio; then each output's ladder is lowered once by `SourceCache.network_have()` (stock, every Fabricator's stockpile, Smelter output not yet in storage; stock covers the highest levels first). `site_smelter_demands()` also takes the site's `pipeline_units()` off its net.
- **Raw ore owed to dock never smelted**: `production.dock_remaining_requirements(outpost_id)`
  (`required − shipped − dock.count()` per item, active orders held by a dock at that outpost, `_dock_order_sites()`; an order held at several outposts counts only that outpost's share, `dock_order_site_shares()` = the remainder split by docks per site (`split_units()`); no `outpost_id` = every order) subtracted from local stock in `SmelterController.available_ore()` with the Smelter's own `site_id()` (home is no special case) — needed since real ingot demand can eat every unit. The hold is priority-aware (`SmelterController.dock_holds()` / `dock_held()`): it binds only demand whose prio is ≤ the owing order's (`production_docks.dock_owed_prios()`); a higher demand (MANUAL, BUILD, BLOCKER) refines that ore anyway.
- **Fab-site ingot buffer** (`production.fab_site_ingot_targets(outpost, cache)`): every outpost with a Fabricator keeps each Smelter output some Fabricator recipe takes as input, at `(target, need)` from `production.ingot_stock_levels()` (archive `production.ingot_stock_targets`, target default `storage.default_stock_target()` (unseeded before Warehouse research; seeded after, with `INGOT_STOCK_NEED = 100` per item, then editable; values in §2d `ore_stock_target()`)). Smelter side: `site_ingot_ladders(outpost, cache)` = `[[NEED, need], [STOCK, target]]` (`[[STOCK, target]]` when `need` is 0 or ≥ target) lowered by local stock, units in flight here and the site's Smelter `pipeline_units()`, merged per level into the Smelter's one demand map (`SmelterController.demands()` with `get_smelter_demands()` and `site_smelter_demands()`). The buffer's NEED and STOCK levels rank under every order, so a refill never holds up an order, and the buffer needs no idle-time path of its own. Hauler side: `site_supply.ingot_wants()` (§2i-1). Fabricator side: a `load_inputs()` take of a Smelter output that moves 0 units calls `wake_local_smelters()` → `parking_client.wake_for_visit(id, hold=False)` for every parked Smelter at its outpost, at most once per item per `SMELTER_WAKE_THROTTLE_TICKS = 100`.
- **Dock order remainder = one helper, per order**: `production._dock_order_remaining()` → `{order_id: {item_id: required − shipped − Σ dock.count() over every dock serving that order}}`. Every dock-demand site (`get_fabricator_targets()`, `get_material_demands()`, `get_smelter_demands()`, `dock_remaining_requirements()`) reads it. Deduped per order id because several docks can share one order; loaded-but-undispatched units subtracted because they're in neither Inventory nor `shipped`.

#### Smelter ore intake and recipe selection

- **Ore intake caps** (Smelter Step 3, `lib/smelter.py`): take amount =
  `max(0, min(SMELTER_INPUT_CAP − in_buf, SMELTER_LOAD_CHUNK_SIZE, max_ore_for_share − in_buf,
  prefill_cap − in_buf, fair_total − in_buf))`.
  - `share = ceil(demand_qty / workers)` = this Smelter's slice of the demand it works: `demand_qty` = `ladder_level(levels, band(top prio))`, the units wanted at the output's top open band or higher, so a STOCK level never widens the share while an ORDER level is short;
    `max_ore_for_share` converts it to ore units via `(qty * units_per_run + output_count - 1) //
    output_count`.
  - `prefill_cap = craft_prefill_units(recipe, ore, SMELTER_PREFILL_SECONDS)` —
    `SMELTER_PREFILL_SECONDS = 30` (`lib/production_core.py`, with `SMELTER_INPUT_CAP = 50`; both also bound the
    Smelter's `smelter.wants` level for the Drone Depot's direct feed, §2h), split out from the shared `INPUT_PREFILL_SECONDS` so Smelters can
    be tuned alone. At 0.08 h/craft (2 s) that's 15 ore.
  - `workers` = every Smelter on the network holding the recipe (`smelter_recipe_peers(recipe_id)`).
  - **Fair-share cap** (`fair_total`): `(available local ore + Σ input buffers of every Smelter on this
    recipe at the same outpost, this one included) // local_workers`, from
    `production.smelter_recipe_peers(recipe_id, outpost_id)` → `(workers, buffered)` scoped to that
    outpost. Plentiful stock never binds; scarce stock splits evenly among machines sharing it.
- **Recipe selection and switching hysteresis** (`select_needed_ore()`): a Smelter has one demand map, so selection follows the bands (§2a-p). Candidates = demanded, sourceable recipes ranked `(-band, -fine, -units missing)` of the output's top open level (`top_deficit(levels, 0)`). While the current recipe is still demanded + sourceable: (1) a candidate of a higher band **preempts** it once that demand is worth one craft (top-level missing ≥ `output_count`) and its claim is free; (2) otherwise the Smelter keeps the recipe outright if it holds (or can take) the claim; (3) a joiner (peer holds the claim) moves to an *unclaimed* candidate only if that recipe's total demand ≥ `switch_min_demand()` = one `SMELTER_PREFILL_SECONDS` window of output (15 units for a 2 s 1:1 recipe); each switch ejects the buffer and skips a step. Smelter releases the old recipe's claim on switch. The log's `refill` flag marks a top open band of `BUILD_AHEAD` or lower.
- **Join gate** (same function): pile-on joining recipe peer already claims needs
  `demand ≥ switch_min_demand() × (workers after joining)`; else Smelter idles, outcome `demand_covered_by_peers`.
- **One `SourceCache` per Fabricator `step()`** too, built after the output/byproduct drains: `get_fabricator_active_recipe()` runs once and feeds `eject_excess_inputs()`/`load_inputs()`; `choose_recipe(cache)`, `target_reason(item, cache)`, `recipe_depths(cache)`, `blueprint_demand_items(cache)` and `take_item(cache=)` share it.
- **Plan and feed** (`SmelterController._step()`): the Smelter keeps a plan (`_plan`: recipe, ore, demand ladders, dock reserve, `made` = units drained since) and replans (`_replan()`: `demands()`, dock reservation, recipe selection, any switch) only when `plan_due()` says so: no plan yet; plan older than `PLAN_BACKSTOP_TICKS = 1800` (`lib/smelter.py`; demand changes arrive through the record tick, so the backstop is long); a new demand record (`record_tick()` differs from the plan's); the machine's recipe is not the planned one; the planned output's netted demand is spent; the output buffer is full (`>= 50`); or the last step found no ore or left the Smelter idle. The feed path runs every poll: drain output (`made` grows by what was drained), top up ore from the planned demand lowered by `made` (`planned_levels()`), publish wants (`publish_want()`, §2h), idle check. A step builds one `SourceCache`, which the feed path uses for local stock only. `demands()` reads the demand record when one is usable and knows this site (`smelter_demands_from_record()`: the network and site Smelter ladders, the ingot buffer already folded into the site ladders by the publisher, each lowered by the units that reached this site's storage since the record's `have`; one local stock scan, no machine holdings) and walks the tree (`get_smelter_demands()` + `site_smelter_demands()` + `site_ingot_ladders()`) only without one. A machine never publishes the record (DESIGN_HISTORY §2a-q: one that did spent ~1,400 ticks on it and starved). The Fabricator controller follows the same plan/feed split, `PLAN_BACKSTOP_TICKS` in `lib/fabricator.py`.
- `fabricator_target_ladders()`, `get_fabricator_active_recipe()`, `get_material_demands()`,
  `_cascade_blueprint_demand()`, `_cascade_fabricator_output_demand()` all take optional `cache=None` (same behavior without).

### §2a-0-6 Per-site demand and order trees (`lib/production_sites.py`, `lib/site_plan.py`)

A fab site = outpost with ≥ 1 Fabricator (`fab_site_counts(cache)` → `{site_id: Fabricators}`, site id = `claim_site_id()`). Each root target's whole tree builds at the sites planned for it; a site's stock counts only for its own trees.

- **Roots and consumers**: `fabricator_root_targets(cache)` → `(roots, consumers, fabricator_outputs)`: the §2a-1 sources before the intermediate cascade as `{item: ladder}`, plus `{item: {site_id: ladder}}` where each root is consumed (dock order items at the dock's outpost via `_dock_order_sites()`, each site of a shared order its `dock_order_site_shares()` share of the remainder; a blueprint's own `required_item` (`blueprint_required_items()`: pending/paused jobs, minus units aboard vehicles) at `construction_site_id()` = `home` of the latest-reporting `role == "builder"` in `fleet.status`, else home — one Constructor home assumed; everything else at home). Intermediates below a blueprint item are no consumer root. `fabricator_target_ladders()` = roots + cascade.
- **Site targets**: `get_site_fabricator_ladders(site_id, cache)` → `{item: ladder}` (`get_site_fabricator_targets()` = flat totals). Fabricators at home only → `fabricator_target_ladders()` itself. Otherwise per buildable root: `root_deficits()` = the root ladder's levels still short of `network_have()` (`held_stock()` at every outpost, cargo aboard haulers included, so a part on its way home isn't built again, + every Fabricator's pipeline and staged inputs); each level's missing units are split across its planned sites by `split_units()` (by Fabricator count, floor plus remainder, first listed site gets the remainder); the site seed is a ladder of `fab_have()` there + the cumulative shares, each at its level's prio; intermediates cascade from the seed against that site's `fab_have()` only, each level at the prio of the demand it serves. Without a site, `fabricator_target_ladders()` cascades against `fab_have()` at home.
- **Demand record** (archive `production.demand`, one dict, + `production.demand_tick` = its publish tick alone, what a machine reads per poll to see a new record; keys in [archive_ipc.md](archive_ipc.md) §4; `lib/production_demand_record.py`): the production demand picture computed once and shared: the network Fabricator ladders (`fabricator_target_ladders()`), per fab site its targets (`get_site_fabricator_ladders()`), ship plan and `have` (`fab_have()` at publish time), the network Smelter demands and per Smelter site its demands (`site_smelter_demands()` merged with `site_ingot_ladders()`, `smelter_site_record()`) and `have` (`held_stock()` there), the recipe depth map (`recipe_depths()`, `depths`) and the gross construction cascade (`blueprint_demand_items()`, `blueprint`; both the same for every reader, so `recipe_depths()`, `get_construction_material_reservations()` and `dock_delivery_targets()` read them from a usable record through `blueprint_demand_wants()`; the publishers call `compute_recipe_depths()` and the cascade directly), and the `fabricator.site_plan` it was computed under (a record of another plan or `DEMAND_VERSION = 1` is MISSING).
  - **Writers**: the orchestrator's `DemandPublisher` (`lib/demand_publisher.py`), `publish_demand_if_due()` last in `between_steps()`: nothing while `demand_signature()` is unchanged and the last publish is younger than `DEMAND_BACKSTOP_TICKS = 1800`; else a refresh: `prefetch()` (outside any atomic call: the manual-orders and ingot-target seeds, which may write the archive, every outpost's stock scan, which runs its own atomic batches, and the machine holdings in two `run_atomic()` calls), then tasks of one `run_atomic()` call each (`Refresh`: network targets, per site the Fabricator part, the Smelter need and the ingot buffer in batches of `INGOT_CHUNK_ITEMS = 6` Smelter outputs, then finish), as many per call as fit `DEMAND_SLICE_TICKS = 400`; stamped with the tick the refresh began. The atomic calls are switched off (`ATOMIC_TASKS = False`): on the mid-late sample save a task costs up to ~150k steps (Fabricator part of a site), far over the 10,000-step cap, while the synthetic worlds of `devtools/perf/step_profile.py demand_refresh` show ~6.8k opcodes. With the flag off each task logs `demand task <kind> <site> items=<n>: <T> ticks` (debug); T x the census allowance sizes it on a real save. A task that raises is skipped (logged): its site computes locally until the next record. `publish_site_requests()` (§2i-1) publishes for free from its already-warm `SourceCache` (`publish_from_cache()`, same gate). A record stamped later than the publisher's `now` is kept. Machines never write it.
  - **Reader rule** (`get_site_fabricator_ladders(site_id, cache, reuse=True)`; age = now - record tick; `DEMAND_FRESH_TICKS = 600`, `DEMAND_MAX_STALE_TICKS = 5000`, kept ≥ `DEMAND_BACKSTOP_TICKS` + the longest round + margin since the record is stamped at round start; FRESH and STALE differ only in the log line):

    | State | Result |
    |---|---|
    | FRESH or STALE (age up to `DEMAND_MAX_STALE_TICKS`), site in record | use the entry (netted, ship plan taken over) |
    | MISSING (none, other version or plan, older than `DEMAND_MAX_STALE_TICKS`) | compute locally |
    | site absent from the record, `reuse=False` or no clock tick | compute locally |
  - **Netting** (`_net_consumed()`): a ladder is "keep at least N" with the site's stock and pipeline inside it, while a reader nets live stock, so a unit consumed since publish (a finished craft sent into a Supply Dock) would be crafted again. A reader lowers every site ladder, root or intermediate, by `have` then - `fab_have()` now (`ladder_lower()`): a drained intermediate (sent into a dock or a parent's stockpile) comes off until the next record, while a staged input still counts, since `have` is `fab_have()` (held + pipeline + staged). It never raises one: a rise (units hauled in) also changes the remaining, which only a recompute sees. Smelters net the same way by units made locally since `have` (`smelter_demands_from_record()`). `get_site_ship_plan()` still always computes: reserved hauls must come off at once.
- **Ship-before-craft** (`ship_units()`, `SHIP_OVER_CRAFT_SECONDS = 300`, `SHIP_SURPLUS_FACTOR = 10`): during that cascade each non-root item short at the site is first covered by units in flight to it (`logistics_requests.in_flight()`), then by shipping when spare elsewhere (`site_spare_elsewhere()`: other outposts' `outpost_free_tiers()` NEED-band free stock, minus what another fab site keeps for its own targets, `_site_base_targets()` = the same cascade without shipping) is > 0 and either spare ≥ `SHIP_SURPLUS_FACTOR` × shortfall, or `local_make_seconds()` is `None` (no Fabricator/Smelter of that kind at the site, or a missing input no recipe makes) or ≥ `SHIP_OVER_CRAFT_SECONDS`. `local_make_seconds()` = crafts × `craft_seconds()` plus making each locally short input the same way (fluids count as available, one machine's time, depth 6). Delivery time is not estimated. Covered units come off the item's target and are not cascaded into its inputs; the ship part is the site's ship plan (`get_site_ship_plan()` → `{item: [units, prio]}`, prio = the top shortfall level the units serve), requested by §2i-1. Roots are never shipped (§2i-1 consumer site moves them).
- **Plan**: archive `fabricator.site_plan` (`production.SITE_PLAN_KEY`) = `{root_item: [site_id, ...]}`, written by `site_plan.plan_sites()` once per storage tick in headless `orchestrator_automation.py`, only on change. Unplanned roots fall back to `default_root_sites()` (consuming fab site, else home, else first fab site). New root: `min(fab sites, max(1, remaining // SPLIT_UNITS_PER_SITE))` sites, `SPLIT_UNITS_PER_SITE = 20`, ordered by most consumed there, least loaded (planned roots per Fabricator), home, id. Sticky while it has units left; dead sites dropped, replanned once none remain; entry removed once built; cleared when only home has Fabricators.
- **Hauling finished roots**: §2i-1 consumer site.

### §2l Cash Manager (`lib/cash.py`, headless `orchestrator_automation.py`, CASH card `cash_panel.py`)

One budget owner for every Shop purchase. State in one archive dict `cash.budget` (§4).

- **Consumers** call `cash.can_spend(consumer, cost, planned=, label=)` right before a buy and `cash.spent(consumer, amount)` after it (`cash.release(consumer)` when a buy fails or nothing is wanted any more). `spent()` keeps the ask with `planned − max(amount, cost)` while that is > 0; `cash.keep(consumer)` refreshes an existing ask without a grant (`BuildingSwapUpgrader.step()` calls it every pass while a swap runs), so the rest of an order stays the savings goal between buys. Ids are `<kind>` or `<kind>:<instance>`; priority and operating status match on the kind.

  | Kind | Where | Class |
  | :--- | :--- | :--- |
  | `bio_reagents:<lab>` | `bio.py` BioLabController, home Shop buy of missing reagents | operating |
  | `pioneer_reagents:<pioneer>` | `vehicle_cargo.py` `_buy_and_take()` (remote-home hauler Shop pulls, §2i) | operating |
  | `drone_reagents:<drone>` | `drone_hauler.py` `buy_at_shop()` (hauler drone Shop pickups, drones.md §2j) | operating |
  | `crop_automator` | `harvester_machines.py` `buy_automator_kit()`, planned = wanted × price | capital |
  | `bin_upgrade` | `warehouse_upgrade.py` `BinUpgrader` (§2k-1) | capital |
  | `warehouse_upgrade` | `warehouse_upgrade.py` (§2k-1) | capital |
  | `storage_expand` | `storage_expand.py` (§2k-5), planned = one kit per storage outpost short of slots | capital |
  | `pioneer_commission` | `fleet_commission.py` `_buy_missing()` (§2k-2), planned = cost × (1 + queued jobs) | capital |
  | `pioneer_refit` | `fleet_commission.py` `_buy_missing()` for a refit job's missing parts (`cash_kind()`, fleet_lifecycle.md §2f-1) | reserved capital |
  | `drone_commission` | `fleet_commission.py` crafting state: drone parts only the Shop sells (`spec["buy"]`, e.g. the miner's Portable Bio Extractor), §2k-2 | capital |
  | `tank_upgrade` | `tank_upgrade.py` (§2k-3) | capital |
  | `pioneer_upgrade:<pioneer>` | `pioneer_upgrade.py` auto tier upgrades (§2b-1); manual Sport Nav stays a plain affordability check | capital |

- **Decision** (`decide()`, live inside one `archive.transaction()`): `free = balance − other consumers' holds − floor`; deny if `cost > free`. Operating kinds (`OPERATING`) use floor 0 and skip the goal check: reagents come before everything. Capital kinds also leave the **reserve** `RESERVE_FLOOR = 5000` (`capital_floor()`: `max(floor, RESERVE_FLOOR)`), except reserved kinds (`RESERVED`: `pioneer_refit`), which use the floor alone and skip the savings goal: a refit Pioneer stands stripped until its parts arrive. Capital kinds use the floor, then the **savings goal**: the highest-priority other capital ask ranked above this one that holds nothing yet; deny if `cost + goal planned total > free` unless `cost ≤ SMALL_RATIO = 0.10` × goal's next cost. A grant sets a hold of `cost` for `HOLD_TICKS = 600`; every call refreshes the consumer's ask (dropped after `ASK_STALE_TICKS = 3000`). Only cash on hand is granted, never forecast income.
- **Priority**: `cash.budget["priority"]`, reordered with the CASH card's top/^/v/bottom buttons (act on the selected list row); default `DEFAULT_PRIORITY = [crop_automator, storage_expand, bin_upgrade, warehouse_upgrade, pioneer_commission, drone_commission, tank_upgrade, pioneer_upgrade]`; a stored list without a newer default kind gets it appended. Unknown kinds rank last.
- **Floor** = `max(MIN_FLOOR = 1000, operating burn/h × FLOOR_HOURS = 12)`. With no manager pass for `MANAGER_STALE_TICKS = 1200` (panel down, or tier < 4), capital kinds use `LEGACY_RESERVE = 100000` instead.
- **Manager pass** (`CashManager.step()`, first thing each `orchestrator_automation.py` storage pass): balance sample every `HISTORY_STEP_H = 0.25` game h into `history`, kept `INCOME_WINDOW_H = 24` h; spend log (`spent`, ≤ `SPEND_LOG_LEN = 200`). Gross income/h = (balance change + logged spend) / span, burn/h = operating spend / span, both `None` below `MIN_RATE_SPAN_H = 1` h. Sales (kit resale) count as income. `pipeline`: campaign reward still to earn (`reward × unshipped fraction`), already-shipped share, weekly board remainder; shown only. `queue`: every ask, operating first then by priority, with `eta_h` = cumulative unheld cost + floor − balance over income/h (`None` without an income rate); `planned` = sum of planned totals.

### §2m Early Build Order (`lib/early_buyer.py`, headless `orchestrator_automation.py`)

Plays the base build order from the lib tier (Data Archive, 70k TP) until the Control Room (150k TP). Before that, tier-0 `power/solar.py` plays the same order from Ship Computer (10k TP). `EarlyBuyer.step()` runs from `between_steps()`, once per `EVAL_TICKS = 50` (~5 s); info status line at most every `HEARTBEAT_TICKS = 200`.

- **Build order** (`STAGES`, from the headless build-order search, [early_optimization.md](../autoplay/early_optimization.md)): O2 to 2.2 ppt → heat to 12 HU → O2 to 10 ppt → pressure to 1.2 kPa → pressure tail (`TAIL_STAGE`). The first stage with an unmet target is active. Each pass sells the other pillars' generators (and stray kits in Inventory), keeps `POWER_KEEP` (3 batteries, 6 solar; `TAIL_POWER_KEEP` 5/10 in the tail; one filler generator is sold for each missing power building with no free slot), then fills every free base slot with the active pillar's generator, one buy at a time. A fresh deploy is switched on once; breakers are otherwise PowerGridManager's (§1a).
- **Pressure Mk II tail** (from 1.2 kPa, `MK2_RESEARCH` unlocked): once the tail's power counts stand, buys `MK2_PACK` one at a time and applies it with `computer.upgrade()` to every Pressure Generator below Mk II (`tier()`). The build order fixes the count: with 15 power buildings, the Charging Station and the Bio-Loop, 6 generators are left. A refused buy or upgrade ends the pass.
- **Charging Station** (Charging Station researched): bought with the Rovers (wanted count above 0, Rover + Deep Extraction researched) or a Pioneer (due and buildable, below), whichever is ready first, so a missing Drill Module research never holds back the scout; with no free slot one filler generator is sold for it.
- **Rovers**: `ROVERS = 0` by default: a Rover mines only H1 ore and arrives close to the scouts ([unlock_paths.md](../gameknowledge/unlock_paths.md)); the archive's `rovers` asks for some. That many chassis once a station stands. `ROVER_GEAR` (nav, sonar, drill) bought into Inventory for each Rover lacking that kind at any tier; a buy refused with `inventory_full` first sells (else drops) the largest ore, else ingot, stack. Each Rover mounts its own gear at start (`lib/rover.py` `fit_rover_loadout()`, `ROVER_LOADOUT`, `LoadoutFittingMixin` §2k-2).
- **Pioneers**: at `PIONEER_TP = 100000`, one job per evaluation on the commission queue (§2k-2) for the first role of `pioneer_order()` that queued jobs plus deployed Pioneers don't cover: `SCOUTS = 3` `scout`, then `CONSTRUCTORS = 1` `builder` (so an outpost can be founded before the Control Room). A deployed Pioneer counts as `constructor` with `constructor_module` mounted, else as `scout`; one still being fitted counts as its job. A role is queued only once `build_spec()` can build its whole preset (a blocked job needs the FLEET card's Commission tab to cancel, which doesn't exist yet); a locked role is skipped for the next one. Spare scouts are retired later (TODO.md, manual-run item E). The coordinator buys through the cash manager (§2l), so it waits for the floor.
- **State** `early_buyer` (archive dict): `done` (Control Room researched; idle for good), `generators` (default True), `rovers` (default `ROVERS`), `pioneer` (default True), `scouts` (default `SCOUTS`), `constructors` (default `CONSTRUCTORS`). The headless build-order search sets `generators` False: its plan places the buildings (`run.mjs --lib-tier --policy`, §10b).
