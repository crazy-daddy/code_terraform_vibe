# Fabricator Demand, Priority Bands & Order Planning (§2a-0-5, §2a-p, §2a-1…§2a-3)

Part of [`AI_CHEATSHEET.md`](../AI_CHEATSHEET.md). Production core, Supply Dock draining and multi-fabricator support (§2a-0…§2a-0-4) live in [`production_logistics.md`](production_logistics.md).

### §2a-0-5 Multi-Dock order planning & weekly-deadline feasibility (`lib/supply_dock.py`)

Central planner `plan_dock_assignments(clock=None)` runs **once** per cycle from orchestrator_automation.py's AUTOMATION section (checked every `DOCK_PLAN_TICK_INTERVAL = 50` ticks, ~5 s, ahead of the storage pass's feeder-bound sweeps; replans only when `plan_signature()` changed or `DOCK_PLAN_MAX_TICK_INTERVAL = 600` ticks passed, see `docs/cheatsheet/panels.md`), not each dock re-scanning full Earth Order board every cycle. `set_order()`/`clear_order()`/
`set_enabled()` all `*(self only)*` hardware calls, so planner only decides — writes `{dock_id: order_id or None}` to `"supply_dock.order_plan"` archive key (`ORDER_PLAN_ARCHIVE_KEY`); each dock's `SupplyDockController.step()` reads its entry via `desired_order_id()` and does actual `set_order()` itself.

- **Campaign score** (`_score_campaign_order()`): 10, +50 for a recipe/tech unlock, + readiness share × `CAMPAIGN_READINESS_WEIGHT = 30`; key unlock orders `EARLY_UNLOCK_ORDER_IDS` (75 ids: `helios_01`, `vestibule_01`, `helios_02`, `spire_intake_2` = Titanium Ingot > Power Line > Gas Pipe > Liquid Pipe Segment, Power Line needs Titanium Ingot; then the electric drone path `spire_intake_3` … `helios_09`, `spire_09`, `spire_10`, interleaved by dependency, unlock_paths.md "Drone path"; then `helios_10` … `helios_25` up to the Heavy Mining Drill, "Helios after the drone path"; then `spire_11` … `spire_18` (Yield Amplifier) and `vestibule_02` … `vestibule_15` (Heli Thruster, Oil Tanks up to Large), "Yield Amplifier and heli path"; then `helios_26` … `helios_28` (Lead Cask) and `vestibule_16` … `vestibule_28` (Shield Plating, Fuel Rod), "Nuclear path") add `EARLY_UNLOCK_STEP = 31` × (75 … 1) (`early_unlock_weight()`), so readiness never reorders them; + the look-ahead bonus below. Weekly: 5 + readiness share × 20. **Order prio** (`_order_prio()`): `priority.order_prio(score, override, ORDER_SCORE_MAX)` = `ORDER + score × 99 // ORDER_SCORE_MAX` (`ORDER_SCORE_MAX` = the largest possible campaign score, so the fine value spans the ORDER band), or the operator's override (any 0-999, so an order can sit in the MANUAL band or under the stock buffers; ORDERS card, `set_order_override()`). `publish_order_prios()` writes `{order_id: prio}` of every candidate to archive `supply_dock.order_prio` (read by the demand tree through `production_docks.dock_order_prios()`; an order without an entry ranks at `ORDER`) and drops `supply_dock.priority_override` entries of orders that are no candidate any more. `order_rows()` feeds the ORDERS card: every active campaign and weekly order with `prio`, band name, override, the docks the plan assigns it and the units still owed, highest `prio` first.
- **Stability**: dock holding still-`can_fulfill_order()`-true order keeps it regardless of ranking — mid-shipment order not cleared over a marginal `prio` difference. The held order also drives Fabricator demand (`production._all_dock_orders()`), so a dock never drops an order just because nothing is stocked yet. One exception, the **local cask rule**: an empty dock (`total() == 0`) whose outpost's Lead Casks hold still-owed hot units of another candidate order (`_cask_order_ids()` / `_local_cask_units()`) leaves its order for that one. The dock applies it only for a central plan entry (`plan_assigned`); the per-dock fallback never moves a dock off a fulfillable order.
- **Idle dock ranking: key unlocks, then local stock, then spread inside the outpost, then `prio`**: candidates the dock's site serves (Dock site roles below) re-sorted before each idle-dock assignment by `(not shippable from a local cask, not a key unlock order, local stock rank descending, docks at the same outpost on this order ascending, role share descending, `prio` descending, docks on this order network-wide ascending, dock-site affinity descending)`. Local stock rank (`_local_supply()`) = still-owed units the dock's outpost holds unpromised, in `LOCAL_STOCK_STEPS = 10` steps of the order; unpromised = less Construction Blueprint reservations (home only, like loading) and less units that docks already planned this pass at the same outpost claimed (`_promise()`). A weekly order ranks on local stock only when fully covered (a partly shipped weekly order expires unfinished). So across outposts a dock joins an order its site already stocks, or else the higher-`prio` one; inside one outpost docks spread across orders. `pick_best_order()` sorts the same way without the spread counts or promises. Affinity (`_dock_affinity()`) = still-owed units already stocked at the dock's outpost + 1 per item whose tree `fabricator.site_plan` builds there; tie-break only. Local stock, affinity and readiness all count `SourceCache.held_stock()` (Warehouses, Drone Depots, home Inventory), the same count Fabricator netting uses, so dock and Fabricator agree on "enough"; `pick_best_order()` builds one `SourceCache` for the pass. Scored per idle dock before the sort (a remote outpost's first `held_stock()` reads its Warehouses and Depots), so the sort key only reads a dict.
- **Dock site roles** (`DockRoles`, one per pass): the buildings at a dock's outpost decide which order items it ships itself. Fabricator → crafted items (Fabricator recipe outputs, `ROLE_FAB`); Smelter → every raw ore and Smelter output, a stationed miner there that reaches the ore (`outpost_mining.mineable_ores_by_outpost()`) → that ore (`ROLE_MINE`); Lead Cask → `lead_cask.HOT_ITEMS` (`ROLE_CASK`). An item with none of these kinds counts as covered everywhere; an unresolvable site covers everything. A dock takes an order (planner and `pick_best_order()`) only when the order has no role-bound still-owed item or the dock covers at least one; the sort ranks the covered share (`share()`) after the spread count and before `prio`. The rest of a mixed order reaches the dock's outpost as a site-supply consumer request (§2i-1). Stability exception: an empty dock leaves a held order it covers nothing of; the plan entry is then another order or `None`, and `step()` clears the order (`plan_assigned` only). A loaded dock keeps it.
- **Docks at any outpost**: `discover_supply_dock_ids()` is network-wide. Off home a dock connects to a local Warehouse (`local_port_target()`, none → one warn), loads from local stock only (`SourceCache.local_stock()`, `take_item(outpost=)`, no blueprint reservation) and drains to a local Warehouse. Its order items are consumed at its outpost (§2a-0-6), so their trees build there and §2i-1 hauls in the rest.
- **Weekly-deadline feasibility**: `_weekly_infeasible(order, current_day, dispatch_capacity_per_hour)` skips Weekly Earth Order entirely when `remaining_units > dispatch_capacity_per_hour *
  hours_remaining` (`hours_remaining = (order.expires_day - current_day) * 24`) — i.e. even shipping flat-out with all known docks' combined `dispatch_rate()`, remainder can't leave before `expires_day`. Dispatch-capacity ceiling only (not production-rate forecast — upstream recipe throughput/worker counts/deficits = later TODO). Returns `False` (don't block) when needed input missing. Campaign orders (no `expires_day`) unaffected.
- **Stale entries**: plan can name an order that completed after it was written. `desired_order_id()` checks the entry with `orders.get_order()` (`order_is_active()`); not `"active"` → falls back to `pick_best_order()` instead of calling `set_order()` on it. A `set_order()` result `"completed"`/`"unknown_order"` is logged at debug, not warn.
- **Console**: standby and shipping lines print only when the dock's state changes (`report()`), not every `poll_interval`.
- **Fallback**: `SupplyDockController.desired_order_id()` uses archive plan when this dock's id present, else own weekly-feasibility-aware `pick_best_order()` — soft fallback (unlike Solar/Smelter hard dependency in §1a-1).
- **Hot cargo** (Raw Uranium, Fuel Rods, `lead_cask.HOT_ITEMS`): an order needing one goes only to a dock whose outpost has a Lead Cask (`_servable_at()`, planner and `pick_best_order()`); the dock loads it from that outpost's casks (`lead_cask.take_from_casks()`), affinity counts cask stock, and leftovers eject to a cask (`lead_cask.unload_target()`). Sourceability (`production.can_source_item()`): a hot item in any cask, Raw Uranium with a live uranium site in `weather.aftermaths`, Fuel Rods / Nuclear Batteries via the first Fuel Assembler's unlocked recipes (`SourceCache.fuel_assembler_recipes()`; the recipe index and Fabricator cascades stay Fabricator/Smelter-only). Readiness (`_order_readiness()`) counts hot items from Lead Casks network-wide (`SourceCache.cask_stock()`, fallback `lead_cask.network_cask_stock()`).
- **Shared scoring**: `_score_campaign_order()`/`_score_weekly_order()`/`_order_readiness()` module-level, used by planner + per-instance fallback — no ranking drift. `_order_readiness(order, reserved, stock)` takes `held_stock` of the pass's `SourceCache` (a fresh one when None).
- **Key unlock orders** (`EARLY_UNLOCK_ORDER_IDS`, `key_unlock_bonus()`): unlock path in [docs/gameknowledge/unlock_paths.md](../gameknowledge/unlock_paths.md). A current campaign order that is not itself a key order adds the weight of the nearest key order behind it in its contractor's queue (`orders.list_upcoming_orders()`) divided by 1 + the orders in front of that one, so `spire_intake_1` earns half of `spire_intake_2`'s. Key orders sort right after the local-cask rule, before local stock and the spread count, but only while they rush (`_key_rush()`): no dock holds the order yet (one dock drives its production chain, `production_docks._all_dock_orders()`), or the dock's outpost holds unpromised stock of it (`_local_supply()` rank > 0). So the first idle dock that serves a key order takes it, and further docks work other orders instead of waiting on the same chain. An empty dock (stability exception, central plan only) leaves a non-key order for a key order it serves and that still rushes (no other dock holds it, or local stock; `_key_order_ids()`). A loaded dock keeps its order. A key order with no known source (`can_fulfill_order()`) is no candidate at all. **Key unlock look-ahead** (`publish_key_ahead()`, each `plan_dock_assignments()` pass that reads the board): production only follows orders a dock holds, so the first key order in each contractor's upcoming queue (`next_key_orders()`) is stocked ahead. `key_ahead_items()` splits its still-owed items into Fabricator outputs of an unlocked recipe and Smelter outputs; both go into one `fabricator.orders` entry (requester `"key_unlock_ahead"`, `supply_dock.KEY_AHEAD_REQUESTER`) at the `ORDER_AHEAD` band, which Fabricators and Smelters work only when nothing of a higher band is open. Its Fabricator inputs (e.g. ingots for Machine Frames) reach `get_smelter_demands()` at the same band through the cascade. Raw items and items no unlocked recipe makes are left out. Nothing reserves the stock: other orders may use it and the floor refills. `pick_best_order()` (lone dock) ranks every key order first.

### §2a-p Priority bands (`lib/priority.py`)

One integer 0-999 ranks every demand on the network, from an Earth order or blueprint down to the ore it needs. The hundreds digit is the **band**, the rest a **fine** value (0-99). Rationale: [DESIGN_HISTORY.md §2a-p](../DESIGN_HISTORY.md).

| Const | Value | Meaning | Written by |
| :--- | :--- | :--- | :--- |
| `BLOCKER` | 900 | operations stalled: a settled part a job waits on, nothing more arrives by waiting (hauling only: haulers skip their minimum load) | `site_supply`: `settled_items()`, manual-order units built off home, stragglers (§2i-1) |
| `MANUAL` | 800 | the operator asked | `fabricator.manual_orders`; blueprints the operator placed (fine 99); an ORDERS-card override; a drone's own module order (`drone_<n>`: fitting, upkeep, heli conversion) |
| `BUILD` | 700 | autoplay construction blocking progress now | blueprints of autoplay jobs at `construction.priority` 0 (fine 99) |
| `ORDER` | 600 | current Earth orders a Supply Dock holds; fine = dock score | `supply_dock.publish_order_prios()` |
| `UPGRADE` | 500 | one-off parts a job waits on | `fabricator.orders`: fleet upgrade, field machines, Bio Caster delivery, commission, drone kit stock (the Fuel Assembler's plates at `UPGRADE + 90`) |
| `NEED` | 400 | a machine or role cannot run without it | need levels of the stock tables (ingot buffer, site stock, construction stock), Plant Terraformer batches, Yield Amplifier doses; stranded goods evicted to a user |
| `BUILD_AHEAD` | 300 | plan-ahead construction | blueprints at `construction.priority` k ≥ 1 (`300 + max(0, 99 − 10 (k − 1))`) |
| `ORDER_AHEAD` | 200 | the next key unlock orders | `supply_dock.publish_key_ahead()` |
| `STOCK` | 100 | buffers | buffer targets (ingots, site stock, construction stock, `ore_stock_target()`), Terraformer/Amplifier/Bio Caster backlog |

- **Ladder** = `[[prio, cum_units], ...]`, prio descending, cum non-decreasing: at least `cum` units should exist; the units up to the first level are wanted at its prio, the next ones at the next level's. 1-4 levels. It is the one demand shape: Fabricator targets (`fabricator_target_ladders()`), Smelter demands (`get_smelter_demands()`), site wants and request entries (`levels`). Helpers: `ladder_deficits(levels, arriving)` → `[(prio, missing)]`, `top_deficit()`, `band_deficits()`, `ladder_raise()` (max-fold: root floors of one item), `ladder_add()` (sum-fold: cascade contributions of several parents), `ladder_max()`, `ladder_lower()`, `ladder_promote()` (levels of band ≥ a minimum moved to one prio: settled parts → `BLOCKER`), `from_levels(target, need)`.
- **Three rules.** (1) Bands are lexicographic: a unit of a higher band always goes first, however big the load of a lower one. (2) The fine value breaks ties only inside a machine or dock (Fabricator `choose_recipe()`, Smelter selection, the dock planner); haulers and miners rank by band only. (3) Stock covers the highest level first (`ladder_deficits()`, `ladder_lower()`), so a stock top-up never rides on an order's prio; child demand inherits each parent level's prio.
- **`FAIR_BANDS = (BUILD_AHEAD, ORDER_AHEAD, STOCK)`**: deficits of these bands are split between competing outposts in proportion to their deficits (`fair_share_tiers()`, §2i); higher bands are served in full.
- **Archive keys** ([archive_ipc.md](archive_ipc.md) §4): `fabricator.orders` = `{requester: {item: [[units, prio], ...]}}` (§2a-1 item 4); `supply_dock.order_prio` = `{order_id: prio}` and `supply_dock.priority_override` = `{order_id: prio}` (§2a-0-5); `logistics.requests` entry = `{"levels": ladder, "have", "by", "tick", "buy"?, "keep"?}` (§2i); `fabricator.wants` values `[units, prio]` and `smelter.wants` entries with `prio` (Smelter → Fabricator and Depot → Smelter pushes go to the most urgent want first); `production.demand` / `production.demand_tick` hold the demand record (§2a-0-6).
- **Planner cost**: the route planners loop all nine bands per item (`ROUTE_COST_PER_SOURCE`/`ROUTE_COST_PER_ITEM`, [vehicles_drones.md](drones.md) §2j).

### §2a-1 Fabricator demand tracking (`lib/production_cascade.py` `fabricator_target_ladders()`)

Single source of truth for what Fabricator builds, feeds `get_material_demands()`. Ore demand comes from the site supply ore requests (§2i-1), home included. Four demand sources folded into one `{item_id: ladder}` map (§2a-p; `fabricator_target_ladders()`, `get_fabricator_targets()` = the flat totals), then cascaded into Fabricator-built inputs (`_cascade_fabricator_output_demand()`): each level of a parent's shortfall (`ladder_deficits()`) cascades at its own prio, so an intermediate inherits the band of the demand it serves, contributions of several parents sum, root floors of one item max-fold. An item whose recipe has an input with no source (none on the network and `can_source_item()` false, e.g. a still-locked Pressure Valve under Pipe Bridges) is not cascaded, so its other inputs are not built to sit stranded. No standing Fabricator stock table: standing stock is requested per site (§2i-1 stockpiles and construction stock) and reaches the Fabricators as `fabricator.orders` entries.

1. Active Supply Dock order's `requires`, for items Fabricator can build at the order's prio (`supply_dock.order_prio`, §2a-0-5; `max()`'d vs other sources, not summed), plus the reserve at the Constructor's home (`builder_reserve()`: units held there of each request entry with a `keep`, capped at that keep): a dock order builds its own units instead of counting the construction stock.
2. **Pending/paused Construction Blueprints**, via `_cascade_blueprint_demand()` (§2a-0-1), each job's units at `priority.blueprint_prio()`: `MANUAL` + 99 for a blueprint the operator placed (not in `autoplay.planned`), `BUILD` + 99 for an autoplay job at `construction.priority` 0, `BUILD_AHEAD` + `max(0, 99 − 10 (k − 1))` for plan-ahead priority k ≥ 1 (`blueprint_prios()` reads both archive keys once per pass; `blueprint_required_ladders()` seeds the walk); `max()`'d vs existing target — not summed (targets = steady-state floor, not additive per source).
3. **`fabricator.manual_orders`** archive key (`{item_id: quantity}`, e.g. `{"drone_small": 2}`) — ad-hoc build requests, edited directly (no default seeded). Quantity = units still to build, not a stock floor: folds into target as `network_stock() + quantity` (`max()`'d with other sources; `get_manual_order_blocking_items()` seeds the same way), so units already built never satisfy the rest. At the `MANUAL` band, so it outranks every Earth order, fleet part and buffer in `choose_recipe()`; the intermediates it is stuck on inherit `MANUAL` through the cascade and sort first by recipe depth. Counted down (dropped at 0) by `production.consume_manual_order()`, called from `drain_output()` with qty actually drained. Units drained off home move to archive `fabricator.manual_transit` (`{item: {"units", "base"}}`, base = home stock then): `fabricator_root_targets()` keeps `base + units` as the item's home consumer want at `BLOCKER` (no build target; nothing more arrives by waiting), so §2i-1 hauls them home at once; `reconcile_manual_transit()` drops the entry once home stock reaches `base + units` or no unit is left off home (`network_stock() - stock()`). Key must exactly match recipe's `output_item` (hand-typed, no write validation) — `get_fabricator_targets()` prints one-time warning (per-script-run, `_WARNED_UNKNOWN_MANUAL_ITEMS`) when key doesn't match default Fabricator's unlocked recipe outputs (heads-up only, can false-positive for other Fabricator or not-yet-unlocked recipe).

4. **`fabricator.orders`** archive key (`lib/production_orders.py`) — the orders book `{requester_id: {item_id: [[units, prio], ...]}}` (a single `[units, prio]` pair is accepted), written only by code through `production.set_order(requester, items)`; `order_levels(need, need_prio=UPGRADE, stock, stock_prio=STOCK)` builds one item's pairs (a need floor at one prio, a stock buffer at a lower one). `units` is a "keep at least this many" floor. Floors of one item are summed per prio across requesters and accumulated down the prios into a ladder (`order_ladders()`), `max()`'d into the target. Requesters and their bands: the fleet upgrade coordinator (`"fleet_upgrade"`, Depot kits/chassis), each drone (its own id: better Cargo Pods/Oil Tanks/missing loadout modules), the planting Harvester (`"field_keeper"`, field-machine kits, §1k), the Bio Caster (`"bio_caster"`: forge materials for the current Volcanic delivery at `UPGRADE`, those of every open Volcanic order up to that at `STOCK`, §1g), the COMMISSION coordinator (`"fleet_commission"`, the kit of the drone job being crafted at the job's band: `MANUAL` for a card click, `BUILD` for autobuild; the kits of the drone jobs queued behind it at `UPGRADE`, fleet_lifecycle.md §2k-2) and the drone kit stock (`"drone_kit_stock"`, `lib/drone_kit_stock.py`: once its recipe is unlocked, 1 Depot kit of the first unlocked tier and 1 Service Station kit while some outpost has none of that building; written each `plan_dock_assignments()` pass; the building planner deploys them) all at `UPGRADE`; the Fuel Assemblers (`"fuel_assembler"`, Lead Plates for the next crafts, `UPGRADE + 90`, §1n); the Plant Terraformers (`"plant_terraformer"`: next `NEED_CYCLES` batches of Fertilizer/Growth Accelerant at `NEED`, a 24 h buffer at `STOCK`, §1k) and the planting Harvester's Yield Amplifier (`"field_amplifier"`: doses at `NEED`, buffer at `STOCK`, §1k); the crafted site stockpiles (`"site_stock"`) and the construction stock (`"construction_stock"`): need levels at `NEED`, the rest up to the target at `STOCK` (§2i-1); the next key unlock orders' items (`"key_unlock_ahead"`, `ORDER_AHEAD`, §2a-0-5); the machine tier packs (`"machine_upgrade"`, `UPGRADE`, §2k-6). Each requester replaces/clears only its own entry; entries of drones that no longer exist are pruned by `FleetUpgradeCoordinator._prune()`; non-drone requesters must be listed in `production.STANDING_ORDER_REQUESTERS = ("field_keeper", "bio_caster", "fleet_commission", "plant_terraformer", "fuel_assembler", "field_amplifier", "site_stock", "construction_stock", "drone_kit_stock", "key_unlock_ahead", "machine_upgrade")` or they get pruned too. `"bio_caster"`, `"fuel_assembler"` and `"plant_terraformer"` are shared type-level requesters, so undeploying one machine can't clear them: they write a heartbeat entry (`set_order(stale_ticks=ORDER_STALE_TICKS)`, archive_ipc.md `fabricator.orders`) on every poll, and it lapses once no machine of that type republishes it. Site orders (`production.SITE_ORDER_REQUESTERS = ("site_stock", "construction_stock", "bio_caster", "plant_terraformer")`) raise the Fabricator target only; their sites request the items, so home is no consumer. A requester passing `set_order(..., site=)` is consumed at that outpost (`"@site"`, `order_consumer_sites()`), or nowhere for `NO_CONSUMER_SITE`; every other requester at home. `"key_unlock_ahead"` names `supply_dock.key_ahead_site()`: the dock outpost covering most of the orders' role-bound items (`DockRoles`), then most docks, then lowest id, so the items wait where `_local_supply()` pulls the order. See §2k.

`choose_recipe()` ranking (§2a-p): candidates are the recipes whose output has a site ladder (`get_site_fabricator_ladders()`) still short of `held_stock()` + pipeline + staged units. Each carries `(prio, missing)` = `top_deficit(levels, have)`, the highest level still short and the units missing at it, so a target's lower levels never lift it (a `STOCK` top-up of an item with an open order ranks by the order's units only). Sort key `(-band(prio), -depth, -fine(prio), -missing)`: the band first (a manual order before an Earth order before a buffer), then the deeper recipe inside one band (`production.recipe_depths(cache)`: a root target is depth 0, an input of a depth-d item d + 1, the deepest parent counts, so an intermediate its parent cannot be built without comes first; this also covers inputs a manual order or a fleet part is blocked on, which inherit the band through the cascade), then the fine prio (dock score, blueprint priority), then the units missing. Fluid-paused, unsourceable and foreign-claimed recipes are skipped (candidates are claimed in rank order, next on claim fail). **Sticky recipe** (hysteresis per band): the current recipe stays while it is still short, sourceable, claimable and not `starved()`, and no sourceable candidate of a higher band exists; depth and fine prio never switch it (a switch ejects the staged inputs, `eject_excess_inputs()`, and reloads: two feeder trips per unit). `starved(recipe, cache, site_id)` = some input has less than one craft in `local_stock()` and nothing in flight to the site; a starved current recipe gives way to a same-band candidate that can run now. `target_reason(item)` names the band of the item's top open level (the Supply Dock order for an `ORDER` one). `load_inputs()` publishes the units it could not take to `fabricator.wants` as `[units, prio]` (the recipe's prio), so a Smelter pushes into the most urgent Fabricator first (`fabricator_wants_for()`).

### §2a-1b Sourceability caching across a pass (`lib/production_source.py` `SourceCache`)

`can_source_item()`, `can_source_fluid()`, `can_fulfill_order()` (§2a-0-5) each walk real game-API calls (Smelter/Fabricator discovery + `list_recipes()`, `outpost.buildings()`,
`journal.surveyed_sites()`, per-Warehouse `count()`), not free local compute.

`SourceCache` (instantiate once per pass, thread through every call) memoizes:
- `smelter_recipes()`/`fabricator_recipes()`/`surveyed_sites()` — each game call fires at most once per cache instance.
- `can_source_item()`/`can_source_fluid()` results per item/fluid-key — shared sub-item (e.g. Steel under both Circuit Panel and Iron Ingot) resolves once, not per branch. Separate `_item_stack` set does cycle detection so memo never poisoned with in-progress answer.
- Stock snapshot: `scan(outpost)` = one `stock_scan.scan()` per outpost per pass (`.stacks()` once per Inventory/Warehouse/Bin/Depot stockpile, `STOCKS_CHUNK` stores per atomic call, plus the home Crop Automators' Forage via `storage_take.crop_automator_forage()`), kept in `_scans`; every stock method is a scope over that scan, so Forage-fed recipes (Reinforced Biopolymer, Enrichment Compound) stay sourceable while the field keeps its Forage; `building_stock()` = holders among Inventory/Warehouses/Bins. Total cost `1+W` calls per pass regardless of distinct items — strictly better than `.count()`-per-item `total_stock()` (`D*(1+W)`).

- **Stock scopes** (`lib/stock_scan.py`: store kinds `INVENTORY`, `WAREHOUSE`, `BIN`, `DEPOT`, `AUTOMATOR`; scopes `LOCAL` = Inventory (home) + Warehouses + Bins + Automator Forage, `HELD` = `LOCAL` + Depots, `DEPOTS`, `STORES` = Warehouses + Bins): `stock(item)` = `LOCAL` at home; `local_stock(item, outpost)` = `LOCAL` there, what a machine port can `take()`; `depot_stock(item, outpost)` = `DEPOTS`; `held_stock(item, outpost)` = `HELD`; `network_stock(item)` = `held_stock()` at every outpost + cargo aboard haulers. `logistics_requests.outpost_stock()` and `PlanReads.stock()` = `HELD`, from the same scan. `stock_scan.held_units(item, outpost)` = a one-off `HELD` read (seed sweep, battery need, home salt). `tests/test_stock_scope.py` pins every counter's number against one world. Rule: **netting counts `held_stock()`** (Fabricator "make more" netting adds pipeline and staged inputs: `fab_have()`, §Pipeline netting; `_stock_fn()` blueprint cascades and reservations stay `held_stock()`, they protect units that can still be taken; Supply Dock readiness/local supply/affinity, `can_source_item()`, fleet intent, manual transit); **loaders count `local_stock()`** (`load_inputs()`, dock loading): a Depot pushes its freight to local consumers and stores (drones.md §2h), machines never pull from it. Ground haulers are the exception: they `take()` Depot stock above `depot_holds()` (§2i free stock).
- `_cascade_blueprint_demand()` result (blueprint + fleet-cargo walk) on `cache._blueprint_demand`; callers get a copy.

All three call sites default `cache=None` (private one-off `SourceCache()`), but hot paths build + share one: `plan_dock_assignments()` one per pass; `FabricatorController.step()` one per step.

**Recipe input table** (across passes, per script): `production._recipe_index()` builds `{output_item: {input_item: qty per output unit}}` from the Fabricator + Smelter recipe lists (first recipe per output wins, Fabricator first) and keeps it `RECIPE_INDEX_TTL_TICKS = 6000`, rebuilt early when a list's length changes (a research unlock); also memoized on `SourceCache._recipe_index` for the pass. `_recipe_inputs_for()` is a dict lookup on it (shared, read-only). Replaced a scan of every recipe per item per call (~40% of a Smelter step).

**Building discovery memo** (across passes, not on `SourceCache`): `production._discover_building_ids()` (Smelter/Fabricator/Supply Dock discovery) and `storage.discover_storage_buildings()` reuse their result for `DISCOVERY_TTL_TICKS = 20` ticks (~2 s) per `(type, outpost)`, so a new building is seen at most that late. A Smelter step alone runs about a dozen discoveries; `total_stock()` runs one per call. Cache = one-pass snapshot only — never held across ticks or reused between passes.

### §2a-1c Recipe switch with a paused unit (Smelter + Fabricator)

`is_running()` reads `False` while an unfinished unit waits (e.g. output full), but `get_progress()` stays > 0. The game then refuses `set_recipe(<other recipe>)` and `clear_recipe()` with `busy`; re-setting the same recipe keeps the progress. Progress is never lost, so the controllers call `set_recipe()` on `not is_running()` and retry next poll on `busy`.

### §2a-2 Fabricator input-stockpile ejection (`lib/fabricator.py` `eject_excess_inputs()`)

`set_recipe()`/`clear_recipe()` both leave input stockpile untouched — only built-in clear is `InputSlot.flush()`, which **permanently discards** material. `eject_excess_inputs()` runs every `step()`, before recipe selection, recovers stranded/excess staged material via `InputSlot.eject(destination, item_id, count)` (routes to least-full Warehouse with room via `storage.best_unload_target()`, or Inventory — never `flush()`) in two cases (both off currently-set recipe via `production.get_fabricator_active_recipe()`):

1. Staged material active recipe doesn't need (leftover from prior recipe, or no recipe) — eject all.
2. Staged material active recipe DOES need, beyond `required_per_craft * crafts_remaining` (same cap `load_inputs()` loads to) — eject excess only.

`eject()` transactional, safely no-ops on portion reserved for in-progress craft, so unconditional every-step call harmless.

### §2a-3 Fabricator fluid-input connections (`lib/fabricator.py` `ensure_fluid_connections()`)

Recipe's `fluid_inputs` (e.g. `{"water_in": 1.0}`) delivered via `FluidPort` connection, not Inventory/Warehouse take. `ensure_fluid_connections(recipe)` runs every `step()`, one `fluid_routing.FluidInputRouter` per fluid port (§1b **Input vs output routers**):

- Per `fluid_key` active recipe declares, `production.FLUID_SOURCE_TYPE_IDS[fluid_key]` names every building type that can feed it (e.g. `water_in` accepts `water_pump`,
  `steam_condenser`, `liquid_tank`, `bulk_liquid_reservoir`) — same mapping `can_source_fluid()` uses. Discovery is `production.discover_fluid_sources()` (§1b **Candidate helpers**).
- **Generic Liquid/Gas Tank existing ≠ proof it can supply given fluid** — buffers latch onto whichever fluid piped in *first*, hold only that until drained to `0`.
  `production.BUFFER_FLUID_TYPE_IDS` + `fluid_building_is_viable(fluid_key, type_id, building)` gate both `can_source_fluid()` and this discovery loop identically: dedicated producer always counts (fixed one fluid); buffer counts only once own `.fluid()` latched to needed fluid (`production.FLUID_LATCH_IDS`). Resolves bare `BuildingRef` to live component via `get_component(ref.id)` first when passed object has no `.fluid()`.
- **No `is_stalled()` on Fabricator itself** — reachability inferred from port's own `flow_rate()` staying `0` for `FLUID_STALL_STREAK_BLACKLIST_THRESHOLD=5` *consecutive* ticks while room to receive (`level() < capacity()`, `fluid_routing.port_starved()`, shared by every input router on a machine without `is_stalled()`) — legitimately full port also reads `flow_rate()==0`, must NOT count as stall. Same per-entry blacklist expiry as other connect/blacklist controllers (`FLUID_RESCAN_INTERVAL_TICKS=150`); `FLUID_DISCOVERY_CACHE_INTERVAL_TICKS=100`, `FLUID_NEUTRAL_GRACE_STEPS=5`. Candidates ranked by `fluid_routing.rank_sources()` ([power_fluids.md §1b](power_fluids.md) Candidate helpers); a healthy link on a near-empty tank or a Pump moves to a stocked tank.
- One router per `fluid_key` (`_fluid_routers`, created lazily) — recipe can need multiple fluids at once (oil-refining needs `oil_in` + `water_in`), independent sources.
- **Fluid-only recipe** (`is_fluid_only()`: fluid inputs, no item inputs, e.g. `craft_tar`) never goes idle while fluid flows. Once its `crafts_remaining` is 0, `step()` skips `ensure_fluid_connections()`, `stop_fluid_feed()` disconnects its fluid ports, and the recipe switch/clear runs even while `is_running()` (`busy` → debug, retry next poll). The router reconnects when a recipe needing that fluid is active again. It also pauses while its fluid's tanks are low: `fluid_low_reason()` reads that port's `FluidInputRouter.reachable_tank_fill(now)` (level/capacity over the discovered source tanks not blacklisted, i.e. the tanks it can switch to; producers skipped) every `FLUID_ONLY_RESERVE_REFRESH_TICKS = 100` into a latch that pauses below `FLUID_ONLY_PAUSE_BELOW = 0.05` and resumes at `FLUID_ONLY_RESUME_AT = 0.20` (no reachable tank of that fluid: never paused). A paused recipe is cut like a met one and skipped by `choose_recipe()` (debug line; the flip logs once at info). Why: the pause keeps a reserve for the consumers that never pause (Oil Generators on last resort, recipes with fluid plus items); throughput is set by the supply either way ([gameknowledge/fluids.md](../gameknowledge/fluids.md), "What to do in game").
