# Storage, Outpost Mining & Storage Upgrades (§2c, §2d, §2k-1, §2k-3, §2k-6, §2k-5)

Part of [`AI_CHEATSHEET.md`](../AI_CHEATSHEET.md). Pull logistics and site supply live in [`pull_logistics.md`](pull_logistics.md).

### §2c Storage Management (`lib/storage.py`, sweeps in `lib/storage_sweeps.py`)

Makes whole production chain aware of storage buildings, not just central home `"inventory"` endpoint. Scope (`STORAGE_TYPE_IDS`, Warehouses first): Warehouse (5 material-locked slots × 2,000), Large Warehouse (15 × 2,000), Storage Bin (1 × 500). `discover_storage_buildings()` wraps each bin in `BinStore`, a Warehouse-shaped view (one slot; `space_for(item)` = `space()` while empty or latched to that item, else 0; `materials()`, `slots()`, `capacity()`, `total()` derived), so every caller (unloading, `take_item()`, stock reads, sweeps, drone buffers) handles bins like Warehouses. An early outpost with only bins therefore unloads into them. Everything defaults to home outpost, matching Inventory only participating at Nocturna Base.

- `total_stock(item_id, outpost=None)` = Warehouses' and Bins' `count(item_id)` at `outpost`, plus `inventory.count(item_id)` at home only; no Drone Depots. A one-off loader/count read; netting counts `stock_scan` `HELD` (`SourceCache.held_stock()` §2a-1b, `logistics_requests.outpost_stock()` §2i). `inventory_count(item_id)` = home Inventory alone (0 if unreadable), for kit/part checks (fleet commission/upgrade, tank/warehouse swaps, wildlife MK2 packs).
- `outpost_is_home(outpost=None)`: `None` counts as home (every helper's default); reads `OutpostRef.is_home` (bool) or the Outpost component's `is_home()`. `local_port_target(outpost=None)`: resting port endpoint for a machine there (`"inventory"` at home, first local Warehouse id elsewhere, `None` if none).
- `best_unload_target(item_id, min_amount=1)`: among Warehouses and Storage Bins at `outpost` with `space_for(item_id) >= min_amount`, ranks by contents (`materials()`), never by recent `"busy"` answers. Sort key `(opens empty bin, clash, not holder, ...)`; among holders (Warehouse or latched Storage Bin) the one holding the most of the item wins (one `count()` per holder), so deliveries grow the main stack and never feed a stray; among new stacks `(neighbour heat, fill_percent())`. `take_item()` drains the emptiest bin, so two bins of one item converge into one. Opening an empty Storage Bin ranks after every Warehouse with room, even a clashing one: bins mean slots are tight, so a feeder wait beats locking a bin to one item (a bin already latched to the item ranks like a Warehouse holder). Then: a Warehouse without a **recipe partner** of the item that already holds it, then one without a partner (new stack), then the lowest clash (`item_heat(item) × item_heat(partner)`), holder first. An item stuck next to its partner therefore splits off once into a partner-free Warehouse, and every later delivery goes to that new stack; one Warehouse, or no partner-free one with room, gives plain consolidation. Neighbour heat (sum of `item_heat()` of the other contents) only counts for an item with heat > 0. `holders_only=True` skips every store not holding the item (no new stack, no Inventory). If nothing qualifies: `"inventory"` at home, `None` elsewhere (cargo stays aboard / staged).
  - **Partners** (`SMELT_PARTNERS`, `recipe_partners()`): each ore and its Smelter product (`iron_ore`/`iron_ingot`, `silicon`/`glass`, `titanium`/`titanium_ingot`, `cobalt`/`cobalt_ingot`, `lead_ore`/`lead_ingot`, `rare_earth`/`rare_earth_core`, `neutronium`/`neutronium_bar`). A Smelter takes the ore and sends the product at the same time, and a Warehouse handles one material operation at a time.
  - **Heat** (`ORE_HEAT_ORDER`, `item_heat()`): assumed transfer volume, hottest first: `iron_ore` 7, `silicon` 6, `titanium` 5, `cobalt` 4, `lead_ore` 3, `rare_earth` 2, `neutronium` 1; a product has its ore's heat, anything else 0. At home, a `must_stay_in_inventory()` item goes to `"inventory"` first while it has `space_for()` room and no active Supply Dock order there owes it (`_inventory_first()`), so hauled-in kits/modules skip the reclaim sweep. `vehicle_cargo.py`'s `unload_cargo()` picks destination **per stack**.
- **Top-up** (`top_up_target()`, `top_up_bin()`): when no holder (bin or Warehouse) has room for a whole stack, the fullest Storage Bin latched to the item takes what fits first; only the rest goes to `best_unload_target()` (possibly a new bin). Used by `drain_port_to_storage()` (not with `allow_partial`) and `vehicle_cargo.unload_cargo()`.
- `drain_port_to_storage()` sends each staged stack to `best_unload_target()`; a Warehouse answering `"busy"` (material endpoint lock, e.g. the one a blend was just taken from) is passed to `best_unload_target(exclude=, holders_only=True)` so the next-best holder of the item is tried, up to `BUSY_TARGET_RETRIES = 3` extra targets (the busy one is also `mark_busy()`'d). A retry never opens a new stack (Warehouse slot or empty Storage Bin); the stack waits for a busy holder instead. The Inventory rebalance direct move follows the same rule after a `"busy"` answer. All busy: the stack stays staged and callers' Inventory fallbacks apply.
- `eject_unneeded(port, keep, target=None, outpost=None)`: ejects every input stack not in `keep` to `target`, or without one to `best_unload_target()` at `outpost` (a stack no store has room for stays). Returns `["item:status", ...]`.
- `take_item(port, item_id, amount, outpost=None, cache=None, report=None)`: single function behind every `machine.input.take(item_id, amount)` call site. Tries **only endpoints holding item** (`_holder_candidates()`): Inventory first (home only — no own Auto Feeder, never locks), then Storage Bins by least stock (empty bin unlatches its material), then Warehouses by most stock; any endpoint answering `"busy"` within `TAKE_BUSY_COOLDOWN_TICKS = 20` (~2 s) moved last (still tried as last resort). No API to ask "is Warehouse busy?" upfront — `"busy"` rejection returns immediately (no feeder wait), so it is the probe; remembered per script in module-level `_recent_busy`. With `SourceCache`, holders come from its one-shot `building_stock(item_id)` snapshot (home only); else one `.count()` per building. `report` gets `{"sources": [(id, status, moved), ...]}`.
  Feeder time per transfer (simworker `hb()`/`mb()`): `max(1, round(units / speed × 0.01 h × 600 s/24 h × 10 ticks/s × fast))` ticks = **2.5 ticks/unit**, no fixed part beyond the 1-tick floor. `speed` = the faster endpoint's factor: Drone Depot 1/2/4 (S/M/L, ×2 with `depot_handling_unlock`), Plant Terraformer and Feed Maker by tier, every other store 1. `fast` = 0.5 after `research_fast_feeders` (400k TP), else 1. Locks every participating building for the duration.
- **Multi-Smelter Coordination** (`SmelterController`) — `production.discover_smelter_ids()` finds Smelters at runtime. Inventory-manager sweep runs centrally from orchestrator_automation.py's AUTOMATION section (§1a-1). Each smelter's `select_needed_ore()` claims its recipe (`claim_recipe()`/`release_recipe()`, `archive.transaction("smelter.recipe_claims",
  ...)`, per outpost like `fabricator.recipe_claims`, `RECIPE_CLAIM_STALE_TICKS = 600`; both machines share `lib/recipe_claims.py` `RecipeClaimMixin`) before crafting, so two smelters don't start same recipe while other demanded ore sits untouched. A claim this machine won is re-written only every `CLAIM_REFRESH_TICKS = 100` (Smelter and Fabricator, per instance `_claim_ticks`); in between `claim_recipe()` answers from memory. Losing the claim or `release_recipe()` clears the memory; a clock reading 0 always takes the full path. A plan outlives the stale window (`PLAN_BACKSTOP_TICKS`), so every step between replans calls `renew_claim()` on the planned recipe (only when this machine holds its claim; a joiner stays unclaimed).
  - **Pile-on fallback**: if only ONE ore demanded, `select_needed_ore()` collects every
    sourceable/demanded candidate, tries to claim each, and if none can be claimed exclusively,
    joins the first anyway rather than idling. Joined smelters split intake via the demand-share
    and fair-share caps (§2a-0-2) and self-throttle together as `get_smelter_demands()` nets down.
- **"Inventory manager" sweep** — `rebalance_inventory_to_warehouses()`, called once per `STORAGE_TICK_INTERVAL` cycle from orchestrator_automation.py's AUTOMATION section, home outpost only (Inventory exists only there): any **propertyless** Inventory item moved to Warehouse **entirely** when it spans more than `INVENTORY_REBALANCE_SLOT_THRESHOLD = 2` slots, or already split (some in Inventory, some in Warehouse — `_warehouse_item_ids()`). Skipped while home has no store (no non-retiring Warehouse or Storage Bin), so a home without Warehouses logs no "Could not clear" warnings.
- **Inventory free-slot reserve** — `storage.INVENTORY_FREE_SLOTS_KEEP = 4` empty Inventory slots stay free for Shop buys, `undeploy()` and module swaps. `inventory_room(item_id)` = `space_for()` minus the held-back empty slots × stack size (partial-stack room stays usable). Applied by: `best_unload_target()` (Inventory-first and home fallback need room ≥ `min_amount`, else None), `_send_to_best_target()`/`drain_port_storage_first()` (cap sent units), `drain_port_inventory_first()` (rest goes to a Warehouse, else stays staged), vehicle `unload_cargo()` (partial unload, rest stays aboard), Supply Dock cargo drain, `reclaim_inventory_only_items_from_warehouses()`. Not applied: rebalance swap eviction (net slot gain), deliberate pulls for immediate use (field keeper, wildlife planner, crop/field ejects).
  - **Exception**: `item_catalog.lookup(item_id).category` of `"equipment"`, `"module"`,
    `"portable"`, or `"upgrade_pack"` (`NON_WAREHOUSABLE_CATEGORIES`, `must_stay_in_inventory()`),
    plus the ids in `INVENTORY_ONLY_ITEM_IDS` (drone hardware, `AGRICULTURE_DEPLOY_KITS`: biosphere
    kits the catalog files as `"agriculture"` although they deploy from Inventory), are never swept — equipment and building upgrade packs apply from Inventory only;
    modules/portables must be in Inventory to equip a vehicle. `"construction_kit"` is NOT in this set (placed via blueprint construction, fine to
    warehouse).
  - **Direct move**: `inventory.transfer_to(best_unload_target(item_id, 1, exclude=tried))` with
    everything left, then the next-best pick for what didn't fit or answered `"busy"`, so the
    item joins its existing holder instead of opening stacks in several Warehouses.
  - **Swap fallback**: if no Warehouse has any room, evicts whichever Warehouse occupant is
    cheapest to bring back (smallest quantity) — only when `slots_freed > slots_reclaimed`
    (`slots_reclaimed = ceil(evicted_qty / inventory_stack_size())`), a genuine net reduction.
    `slots_freed` is computed from `remaining` (units still stuck *at swap-fallback time*, after
    any direct-move already ran). In practice a swap is only a net win
    for a small-quantity occupant (roughly `slots_freed * stack_size` units or fewer); a
    persistently-fragmented item logs `[storage] Skipping swap for <item>: ...` /
    `[storage] Could not clear...` / `[storage] Swap for <item> did not go through...` /
    `[storage] Freed a slot... but it still reports no room...` instead of silently continuing.
- **Fleet part keep** — `storage.FLEET_PART_KEEP`: home Inventory holds at most 1 drone chassis or Depot kit and `FLEET_MODULE_KEEP = 4` of each Battery Pack / Cargo Pod / Oil Tank / Electric / Heli Thruster id (4 = the largest `drone_upgrade.FIT_LOADOUTS` count of one category, a large scout's Battery Packs). `fleet_part_keep()` drops the keep to 0 for a tier below the best craftable one of its `FLEET_PART_LADDERS` ladder (chassis, Depot kit, Cargo Pod, Oil Tank; `production_cascade.fabricator_unlocked_outputs()`), so an outgrown chassis or module waits in a Warehouse; with nothing of the ladder craftable every tier keeps. Each unit takes a whole Inventory slot, so queued drone kits and the parts a swap returns would fill Inventory and stall unloads. `inventory_part_room()` = `inventory_room()` capped at what Inventory lacks of `fleet_part_keep()`; used by `best_unload_target()`'s Inventory-first rule, `_send_to_best_target()` (a Fabricator drain sends the keep's share to Inventory, the rest to a Warehouse) and the reverse sweep (tops Inventory up to the keep as parts get used). `park_surplus_fleet_parts()` (storage pass, before the reverse sweep, home only) moves Inventory units above the keep to `best_unload_target()`, where one id shares a Warehouse slot.
- **Bin consolidation** (`consolidate_storage_bins()`, once per storage pass from `orchestrator_automation.py`, every outpost): the smallest Storage Bin of an item held by 2+ bins at one outpost, at most `BIN_CONSOLIDATE_MAX_UNITS = 200`, moves into the fullest other bin of that item with room for the whole stack, `BIN_CONSOLIDATE_CHUNK = 20` units per call (`transfer_to()` blocks the calling script ~2.5 ticks per unit), one transfer per call over all outposts. Recently `"busy"` bins are skipped. The emptied bin unlatches.
- **Storage snapshot** (`storage.StorageSnapshot`, one per storage pass in `orchestrator_automation.py`): one `slots()` read per store per outpost (atomic, `STOCKS_CHUNK` stores per call), shared by the rebalance, reclaim, bin and stray sweeps. A sweep that moves units calls `touched(ids)`; those stores are read again on the next access. Other changes during the pass are accepted as stale (`transfer_to()` reports `"partial"`). `slot_layout(outpost, snapshot=None)` reads through one too.
- **Warehouse strays** (`consolidate_warehouse_strays()`, once per storage pass after bin consolidation, every outpost): a `"busy"` retry, partial drain or full slot can leave a small second stack of an item in another Warehouse. The smallest Warehouse holder of an item held by 2+ stores, at most `WAREHOUSE_STRAY_MAX_UNITS = 200`, moves `WAREHOUSE_STRAY_CHUNK = 20` units per call into `best_unload_target(item, count, exclude=[source], holders_only=True)` (biggest other holder with room for the whole stray), skipped when that holder's recipe-partner clash is higher than the stray's own. Runs only while the stray's Warehouse has no empty slot, the item has `WAREHOUSE_STRAY_MANY_HOLDERS = 3` or more holders, or the stray shares its Warehouse with a recipe partner (`recipe_partners()`); otherwise a second holder costs nothing and gives `take_item()` a fallback while one answers `"busy"`. Recently `"busy"` and retiring stores are skipped; one transfer per call.
- `inventory_stack_size()`: `10`, or `20` once `research.is_unlocked("research_high_density_storage")` ("Bigger Stacks").
- **Reverse sweep** — `reclaim_inventory_only_items_from_warehouses()`, called right after "inventory manager" sweep from `orchestrator_automation.py`'s AUTOMATION section: any Warehouse stock whose `item_catalog` category in `NON_WAREHOUSABLE_CATEGORIES` (`must_stay_in_inventory()`) moved back to Inventory up to `inventory_part_room()` (free-slot reserve, fleet part keep). Such stock lands in a Warehouse when Inventory had no room, as parked fleet part surplus, or by manual stash.
  Each slot moves with `property_match="exact"` so durability-bearing variant not merged with different variant of same `item_id`.
  - **Dock-demand exception** (`_items_demanded_by_active_dock_orders()`): an item still owed by any
    Supply Dock's active order is left in the Warehouse instead — `supply_dock.py` already ships
    straight from a Warehouse via `take_item()`/`total_stock()`, and a bulk Earth Order contract for
    a "deployable" equipment item can run hundreds of units deep, far more than Inventory has slots
    for. Self-contained (own `outpost.buildings("supply_dock")` scan) rather than importing
    `production.py`, which itself imports from this module.

### §2d Outpost Mining: Active Ores, Reach & Stock Targets (`lib/outpost_mining.py`)

Answers "which ores are worth a buffer?", "which ores can outpost X's miners reach?" and "how much to stockpile?" — consumed by the stationed-mining role (§2e) and the ore planners (§2i-1, dock roles). No map markers: a stationed miner mines `NEED` demand plus a `STOCK` buffer of each active ore, from any surveyed site it can cut and reach. Leftover `resource.` markers from older builds are cleared by `unsupported_markers.clear_resource_markers()` (`ArchiveCleaner.clean_resource_markers()` stage, and every `update_unsupported_markers(clear_previous=True)`: the once-per-run backfill and the panel's "Sync Unsupported" button).

- **Active ores** (`active_ores()`, `latch_active_ores()`): archive `mining.active_ores` (`ACTIVE_ORES_KEY`) = `[ore_item_id, ...]`, add-only. An ore joins when any site's plan wants it, or its Smelter product, at `NEED` or above (`site_supply.needed_ores()` after each plan pass), or a stationed miner's bands hold it at `NEED`+ (`vehicle_mining.stockpile_bands()`). Only active ores get a `STOCK` buffer (smelting-site floor, stationed miner's stockpile), so ores start buffering in the order demand first reaches them.
- **Ore buffer room** (`ore_buffer_fits(outpost, ore)`): `storage.slot_room()` over `storage.slot_layout()` with `ORE_BUFFER_FREE_SLOTS = 1` kept empty: room left in the slots already holding the ore, or, with none, one empty slot beyond the reserve. An outpost with no store building passes.
- **Mining reach** (`publish_reach()`, `mineable_ores_by_outpost()`, `mineable_ores(outpost_id)`): archive `mining.reach` (`MINING_REACH_KEY`) = `{vehicle: {"outpost", "ores", "tick"}}`, the ores a stationed miner's drill cuts at a surveyed site a full battery reaches from its outpost. Written by the miner on change or every `REACH_REFRESH_TICKS = 6000`; entries older than `REACH_STALE_TICKS = 36000` don't count; `ArchiveCleaner.clean_mining_reach()` drops vehicles gone from the fleet.
- **`resource_assignment_range_m()`** — archive key `RESOURCE_ASSIGNMENT_RANGE_KEY = "outposts.resource_assignment_range_m"`, default `200.0` m: a site this close to an outpost counts as minable without a long haul (`vehicle_survey.outpost_weights()` scan-stop weight, autoplay `outpost_needs`).
- **`ore_stock_target(item_id)` → units** — one global `{ore: units}` dict under `mining.ore_stock_targets` (`ORE_STOCK_TARGETS_KEY`), same number at every outpost: mining-outpost stockpile, home floor, smelting-site ore buffer. Default `storage.default_stock_target()`: `BIN_STOCK_TARGET = 400` (80% of a 500-unit Storage Bin) until `research_warehouse` (`WAREHOUSE_TECH_ID`) is unlocked, returned without seeding; after the unlock `WAREHOUSE_STOCK_TARGET = 1800` (90% of a 2000-unit Warehouse slot), seeded into the archive on the first lookup of an ore, then editable. Both stay below one slot so a small overshoot (late Smelter batch, full Pioneer load) fits the slot already holding the item instead of opening a second one. Archive values seeded earlier keep their number. The old per-outpost `outposts.ore_stock_targets` is purged by `ArchiveCleaner.clean_retired_keys()`.
- **`RAW_ORE_ITEM_IDS`** (`lib/game_rules.py`) — the 7 mineable ore item ids; **`HOME_OUTPOST_ID = "outpost_home"`**.

### §2k-1 Warehouse → Large Warehouse Upgrade (`lib/warehouse_upgrade.py`, headless `builder_automation.py`)

The state machine shared with §2k-3 (gate, buy, deploy/adopt, status line, refusal counting, `TRANSIENT_UNDEPLOY_STATUSES` (owned by `lib/pillar_swap.py`), kit selling) lives in `lib/building_swap_upgrade.py` `BuildingSwapUpgrader`; each subclass supplies its type ids/labels, `_start_next()` (group selection) and `_drain()`.

Same gate as §2k (FLEET card Drones-tab switch `fleet.upgrade["enabled"]` + mining-drill phase), plus `research_high_bay_warehousing` unlocked and the cash manager's grant for the Large Warehouse price (Shop catalogue, fallback `LARGE_PRICE_FALLBACK = 60000`; consumer `warehouse_upgrade`, planned = every remaining swap, §2l). **One swap at a time network-wide**, `SWAP_RATIO = 2`: up to two Warehouses at one outpost → one Large Warehouse (10 slots/20k → 15 slots/30k; fewer buildings for Auto Feeder consumers to walk). Outpost with the fewest free store slots first (`slot_layout()` rows with no item or count 0: Warehouse, Large Warehouse and Storage Bin slots; a slot-full outpost jams its Depot), ties to the most plain Warehouses; there, the two emptiest (`total()`, fastest drain). A lone leftover Warehouse is swapped 1:1 (+5 slots, +10k units). State in `fleet.upgrade["warehouse_swap"]` (status line `fleet.upgrade["warehouse_status"]`), restart-safe.

- `buying` (`shop.buy("large_warehouse")`, skipped if one is in Inventory; snapshot of the outpost's Large Warehouses) → `deploying` (`computer.deploy("large_warehouse", outpost)` or adopt a new one not in the snapshot; going over the outpost building count is accepted, it's brief) → `draining` → done. States run **back to back in one pass** (no sleep between buy, deploy and drain start): a freshly deployed empty Large Warehouse is the least-full store, so other unloaders and `orchestrator_automation.py`'s Inventory rebalance fill it within seconds. Refused deploy (`building_ops.classify()` fatal: `deploy_limit` etc.) or undeploy refused `MAX_ATTEMPTS = 5`× in a row → `blocked`; operator deletes `warehouse_swap` to retry. `TRANSIENT_UNDEPLOY_STATUSES` (`inventory_full`: no Inventory room for the returned kit; `error` / `no_computer` from `building_ops.undeploy()`) never count as attempts: the swap waits, and a swap blocked by one of them resumes by itself. Switch off only cancels a `buying` swap with nothing bought yet and no building deployed (not a re-buy).
- **Drain in passes, retiring stores**: each old Warehouse is emptied with back-to-back `transfer_to(new, item, ≤ DRAIN_CHUNK_UNITS = 200, properties=exact)` calls for at most `DRAIN_PASS_TICKS = 600` ticks per pass (checked between calls, so a pass can run one chunk over); then the step returns `draining, N unit(s) left` and the next pass carries on. An emptied Warehouse is undeployed immediately and its kit sold (`shop.sell("warehouse", n)`; only the kits this swap got back, counted in `to_sell`). While the swap is `deploying`/`draining` (`building_swap_upgrade.RETIRING_STATES`) or re-buying (`buying` with `new_id` set), its old stores not yet removed are in `storage.retiring` (`RETIRES_STORES = True` on the Warehouse and bin upgraders; any other state, a block included, releases them): `best_unload_target()`, `top_up_target()`, `local_port_target()`, the Inventory sweep and bin consolidation skip them; `take_item()` and stock reads still use them. Each script reads the set through a `DISCOVERY_TTL_TICKS` cache, so one late delivery can still land; stock that slips in is drained on the next pass (`undeploy()` answers `cargo_present`). Target = new Large Warehouse, else any non-retiring Warehouse/Large Warehouse at the outpost with `space_for > 0`. `"busy"` → retry after `BUSY_RETRY_S = 0.2` s, at most `MAX_BUSY_RETRIES = 50` in a row per chunk; `DRAIN_MAX_IDLE_PASSES = 5` passes with nothing moved → give the step back (`stuck with N unit(s)`).
- **Why its own Automation**: feeder ~2.5 ticks/unit (§2c) → a full pair takes tens of game minutes to drain, split into `DRAIN_PASS_TICKS` passes so the Automation's other steps keep running; Warehouses have no script slot. `builder_automation.py` idles `IDLE_SLEEP_S = 3` s between passes. Status line printed (info) whenever it changes beyond its numbers; per-chunk moves, target fallbacks and undeploy answers at `debug()`.
- **Storage Bins → Warehouse (`BinUpgrader`, same module, interim)** until the autoplay builder upgrades bins by slot demand (TODO.md). Same state machine and greedy drain; same FLEET switch but no mining-drill wait (`WAIT_FOR_DRILLS = False`): starts on the Warehouse unlock. Storage Bins → one Warehouse, planned by slot: per material, the emptiest latched bins are packed into Warehouse slots of at most `SLOT_UNITS = 2000` units each (any number of bins: 8 quarter-full bins → 1 slot), biggest slots first, at most `WAREHOUSE_SLOTS = 5` slots, plus every empty bin. Any bin starts a swap, so every bin goes; bins past 5 slots wait for the next swap. Warehouses bought per outpost ≤ ceil(bins / 4). Needs `research_warehouse` (`storage.WAREHOUSE_TECH_ID`); price from the Shop catalogue, fallback `LARGE_PRICE_FALLBACK = 3000`; consumer `bin_upgrade` (§2l). Outpost whose plan retires the most bins first. Drain targets follow `storage.best_unload_target()` with the retiring bins excluded (existing stack of the item first, so a material's bins merge into one slot; never opens an empty bin); fallback = new Warehouse, then other Warehouses/Large Warehouses. Each drain pass calls `storage.forget_storage_discovery()` so the routing sees the new Warehouse at once. **Re-buy**: other deliveries can take the new Warehouse's slots mid-drain; `STUCK_PASSES_BEFORE_REBUY = 3` drain steps in a row that end stuck with no store at the outpost having room (counter `stuck` in the swap dict, reset by any move) send the swap back to `buying` (`BuildingSwapUpgrader._rebuy()`, cash-gated by `_can_buy()`, old bins stay retiring); the new Warehouse becomes the drain target, the previous one stays as a fallback. The Large Warehouse swap never re-buys (`STUCK_PASSES_BEFORE_REBUY = 0`). State in `fleet.upgrade["bin_swap"]` (status `fleet.upgrade["bin_status"]`). Runs first in the Automation loop, before the Warehouse pair step.

### §2k-3 Liquid Tank → Large Liquid Tank Upgrade (`lib/tank_upgrade.py`, same headless `builder_automation.py`)

Same gate as §2k-1, plus `research_reservoir_engineering` unlocked and the cash manager's grant for the Large Liquid Tank price (Shop catalogue, fallback `LARGE_PRICE_FALLBACK = 15000`; consumer `tank_upgrade`, §2l). Kit and building type id `bulk_liquid_reservoir` (not `large_liquid_tank`). **One swap at a time network-wide**, `SWAP_RATIO = 5`: up to 5 Liquid Tanks of one liquid at one outpost → one Large Liquid Tank (100 t each → 1,000 t). Leftovers are swapped too (7 tanks → 2). A tank's liquid = its latch, else its `tank_assignments` entry; a tank with neither is skipped, and so is an exotic one (`wildlife_data.EXOTIC_FLUIDS`) once Wildlife is complete (`wildlife_common.wildlife_complete()`; the Wildlife planner undeploys those, [wildlife.md](wildlife.md)). Biggest (outpost, liquid) group first; there, the emptiest tanks. State in `fleet.upgrade["tank_swap"]` (status line `fleet.upgrade["tank_status"]`), restart-safe. Runs after the Warehouse step in the same loop; a Warehouse drain delays it.

- `buying` → `deploying` exactly as §2k-1 (snapshot, adopt, same blocking deploy statuses), back to back in one pass → `draining`.
- **Draining, non-blocking** (one check per pass): every pass re-asserts `fluid_routing.tank_assignments` — new tank → the liquid (replaces any blank `""` from `warn_about_unassigned_tanks()`), each old tank not yet removed → `RETIRING_ASSIGNMENT = "retiring"`. `tank_is_eligible_target()` rejects a retiring tank before its latch check, so producers' `FluidOutputRouter`s move to the new tank; consumers still pull from the old ones until they run dry. The new tank's `liquid_in` is connected to the first old tank; once `is_empty()` the port is disconnected, the old tank undeployed, its entry dropped and its `liquid_tank` kit sold (only kits this swap got back, `to_sell`); then the next old tank.
- Undeploy only once empty: undeploy drops the liquid a tank holds (fluid never blocks it, simworker `CD()` checks item bins only). A stopped drain (new tank full, or a producer that can't reach the new tank still feeding the old one) waits; the status line shows the level and `" (new tank full)"` / `" (still fed N t/h)"`. `cargo_present` = liquid slipped in, drain again; `TRANSIENT_UNDEPLOY_STATUSES` wait. Other undeploy refusals, `connect()` refusals or a broken link state (`BROKEN_CONNECTION_STATES`) `MAX_ATTEMPTS = 5`× in a row → `blocked`; operator deletes `tank_swap` to retry.

### §2k-6 Machine Tier Packs (`lib/machine_pack_upgrade.py`, same headless `builder_automation.py`)

Runs every `FLEET_TICK_INTERVAL`, gated by the FLEET card's auto-upgrade switch (`drone_upgrade.is_upgrade_enabled()`). A pack counts only once its Fabricator recipe is unlocked (`fabricator_unlocked_outputs()`); a pack already in Inventory is applied anyway.

- **Fabricators and Smelters**: `PACK_LADDER` = Fabricator Mk II, Smelter Mk II, Fabricator Mk III, Smelter Mk III, one step at a time. The step's machines are those one tier below its target (`components.machine_tier()`). Packs in Inventory go on at once via `computer.upgrade(pack, machine)`; the rest is ordered as `min(left, ORDER_BATCH = 2)` minus Inventory under requester `machine_upgrade` (UPGRADE band, in `STANDING_ORDER_REQUESTERS`). `tier_too_high` counts as done; `under_construction` / `item_not_in_inventory` retry next pass.
- **Oil Pumps** (`poi_extractor_ids(("oil_pump",))` below Mk II, once `oil_pump_upgrade_pack_mk2` is unlocked): one `construction_blueprint.plan_upgrade()` at a time, none while any `"upgrade"` blueprint is pending, paused or active. A Pioneer runs it like any blueprint; the pack reaches the Fabricators as blueprint demand. `target_claimed` = already planned.
- Any other refusal (e.g. `not_enough_power`: Mk II draws 1.5×, Mk III 3×) parks that machine for `REFUSED_RETRY_TICKS = 18000`, so the ladder moves on without it.

### §2k-5 Storage Outpost Expansion (`lib/storage_expand.py`, same headless `builder_automation.py`)

A storage outpost (`site_supply.storage_outposts()`, §2i-1) fills to capacity with evicted leftovers, so it gets more stores instead of a cap. Each pass: storage outposts with fewer than `FREE_SLOTS_MIN = 2` empty slots in all (`storage.slot_layout()`: each Warehouse slot, each Storage Bin) raise a `StatusWarning` on the builder script and the summary on the AUTOMATION card (`IDLE_SUMMARY` when none). The one with the fewest empty slots gets one store per pass: `KITS`, best unlocked first (Large Warehouse once `research_high_bay_warehousing`, else Warehouse; ids, research and fallback prices from `WarehouseUpgrader`/`BinUpgrader`). Bought through the cash manager (consumer `storage_expand`, planned = one kit per short outpost, §2l) unless a kit is in Inventory and no swap of that type (`fleet.upgrade` `warehouse_swap`/`bin_swap` in `buying`/`deploying`) owns it; then `computer.deploy(type, outpost)` and `forget_storage_discovery()`. After a deploy, or a refused one, that outpost waits `SETTLE_TICKS = 600`; a refused deploy keeps the kit in Inventory for the retry. No FLEET switch gate: the cash manager is the only brake.
