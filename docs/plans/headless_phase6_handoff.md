## Phase 6 (optional)

1. Construction `instant`: read `ConstructionSystem.tick` in the decompiled worker for the progress field a build job carries, add an anchor to `anchors.mjs` (stable string, exactly one match, warn-and-disable), and a mode on a `construction` group (none exists yet: `GROUPS` in `standins.mjs` has no construction group; the builder Pioneers are `logistics`). A/B on 0262 (12 Pioneers, builds in progress): build completion ticks real vs `instant`, kits consumed, errored.
2. Power `topup`: find the battery storage field (`power.stored` in the metrics comes from the grid report; the per-battery field is in the machine data) and set every battery to capacity each tick. A/B on 0142 (batteries cycle: `stored` 1,182-2,449 over the run): brownout seconds, `stored` trace, heat gained.
3. A `trim` row with an effect, if a save with surplus generators appears (the 20261008 run's later saves, `1211`-`1220`, have more generators; check `peak × margin / perGenerator` against the count first).

Pitfalls that still apply: `pass(t)` counts from the run's start, archive ages use `state.tickCount`; `--only-scripts` pins `keep` and a stand-in skips kept slots; validate params for value before any side effect; the watcher does not cover `devtools/`; a group that is off or stood in has a boundary (`GROUPS[g].produces` / `consumes`) and the A/B gaps come from there first, name them in ab_results.md rather than tuning the stand-in; `scale` removes kits, so net worth starts lower in a stand-in run; `final_save.json` is the raw state (no `state` wrapper, unlike a game save) and is UTF-8.
