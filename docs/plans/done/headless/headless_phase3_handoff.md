## Phase 3: logistics `mover`

Goal: a JS item mover that serves `logistics.requests` directly (take from a source store, deliver after a travel delay) so the hauler fleet can be `off` while the orchestrator and the requesters see one consistent world. The design is in standins.md "Logistics `mover`" and the plan file; a throughput upper bound, never a fleet model.

Build order (plan file "Phases" phase 3 and "Delegation"):

0. `cavecrew-investigator` re-verifies in `scripts/4_controlpanel/lib/` before any code (grep, read ranges; the plan's line numbers are from 2026-10-14): `logistics_requests.py` (`set_requests()` shape `{outpost: {item: {levels, have, by, tick, buy?, keep?}}}`, `REQUEST_STALE_TICKS`, `_unchanged()`, `reserve_pickup()` pickups shape, `release_pickups()`, `in_flight()`, `drone_haulers_present()`), `priority.py` (`request_target()`, `tier_level()`, the ladder), and which keys only drone scripts read (`drone.mission`, `drone.heli_free`, `depot.stage`) so the mover can skip them. Output: a file:line table plus the exact dict shapes.
1. **Spec in the main thread** (before the builder): the pickups key format `logistics.pickups["pull:standin_mover:<dest>:<item>:<source>"] = {vehicle, dest, source, item_id, units, tick, aboard: true}`, deletion on arrival, how deficits are computed (live store count minus in-flight, never `have`), source choice (nearest outpost with stock above its own request target, `planet.outposts[].x/y`), `sim.buy()` for `buy: true` entries, travel `loadTicks + 10 * distance / speedMps`, whether `fleet.status` needs a `standin_mover` heartbeat for `drone_haulers_present()`.
2. **`standins.mjs` mode `mover`** (`MODES.logistics.mover`, remove `PLANNED.mover`): params `{every: 100, speedMps: 12, loadTicks: 50}`; `#moverSetup` stops the group's hauler scripts like `off` (ghosts = stopped, overridable by the scenario's `ghosts.logistics`), `#moverPass(tick)` every `every` ticks reads the key via `sim.getArchive`, moves items with `stacks.mjs` (`takeAt`/`addAt`, `countAt`; `outpost:<id>` addressing), keeps a queue of arrivals, writes and deletes pickups. Supply docks that must stay real go in `keep`. A builder can take the handler once the spec is fixed; `test/mover.test.mjs` on a fake state (two outposts, a requests key, warehouse stacks: deficits, source choice, arrival timing, pickups appear and disappear, overflow retry).
3. **Report**: `summary.standins.mover = {moved: {item: units}, trips, pendingUnits, bought}`; scenarios.md Output row; standins.md phase row and Modes row.
4. **A/B** (ab_results.md "Open rows"): 0262 with factory real, drones vs mover: ingots and kits reaching outposts per hour; and `--standin logistics=mover` with everything else real: `errored` 0, no fleet warnings. `cavecrew-reviewer` on the diff before the runs; runs in the background (20 game minutes on the midlate save take ~13 min wall each).
5. **Docs**: DESIGN_HISTORY entry (pickups emulation so requesters see one world; upper bound, not a fleet model); `archive_ipc.md` if the mover writes any key of its own.

Risks the plan lists: the mover over-delivers when `in_flight()` does not see its pickups (shape must match `reserve_pickup()` exactly); `drone_haulers_present()` may switch requesters into the drone-yield branch; `logistics.requests` entries go stale (`REQUEST_STALE_TICKS`) and must be dropped, not served; `have` is never trusted.

Pitfalls from phases 1 and 2 that apply here too:
- `--only-scripts A,B` pins slot ids in `keep`, and a stand-in mode skips machines whose slots are kept, so a scenario file (`default: "off"` plus explicit modes) is the way to isolate a group; two such files were used for the power check (`iso_real` / `iso_scale`, in the scratchpad, not checked in).
- Tests use fake sims (`test/standin.test.mjs`, `test/scale_groups.test.mjs` `fakeSim`): extend one with `getArchive`/`setArchive`, outposts and store machines rather than loading a save.
- The watcher does not cover `devtools/`, so no sync hold is needed for these files; never put probe files under `scripts/`.
- Validate scenario params for value, not only name (`validateScenario` checks names only; `scale` checks `perRecord`/`max` at setup).
